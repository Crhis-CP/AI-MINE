> 计划版（status: specified）：下面是实现 PR 要满足的要求，不是本计划 PR 的交付结果。

四步优化第一步（决定台账“DEC-78补充·分工确认与四步优化”，Owner 2026-11-11）。来源：2026-11-11 全项目审查。

## 背景（为什么做）

`sources.adapt-intervals` 每天 04:20 按近 7 天的发稿量，把所有启用的资讯信源的 `interval_minutes` 重写到 15～60 分钟之间（付费读取的列表 60～120，热度信号最多 180）。后台允许把间隔设成 1～1440 分钟，但设完最多撑到当晚就被改回去，后台没有任何提示。函数注释写的范围（15～120）也和代码不一致。

## 交付内容（做什么）

- **迁移**（只追加一列）：`sources.interval_pinned boolean NOT NULL DEFAULT false`。已有信源一律不加标记，因为它们现在的间隔是程序写的，不是人设的。
- `admin/sources.ts`：后台保存信源时只要改了间隔，就把标记置为真。
- `sources/collect.ts`：夜间调整跳过带标记的信源；注释改成实际范围，并写明清单里的间隔只是起始值。
- 清单（`industry/sources.json`）里的间隔不加标记：新导入的信源仍由程序按发稿量调整。

## 测试

- `tests/source-lanes.test.ts`：后台把一个资讯信源的间隔改成 240 分钟后再跑夜间调整，仍是 240；没改过的安静信源照旧被调到 60。
- `migration-inventory` 自测含新迁移；verify 里列的数据库测试全部通过。

## 上线后（Codex）

- 带迁移，按惯例单独发布。迁移只加一列，有默认值，不锁表重写。
- 只读核对：`SELECT count(*) FROM sources WHERE interval_pinned` 为 0（上线时没有人工标记）。

## 没做什么

- 后台页面暂时没有“取消人工设定”的按钮，也没有在间隔旁标出“人工设定”。放在第三步后台改版里一起做；在此之前要取消标记可以由 Codex 按 Owner 指示改库。
- 不回填清单里的 120/180/360：这些值上线后早已被夜间调整覆盖，恢复它们等于整体放慢抓取，是否需要另议。
