## 背景（为什么做）

结论：TASK-0092 把 Owner 的信源表放进了行业包，TASK-0093 让信源分了业务线；这张卡把信源表里有采集配置的条目建成真正的法规线信源，部署以后就能按批启用、开始采集。

照上游的做法：`scripts/seed.ts` 从行业包读信源，新的一律停用、不排期，已存在的不覆盖（`scripts/seed.ts:1-3`、:29-42）。但它不建许可记录，按它建出来的信源一采集就报“Source date permission missing”（`packages/backend/src/sources/collect.ts:148-149`）；后台建信源用的 `createSource` 会同时写负责人声明的许可（`packages/backend/src/admin/sources.ts:198-244`，DEC-33）。所以法规信源改走 `createSource`，再加一个只给脚本用的 `lane` 参数。

现在法规与资讯的抓取共用一个队列、一个并发池（`jobs/sources.ts:11-12`，默认 8 个），入队不带优先级，调度每分钟取 40 条（`sources/collect.ts:276-286`）。一次启用几十个政府网站，它们的首次抓取会排在资讯前面，资讯采集被推迟几分钟到十几分钟（INV-42 要防的“一条线占住另一条线”）。分线排队要另一张卡（TASK-0111）；在那以前，启用脚本强制分批：每次只开一个国家或一份指定清单、最多 10 条。信源表里的状态是核对时的结论，启用时可能已经过了几天、栏目改版了，所以启用前当场用生产同一套采集器试抓一次（`previewSource`，`admin/sources.ts:72-89`，只取不存），取到才开。

## 交付内容（做什么）

1. `admin/sources.ts`：`createSource(input, actor, opts?: { lane?: "news" | "policy" })`，默认 `news`，插入时写 `lane`。后台“新建信源”的接口与页面不变（仍是资讯线）。
2. `scripts/seed.ts` 加 `seedPolicySources(entries)`，在现有的 `seedSources` 之后跑：
   - 只建信源表里有 `collect` 且状态是 `ready` 或 `needs_overseas` 的条目；`needs_reader` 等 Owner 同意网页读取服务（TASK-0092 的 Owner 决定）以后再建，`blocked`、`reference_only`、`identity_pending` 本来就没有 `collect`。
   - 信源 ID：`policy-` 加信源表编号的小写，例如 `CN-004` → `policy-cn-004`；名称：机关中文名 · 信源中文名。
   - 照信源表写 `kind`、`config`；采集间隔 360 分钟；`tier = 'T1'`（官方一手）；`syndicate_fulltext = false`（全文 RSS 照上游默认关）。`site_fulltext` 照 Owner 在选择卡片 D2 上的选择（写成 `seed.ts` 里的一个常量，Owner 选 B 或 C 就在部署前改它）：默认只有 `terms = open` 的为 `true`，其余为 `false`，这是 DEC-33 保留的逐源收紧——网站自己的条款没有允许翻译转载（`createSource` 据此把“公开原文全文”“公开译文”两项用途写成禁止，`admin/sources.ts:218`）；以后 Owner 放宽，走后台“编辑权限并填写依据”，不靠重跑初始化。
   - 许可范围：入口网址的主机名，路径前缀 `/`；信源表若写了文书所在的其他主机（例如附件在另一个子域名），一并列入；`attachments_in_scope = true`。
   - 新建的停用、`health = 'paused'`、不排期。先按 ID 查在不在（`SELECT 1 FROM sources WHERE id = …`），已存在就跳过、不调 `createSource`（`createSource` 对已存在 ID 是抛 `Conflict`，`admin/sources.ts:205-210`，在部署的 setup 里会让整次部署失败）；`createSource` 返回 `{ created: false, duplicate }` 的（与现有信源同一列表网址，`admin/sources.ts:203-204`）单独计数并打印“与现有信源同址，未建：<ID> → <现有 ID>”，不算失败。人工改过的设置与启停一概不动；重复跑结果相同。
   - 打印：新建几个（按状态分开数）、已存在几个、同址未建几个、没建几个（按原因：没有采集配置、等网页读取服务）。
3. 新脚本 `scripts/policy-sources.ts`（在 worker 容器里跑）：
   - `list`：按国家列出法规信源的 ID、信源表状态、`hold`、启停、健康、最后成功时间。
   - `enable (--country CN | --ids CN-002,CN-004) [--limit N] [--dry-run]`：
     - 不带 `--country` 也不带 `--ids` 一律拒绝；一次超过 10 条拒绝（TASK-0111 上线前）。只动 `lane = 'policy'` 的信源，已启用的打印“已启用”跳过。
     - 只开信源表状态为 `ready` 且 `hold` 为空的条目；其余打印中文原因跳过（`needs_overseas` 要等境外线路，TASK-0053；`needs_reader` 要 Owner 先同意网页读取服务；`hold` 照抄原因）。不接受别的状态参数，开这些类别以后另开卡加开关。
     - 先打印将要启用的清单。对每条当场跑一次 `previewSource`（生产同一采集器、不入库）：取到 ≥1 条才启用（照 `updateSource` 的写法设 `enabled = true`、`next_fetch_at = now()` 并写审计）；取不到或出错就跳过并打印中文原因，不中断整批。预览的条数与前三条样例（标题、日期、链接）写进审计（`action` 用 `source.preview`）。有跳过的，脚本最后返回非零并列出它们。
     - `--dry-run` 只打印清单与预览结果，不改任何行。
4. 测试 `tests/policy-source-seed.test.ts`（合成信源表；试抓用测试里起的本机 HTTP 服务，照 `tests/rss-conditional.test.ts` 的做法，不连外网）：
   - 有配置的 `ready`、`needs_overseas` 条目都建成了法规信源，`lane = 'policy'`、停用、不排期，各有第 1 版许可记录（`owner_declared`、范围是入口主机）；`terms = open` 的九项用途全允许，其余的“公开原文全文”“公开译文”是禁止。`needs_reader` 与没有配置的没有建。
   - 再跑一次：0 新建；先把其中一个人工启用、改名，再跑：不抛错、0 新建，名字与启停原样不动。
   - 同一网址在信源表里出现两次：第二条不建，打印“同址未建”。
   - `enable` 不带 `--country`、`--ids` 被拒绝；一次 11 条被拒绝；`--dry-run` 不改任何行。
   - 预览取到 0 条的信源不被启用，脚本返回非零并列出它；预览取到条目的启用成功，审计里有 `source.preview` 与 `source.update` 两条；`hold` 不为空、状态不是 `ready` 的不被启用；资讯信源不受影响。
   - 现有的 `tests/source-seeds.test.ts` 照旧通过（资讯信源的初始化不变）；`scripts/verify/tests/production-scripts.test.ts` 照旧通过（新脚本在正式镜像里能跑）。
