## 背景（为什么做）

结论：TASK-0092 把 Owner 的信源表放进了行业包，TASK-0093 让信源分了业务线；这张卡把信源表里有采集配置的条目建成真正的法规线信源，部署以后就能按批启用、开始采集。

照上游的做法：`scripts/seed.ts` 从行业包读信源，新的一律停用、不排期，已存在的不覆盖（`scripts/seed.ts:1-3`、:29-42）。但它不建许可记录，按它建出来的信源一采集就报“Source date permission missing”（`packages/backend/src/sources/collect.ts:148-149`）；后台建信源用的 `createSource` 会同时写负责人声明的许可（`packages/backend/src/admin/sources.ts:198-244`，DEC-33）。所以法规信源改走 `createSource`，再加一个只给脚本用的 `lane` 参数。

## 交付内容（做什么）

1. `admin/sources.ts`：`createSource(input, actor, opts?: { lane?: "news" | "policy" })`，默认 `news`，插入时写 `lane`。后台“新建信源”的接口与页面不变（仍是资讯线）。
2. `scripts/seed.ts` 加 `seedPolicySources(entries)`，在现有的 `seedSources` 之后跑：
   - 只取信源表里 `collect` 不为空的条目；`reference_only`、`identity_pending` 本来就没有 `collect`，不建。
   - 信源 ID：`policy-` 加信源表编号的小写，例如 `CN-004` → `policy-cn-004`；名称：机关中文名 · 信源中文名。
   - 照信源表写 `kind`、`config`；采集间隔 360 分钟；`tier = 'T1'`（官方一手）；`site_fulltext = true`，`syndicate_fulltext = false`（Owner 声明全部获许，DEC-33；全文 RSS 照上游默认关）。
   - 许可范围：入口网址的主机名，路径前缀 `/`；信源表若写了文书所在的其他主机（例如附件在另一个子域名），一并列入；`attachments_in_scope = true`。
   - 新建的停用、`health = 'paused'`、不排期；已存在的 ID 跳过（打印“已存在”），人工改过的设置与启停一概不动；重复跑结果相同。
   - 打印：新建几个（按状态分开数）、已存在几个、跳过几个（没有采集配置）。
3. 新脚本 `scripts/policy-sources.ts`：
   - `list`：按国家列出法规信源的 ID、状态（信源表）、启停、健康、最后成功时间。
   - `enable --status ready [--country CN ...] [--dry-run]`：把信源表里状态为指定值的法规信源启用（照 `updateSource` 的写法设 `enabled = true`、`next_fetch_at = now()` 并写审计），先打印将要启用的清单；`--dry-run` 只打印。只动 `lane = 'policy'` 的信源。
4. 测试 `tests/policy-source-seed.test.ts`（合成信源表，不连外网）：
   - 有配置的条目都建成了法规信源，`lane = 'policy'`、停用、不排期，各有第 1 版许可记录（九项用途全允许、`owner_declared`、范围是入口主机）。
   - 再跑一次：0 新建；先把其中一个人工启用、改名，再跑：设置原样不动。
   - 没有 `collect` 的条目没有建。
   - `enable --dry-run` 不改任何行；`enable --status ready` 只启用状态为 ready 的法规信源，资讯信源不受影响，每个启用都有审计记录。
   - 现有的 `tests/source-seeds.test.ts` 照旧通过（资讯信源的初始化不变）。
