## 背景

Owner 2026-10-03 在项目对话里听完“交接包为什么不用 Actions”的说明后说（语音转写原文；由 TASK-0014 的 README PR 登记为 08-owner-voice DEC-25 ③ 与 `08-open-questions.md` 表四“Q-13 追加”，本卡不重复登记；那次登记已随 PR #12 合并进 main）：

- 「当然我是站在产品经理的角度来说的我只是那那就用唄那就用呗公开仓库的actions是免费的我这是公开仓库那你就开着呗那就不动呗因为我这是开源项目」
- 「你要记住就是我们的交接包也说了呃以AIhot的他的这个那个框架就是他的技术设计框架为优先因为他在它的基础上完善我们不是也有那种对吧我是产品经理我是站的产品我只关注最后这个结果能不能做到我想要的这些就是交接包的内容交接包说的这些功能能不能做到」

DEC-25 ③ 把“检查怎样接到 Actions 上，以及裁决表 DEC-17、ADR-0017、M0 退出条件③中 Actions 一项与 `make verify` 的工作流守卫怎么改”交给修订 ADR-0017 的任务，就是本卡。

原来的决定来自 Owner 2026-09-26 的「GitHub Actions 如果不是必须，以后不用」（旧ADR-0038 → ADR-0017）。起因是旧项目私有仓库的 Actions 额度耗尽，绑在 Actions 上的必过检查让任何 PR 都合并不了（PIT-055、GOV-21）。现在的情况不同：

- 新仓库是公开仓库（2026-10-03 经 GitHub API 读到 `visibility: public`），GitHub 托管的 runner 对公开仓库不计费。裁决表 DEC-28 与 DEC-64 ⑤、Q-17、路线图、启动手册与规则文件原按“私有”写；DEC-25 ③ 注明了 DEC-64 ⑤ 一处。本卡只给裁定或要求可见性的条目加注（交付内容第 5 条“仓库可见性”列出的各处）；其余复述 DEC-64 ⑤ 的地方（多数不在本卡 `allowed_paths` 里）与仓库公开后许可怎样声明，列入“未完成项”另行处理。
- 代码起点本身就在 Actions 上跑同样的检查（`scripts/verify/upstream-check.yml`，`make verify` 由它逐步翻译而来）。
- ADR-0017 的“推翻条件”已经写好：Owner 以后重新启用某托管 CI，它只作为第 3 条里的“一个执行者”，其余条款不变。
- 平台设置里的 Actions 一直没有停用：建仓时开发会话没有仓库设置权限，做法是仓库里不放工作流文件、由 `toolchain` 阶段拦截（TASK-0001、TASK-0002 的“停用并读回”因此一直未勾）。

本卡就按推翻条件落地，三句话：

1. **同一个入口**：Actions 跑的是 `make verify`，同一套阶段、同一份回执，没有另写的检查。
2. **不多一道门**：分支保护仍是 8.5 的 A 阶段，不设“必须通过检查”，免得再碰上 PIT-055 的死锁。合并仍由集成人核对 PR 最终提交的回执。Actions 不可用时怎么办，见下面的“退路”。
3. **不碰发布与生产**：不构建发布镜像，不部署，不跑定时任务；采集、加工、发布不依赖 GitHub（ADR-0017 第 5、8、10 条，INV-29）。

顺带补上一个缺口。到现在为止的回执都是 `scope: focused`：本项目云端容器的网络策略拒绝 `deb.debian.org`，构建容器里也过不了 npm 源的 TLS 代理（T-0001 验收记录第五节），`compose-smoke`（把整站装进容器跑一遍）跑不了。T-0001 验收记录要求 M0 结束前在能联网的执行器上补跑。GitHub 的 runner 有 Docker 和外网，本卡之后，Actions 可用时每个 PR 都能有 `scope: full` 的回执。`compose-smoke` 从来没有真正跑过（pnpm 12 在镜像里装依赖也没验证过），首次实跑暴露的问题在本卡做最小修复。

### 退路：Actions 不可用时

本卡之后，能出 `scope: full` 回执的执行器只有 Actions：云端容器跑不了 `compose-smoke`，规则文件 8.4 与 Q-65 设想的开发机隔离虚拟机现在没有。ADR-0017 第 3 条的“执行器不可用时换执行器”眼下没有第二个可换，所以写明：

- **M0 期间**：沿用 08-owner-voice DEC-24 ② 已经在用的做法。云端容器的 focused 回执通过、独立审查没有阻断项，就可以合并，合并后在项目对话里说一声；PR 评论写明缺 `compose-smoke`、原因是 Actions 不可用。Actions 恢复后，在 main 的头上手动触发一次工作流，补出 `scope: full` 的回执，记进 T-0001 验收记录。期限同 T-0001 验收记录第六节：M0 退出前。
- **M0 之后**：没有这个例外。Actions 不可用就等它恢复，focused 回执照旧不用于合并（规则文件 8.3）。要不要再备一个不依赖 GitHub、能跑 `compose-smoke` 的执行器（例如租用的临时机器，属规则文件 14.2 的采购），由集成人在 M0 退出前写 Q 卡片请 Owner 定：卡片写明推荐做法（依据 ANTI-20“不把 Actions 当作验证的前提”）和不回复时的默认做法（不采购，Actions 不可用就等它恢复）；列入本卡“未完成项”。
- **仓库改成私有**：作业只在公开仓库上跑（交付内容第 1 条），改成私有后不跑、不计费，按 Actions 不可用处理，直到 Owner 重新确认（交付内容第 5 条 ADR-0017 的更新）。

## 交付内容

分两个实施 PR，按顺序开：一是工作流、守卫与说明（第 1–4 条），二是规格写回与登记（第 5 条）。工作流随实施 PR 一加入，该 PR 自己的提交就会在 Actions 上运行（完成条件第 1 项）；合并后 main 上那次推送的运行，第一次拿到 `main-<sha12>` 回执。

1. **工作流 `.github/workflows/verify.yml`**，写法参照 `scripts/verify/upstream-check.yml`：
   - **名字**：工作流叫 `make verify (GitHub Actions)`，作业叫 `make-verify`。不叫 `verify`，免得日后与 8.5 B 阶段由 App 发布的 `verify` 检查同名（规则文件 8.5：禁止同名 status 冒充）。
   - **触发**：`pull_request`，`types` 写明 opened、synchronize、reopened、edited（卡号取自 PR 描述，改了描述要重跑）；推送到 `main`；手动 `workflow_dispatch`，带一个可选输入 `task`。
   - **并发**：PR 的运行按 PR 分组，有新运行时取消旧的；推送 `main` 的运行按提交分组（组名带提交 SHA），不取消也不被替换。同一并发组里排队的运行会被更新的排队运行替换，按分支分组的话，连续合并时中间那次就拿不到自己的 `main-<sha12>` 回执（规则文件 6.4 第 4 条）。
   - **只在公开仓库上跑**：作业条件写 `github.event.repository.visibility == 'public'`。仓库改成私有，作业直接跳过，不消耗额度，这是 Owner 授权的前提（DEC-25 ③）。首次运行即核实这个字段：字段缺失时比较结果为假、作业跳过，运行记录里一眼可见（不用 `private == false`：表达式按数字比较，字段缺失时 null 与 false 相等，作业反而照跑）。
   - **权限**：工作流级只有 `contents: read`，作业不另设；不用任何密钥；检出时 `persist-credentials: false`。
   - **action**：只用 `actions/checkout` 与 `actions/setup-node` 两个，按完整提交 SHA 锁定，版本与上游工作流相同；不用任何缓存（`package-manager-cache: false`）。
   - **环境**：运行器 `ubuntu-24.04`，Node 24。pnpm 照 `Dockerfile` 的装法，用 `npm install -g pnpm@<packageManager 的版本>`，不依赖 corepack。PostgreSQL 不写在工作流里：一步运行新脚本 `scripts/verify/ci-db.ts`，它从 `docker-compose.yml` 读出 `db` 服务那个按摘要锁定的镜像，用 `docker run` 起在 `127.0.0.1:5432`（信任认证、不设口令、库名 `amp_ci`），等到就绪。镜像只写在 compose 一处：换数据库镜像的卡（如 TASK-0006）只改 compose，Actions 跟着变，不用改工作流，也不碰集成人专属的 `.github/**`。`migrations` 阶段和回执用运行器自带的 `psql` 客户端，版本可能与服务端不同，首次运行时核实并写进 README。
   - **检出的提交**：PR 的最终提交（不是 GitHub 合成的合并提交），完整历史，用来与 main 比较。这个 SHA 经环境变量传给 `make verify SHA=…`，检出错了 `run.ts` 直接拒绝运行；回执绑定的就是它。
   - **任务卡号**：由新脚本 `scripts/verify/pr-task.ts` 从事件文件读出，不经 `${{ }}` 插进脚本。PR 取描述里“任务卡”那一行的第一个 `TASK-nnnn`；手动触发取输入 `task`；推送到 `main` 不需要。取不到时不设，`path-guard` 照常报“没有任务卡”。
   - **计划 PR**：计划 PR 只改 `tasks/` 下的任务卡（规则文件 3.3：“先合并一个只改任务卡的计划 PR”），它新增的卡不在 base 上，`path-guard` 原来必然失败（`path-guard.ts:107-108`；#11、#13 是在云端容器上手工跑 `TASK=TASK-0002` 才通过的；改已有卡的计划 PR，如 #10，本来就能用自己的卡号通过）。`path-guard` 加一条规则：点名的卡不在 base 上、本 PR 新增了这张卡、改动全在 `tasks/` 下，就按计划 PR 通过；改动超出 `tasks/` 仍然失败。PR 描述的“任务卡”一行照常写本 PR 新增的卡。
   - **运行**：执行器编号 `github-actions`，跑 `make verify`。回执全文写进日志和运行摘要；集成人照旧把它贴到 PR 评论。
2. **`toolchain` 阶段**：原规则是“`.github/workflows` 下不许有文件”，改为“只许有 `verify.yml` 这一个，且符合上面的形状”。逐条检查：
   1. `.github/workflows/` 下只有 `verify.yml`；
   2. 触发只限三种：`pull_request` 的 `types` 只许上面四种，推送只限 `main`，另有 `workflow_dispatch`；拒绝 `pull_request_target`、`schedule`、`workflow_run` 等其他触发；
   3. 推送 `main` 的运行不得被取消或替换：取消旧运行只限 `pull_request`，推送的并发组带提交 SHA；
   4. 工作流级权限只有 `contents: read`，作业不得另设权限；
   5. 步骤的 `uses` 只许 `actions/checkout@<40 位 SHA>` 与 `actions/setup-node@<40 位 SHA>`，作业不得 `uses` 可复用工作流；
   6. `actions/checkout` 必须设 `persist-credentials: false`；
   7. 不得引用 `secrets` 或 `github.token`；
   8. `run` 里不得出现 `${{`，值一律经环境变量传入；
   9. 不得 `continue-on-error`、部署环境；
   10. 每个作业设超时，运行器是带版本号的 GitHub 托管 Ubuntu；
   11. 每个作业带 `github.event.repository.visibility == 'public'` 条件；
   12. 作业不设 `services` 与 `container`；数据库由一步运行 `scripts/verify/ci-db.ts` 启动，镜像取自 `docker-compose.yml`（compose 镜像的锁定由 `toolchain` 原有检查核对）；
   13. 有一步运行 `make verify`。

   **文件不存在也通过**：检查只断言“存在就必须是这个形状”，不断言工作流存在（规则文件 8.1，旧 `REQUIRED_PATHS` 教训）。
3. **故意违规用例**：每条规则至少一例。
   - `scripts/verify/tests/toolchain.test.ts`，27 例各被拦一次：多一个工作流文件；`pull_request_target`；定时触发；`pull_request` 多了 `labeled` 类型；推送 `main` 以外的分支；推送 `main` 的运行可被取消；推送 `main` 的并发组不带提交 SHA；写权限；作业另设权限；白名单外的 GitHub action（如 `actions/cache`）；第三方 action；按标签引用；作业调用可复用工作流；检出没设 `persist-credentials: false`；引用密钥；转交令牌；`run` 里插入 `${{ … }}`；`continue-on-error`；部署环境；没有超时；自托管 runner；`ubuntu-latest`；没有公开仓库条件；作业声明 `services`；作业设 `container`；没有运行 `ci-db.ts` 的一步；没有 `make verify`。
