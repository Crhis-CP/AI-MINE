## 背景

Owner 2026-10-03 在项目对话里听完“交接包为什么不用 Actions”的说明后说（语音转写原文；由 TASK-0014 的 README PR 登记为 08-owner-voice DEC-25 ③ 与 `08-open-questions.md` 表四“Q-13 追加”，本卡不重复登记；本卡的实施 PR 等那次登记合并后再开）：

- 「当然我是站在产品经理的角度来说的我只是那那就用唄那就用呗公开仓库的actions是免费的我这是公开仓库那你就开着呗那就不动呗因为我这是开源项目」
- 「你要记住就是我们的交接包也说了呃以AIhot的他的这个那个框架就是他的技术设计框架为优先因为他在它的基础上完善我们不是也有那种对吧我是产品经理我是站的产品我只关注最后这个结果能不能做到我想要的这些就是交接包的内容交接包说的这些功能能不能做到」

DEC-25 ③ 把“检查怎样接到 Actions 上，以及裁决表 DEC-17、ADR-0017、M0 退出条件③中 Actions 一项与 `make verify` 的工作流守卫怎么改”交给修订 ADR-0017 的任务，就是本卡。

原来的决定来自 Owner 2026-09-26 的「GitHub Actions 如果不是必须，以后不用」（旧ADR-0038 → ADR-0017）。起因是旧项目私有仓库的 Actions 额度耗尽，绑在 Actions 上的必过检查让任何 PR 都合并不了（PIT-055、GOV-21）。现在的情况不同：

- 新仓库是公开仓库（2026-10-03 经 GitHub API 读到 `visibility: public`；路线图与启动手册原按“私有”写，DEC-25 ③ 已注明），GitHub 托管的 runner 对公开仓库不计费。
- 代码起点本身就在 Actions 上跑同样的检查（`scripts/verify/upstream-check.yml`，`make verify` 由它逐步翻译而来）。
- ADR-0017 的“推翻条件”已经写好：Owner 以后重新启用某托管 CI，它只作为第 3 条里的“一个执行者”，其余条款不变。
- 平台设置里的 Actions 一直没有停用：建仓时开发会话没有仓库设置权限，做法是仓库里不放工作流文件、由 `toolchain` 阶段拦截（TASK-0001、TASK-0002 的“停用并读回”因此一直未勾）。

本卡就按推翻条件落地，三句话：

1. **同一个入口**：Actions 跑的是 `make verify`，同一套阶段、同一份回执，没有另写的检查。
2. **不多一道门**：分支保护仍是 8.5 的 A 阶段，不设“必须通过检查”，免得再碰上 PIT-055 的死锁。合并仍由集成人核对 PR 最终提交的回执；Actions 不可用时换执行器跑同样的检查，不跳过。
3. **不碰发布与生产**：不构建发布镜像，不部署，不跑定时任务；采集、加工、发布不依赖 GitHub（ADR-0017 第 5、8、10 条，INV-29）。

顺带补上一个缺口。到现在为止的回执都是 `scope: focused`：本项目的云端容器网络策略拒绝 `deb.debian.org` 与 Docker Hub，`compose-smoke`（把整站装进容器跑一遍）跑不了。T-0001 验收记录要求 M0 结束前在能联网的执行器上补跑。GitHub 的 runner 有 Docker 和外网，本卡之后每个 PR 都能有 `scope: full` 的回执。`compose-smoke` 从来没有真正跑过（pnpm 12 在镜像里装依赖也没验证过），首次实跑暴露的问题在本卡做最小修复。

## 交付内容

1. **工作流 `.github/workflows/verify.yml`**，写法参照 `scripts/verify/upstream-check.yml`：
   - **触发**：`pull_request`、推送到 `main`、手动 `workflow_dispatch`。同一 PR 有新推送时取消旧运行；超时 45 分钟。
   - **权限**：只有 `contents: read`。不用任何密钥；检出时 `persist-credentials: false`。
   - **action**：只用 GitHub 自有的 `actions/checkout` 与 `actions/setup-node`，按完整提交 SHA 锁定，版本与上游工作流相同。
   - **环境**：运行器 `ubuntu-24.04`，Node 24，pnpm 按 `package.json` 的 `packageManager` 安装。PostgreSQL 用 `docker-compose.yml` 里同一个按摘要锁定的镜像作服务容器，信任认证、不设口令，库名 `amp_ci`。
   - **检出的提交**：PR 的最终提交（不是 GitHub 合成的合并提交），回执绑定的就是它；完整历史，用来与 main 比较。
   - **任务卡号**：从 PR 描述里“任务卡”那一行取第一个 `TASK-nnnn`。经事件文件读取，不经 `${{ }}` 插进脚本。取不到时不设，`path-guard` 照常报“没有任务卡”。推送到 main 时不需要。
   - **运行**：执行器编号 `github-actions`，跑 `make verify`。回执全文写进日志和运行摘要；集成人照旧把它贴到 PR 评论。
2. **`toolchain` 阶段**：原规则是“`.github/workflows` 下不许有文件”，改为“只许有 `verify.yml` 这一个，且符合上面的形状”。逐条检查：
   - 触发只限上面三种，推送只限 `main`；拒绝 `pull_request_target`、`schedule`、`workflow_run` 等；
   - 权限只有 `contents: read`，作业不得另设；
   - `uses` 只许 `actions/<名字>@<40 位 SHA>`，作业不得调用可复用工作流；
   - 不得引用 `secrets` 或 `github.token`；
   - `run` 里不得出现 `${{`，值一律经环境变量传入；
   - 不得 `continue-on-error`、部署环境；每个作业设超时，运行器是带版本号的 GitHub 托管 Ubuntu；
   - 服务与容器镜像按补丁版本加 sha256 锁定；
   - 有一步运行 `make verify`。

   **文件不存在也通过**：检查只断言“存在就必须是这个形状”，不断言工作流存在（规则文件 8.1，旧 `REQUIRED_PATHS` 教训）。
3. **故意违规用例**（`scripts/verify/tests/toolchain.test.ts`）：多一个工作流文件、`pull_request_target`、定时触发、推送任意分支、写权限、引用密钥、转交令牌、第三方 action、按标签引用、`run` 里插入 `${{ … }}`、`continue-on-error`、作业另设权限、部署环境、没有超时、自托管 runner、`ubuntu-latest`、服务镜像没锁摘要、没有 `make verify`，各被拦一次；仓库里的那份工作流通过；没有工作流时通过。
4. **说明**：
   - `scripts/verify/README.md` 加一节“在 GitHub Actions 上跑”；
   - `Makefile` 与 `scripts/verify/run.ts` 开头“不涉及托管 CI”的说明，改为“托管 CI 只是执行者之一”。
5. **规格写回**：每处只改涉及 Actions 的句子，都引用 08-owner-voice DEC-25 ③。
   - **ADR-0017**：状态行下加一条 2026-10-03 更新：Owner 重新启用 GitHub Actions，按“推翻条件”只作为第 3 条的一个执行者；第 9 条“启用 GitHub Actions”的授权只及于这一个工作流。

## 明确不做

- 不把 Actions 的运行设为分支保护的必过检查，不注册检查发布 App（8.5 的 B 阶段须 Owner 另行授权）。
- 不用 Actions 构建、签名或推送发布镜像，不部署，不跑定时任务。`make release-check` 与部署链归 TASK-0009 与 ADR-0017 第 5–8 条。
- 不改 `make verify` 的阶段与回执格式，不加第三方 action。
- 不改仓库设置。Actions 保持启用是 Owner 的意思，也是现状；可选的加固设置（只允许 GitHub 自有的 action、外部贡献者的 PR 先批准再跑）写进交付记录，由 Owner 决定点不点。
- 不改 `01-vision-and-positioning.md` 第 5 条与 ANTI-20：“不把 Actions 当作验证、构建、上线的前提”照旧成立。
- 不改写旧仓库的历史事实（旧仓库 Actions 于 2026-09-26 停用：08-owner-voice DEC-18、`08-open-questions.md` :149、`07-deployment-and-ops.md` :417、`01-vision-and-positioning.md` :168）。
