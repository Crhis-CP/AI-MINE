## 背景（为什么做）

日常清理（`packages/backend/src/operations/retention.ts`，每天 03:30）只清租约、运行历史、过期文件和缓存。`fetch_runs` 每天约一万多行（473 个来源），`story_heat_hourly` 随事件数乘小时数增长，两张表都从不清理。

审计方核对过所有读取方，采集记录的读取范围如下：

| 读取方 | 读取范围 |
|---|---|
| `acquisition/operational-snapshot.ts:6` | 24 小时 |
| `acquisition/target-evidence.ts:9` | 7 天计数，加上“最近一次成功” |
| `acquisition/source-health.ts:8-10` | 来源上次修改之后的最近一次 |
| `admin/sources.ts:75` | 每个来源最近 30 次 |
| `acquisition/directory-read.ts:27-39` | 调用方给定的时间段 |

热度小时表只在 `events/participation-read.ts:130` 按最近 1 天或 7 天读取（调用方 `publication/stories.ts:367`、`:414`），另外 `events/hot.ts:258-260` 修复热榜窗口内的未完成小时。

## 交付内容（做什么）

1. **两张汇总表**（迁移按仓库惯例写，登记到 `database/migration-inventory.json`，并在 `table-grants.json`、`data-ownership-map.json` 里登记归属）：
   - `database/migrations/acquisition/202611131100_fetch_run_daily.sql` 建 `acquisition.fetch_run_daily`：
     - 主键 `(source_id, day)`，`source_id text NOT NULL REFERENCES sources(id) ON DELETE CASCADE`；
     - `day date NOT NULL` 是北京时间的日期；
     - 计数列 `runs`、`ok`、`failed`、`skipped` 都是 `integer NOT NULL DEFAULT 0`；
     - 合计列 `found_sum`、`new_sum` 都是 `bigint NOT NULL DEFAULT 0`；
     - 时间列 `first_started_at`、`last_finished_at` 都是 `timestamptz`。

     归属模块 `acquisition`。
   - `database/migrations/events/202611131110_story_heat_daily.sql` 建 `events.story_heat_daily`：
     - 主键 `(story_id, day)`，`story_id bigint NOT NULL REFERENCES stories(id) ON DELETE CASCADE`；
     - `day date NOT NULL` 是北京时间的日期；
     - `max_heat`、`avg_heat` 都是 `numeric(10,3) NOT NULL`；
     - `max_participants`、`hours` 都是 `integer NOT NULL`。

     归属模块 `events`。
2. **采集记录清理**，写在 `packages/backend/src/acquisition/fetch-run-retention.ts`（删表的 SQL 必须放在归属模块的目录里），导出 `pruneFetchRuns(now: Date, budgetMs: number)`：
   - 可以删的行：`started_at < now - 90 天`、`status <> 'running'`，并且**不属于下面两类**：
     - 该来源按 `started_at DESC, id DESC` 排的最新 30 行；
     - 该来源最新的一行 `status = 'ok'`。
   - 每批最多 5000 行。删除和汇总放在同一个事务、同一条语句里（`WITH gone AS (DELETE … RETURNING …) INSERT INTO acquisition.fetch_run_daily … SELECT … FROM gone GROUP BY source_id, (started_at AT TIME ZONE 'Asia/Shanghai')::date ON CONFLICT (source_id, day) DO UPDATE SET` 各计数和合计相加、`first_started_at` 取较小值、`last_finished_at` 取较大值）。这样重跑不会重复计数。
   - 循环到删完，或用时超过 `budgetMs` 为止，返回删除的行数。
3. **热度小时表清理**，写在 `packages/backend/src/events/heat-retention.ts`，导出 `pruneHeatHours(now: Date, budgetMs: number)`：
   - 删除 `hour < now - 90 天` 的行，每批 5000 行，写法同上。
   - 只有 `complete = true` 的行进汇总：`max_heat`、`avg_heat`、`max_participants`、`hours` 都在冲突更新时正确合并，平均值按“已有小时数加本批小时数”加权。未完成的旧行直接删除。
4. `retention.ts` 的 `dailyRetention()` 调用这两个函数，各给 5 分钟预算。返回值加上 `prunedFetchRuns`、`prunedHeatHours` 两个计数。第一次上线时历史数据多，会分几天删完，这是预期行为。
5. **台账**：在 `docs/00-decision-ledger.md` 的 DEC-78 一节、最后一条“DEC-78补充”之后加一条：

   > **DEC-78补充·数据保留期（Owner 2026-11-13）**：Owner 同意审计方建议：采集记录（`fetch_runs`）和事件热度小时表（`story_heat_hourly`）保留 90 天，更早的按北京时间逐日汇总（`acquisition.fetch_run_daily`、`events.story_heat_daily`）后删除；每个来源最新 30 次采集和最近一次成功采集始终保留。付费回执的响应正文保留 12 个月，最早一批数据约 2027 年秋满期，届时另开卡，过期正文的回执按“不可复用”处理，不得算作结果未知、不得触发重新付费或人工核对。分析结果、归组决定和向量暂不删除。由 TASK-0704 实现第一步。

6. **测试** `tests/retention.test.ts`：
   - 造 3 个来源、每个 200 天里每天 2 次采集（其中 1 个来源 100 天前起全部失败）。清理后：每个来源最新 30 行都还在；那个全失败来源的最后一次成功仍在；其余 90 天前的行都被删掉；汇总表的各项合计等于被删的行。
   - 清理函数连续跑两次，汇总不重复。
   - 热度：200 天的小时数据，清理后只剩 90 天内的；汇总的最大值、平均值、小时数正确。
   - `admin/sources.ts`、`target-evidence.ts` 的读取结果与清理前一致。

代码量预算：迁移两份，各约 15 行；实现约 90 行；测试约 120 行。
