## 背景（为什么做）

资讯正文的 PDF 已经走有界子线程：`packages/backend/src/content/pdf-text.ts` 一次只解析一份，15 秒超时，128MB 堆上限，用完就结束子线程。法规和金属的 PDF 却直接在 worker 主线程里跑 pdfjs，没有超时：

- `modules/policy/backend/domain/extraction.ts:72-101`（`getTextContent`）
- `modules/policy/backend/domain/vision-render.ts:51-87`（`getOperatorList`、`render`）
- `modules/metals/backend/cochilco.ts:19-33`

四处 `getDocument` 都没设 `isEvalSupported: false` 和 `maxImageSize`（`pdf-text-worker.ts:11` 也没设）。来源配置的 `maxBytes`、`maxPages` 在 `automation-profile.ts:32-35` 里没有上限。一份精心构造的 PDF（压缩炸弹、超大图片、深层嵌套）就能卡住或撑爆整个 worker，任务重试时还会再来一遍。

## 交付内容（做什么）

1. 四处 `getDocument({...})` 都加上 `isEvalSupported: false, maxImageSize: 25_000_000`。
2. 法规和金属的**文字提取**改走子线程：
   - 把 `pdf-text.ts` 的子线程读取抽成可传参数的版本，例如 `readPdfTextBounded(bytes, { bytes, pages, timeoutMs })`；现有 `readPdfText` 用它实现，行为不变。
   - `extraction.ts` 和 `cochilco.ts` 改为调用它。上限取各自来源配置的 `maxBytes`、`maxPages`，再与第 4 条的上限取较小值；超时 30 秒。
   - 如果这两处需要逐页的结构（不只是整段文字），就让子线程返回 `string[]`（每页一段），并在 PR 写明。
3. `vision-render.ts`：整个渲染过程包一层总时限，60 秒到点就中止，丢弃这份文件的渲染结果，走现有的失败分支；渲染页数上限取 `min(maxPages, 50)`。
4. `automation-profile.ts:32-35` 的 zod 加上限：`maxBytes` ≤ 20MB，`maxPages` ≤ 500，`maxResources` ≤ 50，`maxTextBytes` ≤ 5MB。现有配置都在上限内；如果有超出的，停止并报告。
5. 测试（`tests/pdf-text.test.ts`）：带参数版本的上限生效；子线程超时会被结束并给出“读取超时”；`isEvalSupported` 为 false（可以断言传给 `getDocument` 的参数）。

代码量预算：实现约 80 行；测试约 50 行。
