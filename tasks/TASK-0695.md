## 背景（为什么做）

`.github/workflows/verify.yml:58-75`：每次运行（包括 PR、来自 fork 的 PR、手动触发）都会打包并上传完整的可发布镜像（`verified-release-<sha>`）。发布时 `deploy/release_artifact.py` 只核对哈希与清单一致（文件第 2 行写明“哈希绑定字节，不是签名”），不核对这个提交是不是在 main 上、运行是不是 main 的推送。发布手册说生产只用 main 的制品（`docs/runbooks/release-retention.md:7`），但没有任何检查保证这一点。

## 交付内容（做什么）

1. `verify.yml`：“Export the image…”和“Verified release files”两步加条件
   `if: github.event_name == 'push' && github.ref == 'refs/heads/main'`。PR 运行仍然跑完整的 `make verify` 和回执，只是不再产出可发布制品。
2. `scripts/verify/run.ts`：回执加两个字段 `github_event` 和 `github_ref`，取自环境变量 `GITHUB_EVENT_NAME`、`GITHUB_REF`；本机执行器没有这两个变量时写 `null`。
3. `deploy/release_artifact.py` 的回执校验：回执的执行器是 `github-actions` 时，要求 `github_event == "push"` 且 `github_ref == "refs/heads/main"`，否则拒绝，报错写明原因。其他执行器的回执保持现有规则。
4. 测试：
   - PR 事件的云端回执被拒；
   - main 推送的回执通过；
   - 本机执行器的回执不受影响；
   - 缺这两个字段的旧回执：执行器是 `github-actions` 就拒绝，并在报错里提示用新回执。
5. 发布手册补一句：生产只接受 main 推送产出的云端制品；本机执行器的回执规则不变。

代码量预算：工作流 2 行；`run.ts` 约 5 行；校验约 15 行；测试约 40 行。
