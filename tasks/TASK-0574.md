Owner 2026-11-07：“我本身有555个信源，但是现在信源很多都接入不好，优化这个问题。”Codex 审计（Issue #353）：启用资讯源 429 个，近 7 天成功抓取 418 个；等待记录中 robots_unavailable 19,211 次 / 43 个源、host_pacing 8,509 / 423、transport_unavailable 4,206 / 207；失败中 HTTP 错误 132 / 21、HTML 列表 0 匹配 98 / 5、验证页 92 / 5、JSON 路径 12 / 3、robots 跳转未获准 28 / 1；每天约六成发现条目以 visibility 'withdrawn' 结束，原因没有记录。

## 背景（为什么做）

- **robots**：只有 200 非 HTML 或 404 算可用；401/403/410/412、其他 4xx、5xx、HTML 软 404、网络错误一律“暂不可取得”，每 5 分钟重来一次、永不计失败；失败写进同一行，覆盖了上次成功的副本；跳转只允许同主机 2 跳。与 RFC 9309 §2.3.1 不符：4xx 应视为“不可用”（全部允许），5xx 才是“不可达”。
- **连接**：响应前的任何异常都固定 60 秒后重试并冷却主机，不记原因；域名不存在、证书无效这类等不好的故障也无限等待；采集入口把各读取器要求的一次断连重试强制关掉；超时固定 20 秒。
- **主机间隔**：哪怕只需等 2 秒也整轮退回队列，重新排队、重开会话。
- **Accept**：各读取器的 Accept 不一致（JSON 读取声称也要 HTML，robots 没有声明）。
- **不公开原因**：`publishArticleTx` 在七种自动条件下把资讯设为 withdrawn，但不记是哪一种。

## 交付内容（做什么）

- **robots（RFC 9309）**：2xx 解析；HTML 页面或没有任何规则行的文本按空文件允许并记 warning（`robots_html` / `robots_unrecognized`）；4xx 全部允许，缓存 24 小时并记 `robots_http_<码>`；5xx、429、网络失败沿用 30 天内的成功副本（仍遵守其中 Disallow 与 Crawl-delay），没有副本则延后，退避 5 分钟→15 分钟→1 小时→6 小时；失败另存于 `failure_since / failure_count / failure_reason`，不覆盖副本；跳转最多 5 次、可跨主机，记 `final_url`。验证页（包括 robots.txt 上的）仍阻止，不绕过。30 天后不自动放行，来源健康新增“robots 长期无法读取”交人工逐源决定，另有“robots.txt 读取异常”（失败满 1 天、仍在副本期内）的提示，文案如“robots.txt 返回 503 已 3 天，沿用 03-06 的副本（连续 4 次）”。
- **连接原因**：按错误链归类（dns_not_found、dns_temporary、certificate_invalid、tls_handshake、timeout、connection_reset、connection_refused、network_unreachable、address_blocked、proxy_error、other），存进采集记录 `detail.cause`；域名不存在、证书无效、非公网地址直接记失败采集（进入失败计数与退避）；其余按主机连续失败退避 1、2、4……最多 30 分钟，收到任何 HTTP 响应清零；GET 恢复一次断连重试，主机租约按两次请求预留；`crawlProfile.timeoutSeconds`（5–60 秒）按来源覆盖超时。
- **连续等待上限**：同一来源连续 5 次因 robots 或连接等待（中间的主机间隔等待不计），第 5 次记失败采集，错误 `deferral_limit <原因> (<细因>): 5 consecutive waits`，健康显示“连续 5 次连不上源站（连接超时）”。
- **主机间隔**：需要等待 ≤5 秒时在进程内等待后重取同一预约（最多 3 轮），更长的仍走队列；每主机同时一个请求不变；robots 读取等待后先复查别的来源是否已存好副本。
- **Accept**：共用常量 `ACCEPT`——HTML `text/html,application/xhtml+xml;q=0.9,*/*;q=0.8`、订阅 `application/rss+xml, application/atom+xml, application/xml;q=0.9, text/xml;q=0.8, */*;q=0.5`、JSON `application/json, */*;q=0.5`、robots `text/plain, */*;q=0.5`；UA 不变。
- **不公开原因**：新表 `publication.withdrawn_reasons`（publication 模块，私有列，迁移/清单/授权/归属已登记），由 `publishArticleTx` 同事务写入：manual、original_post_not_admitted、non_editorial、blocked、no_material、language_unknown、not_ready，公开时删除；运维快照 publication 数据集新增 `withdrawn_7d:<原因>` 计数（近 7 天发现、未记录的为 `unrecorded`）。读者看到的内容不变。
- **跳转换主机**：内容跳到其他主机仍阻止，错误信息附新地址，健康文案提示“如确认是同一来源，可把信源地址改为该网址”。

## 同类问题（举一反三）

- **模式**：采集等待/失败只记笼统原因，或把可恢复与不可恢复的故障混为一种处理；同一请求类型各处写法不一。
- **搜索方式**：`grep -rn "crawlFetch\|guardedFetch(" packages modules` 找全部采集请求；`grep -rn "visibility" packages/backend/src/publication` 找全部写 withdrawn 的路径；`grep -rn "CrawlDeferred(" packages` 找全部等待原因。
- **一起改的**：RSS、JSON 列表、HTML 列表与表单翻页、详情页、正文提取、法规目录页的 Accept；robots、正文、外部读取器（`crawlExternal`）的主机间隔等待；资讯所有自动不公开条件（只有 `publishArticleTx` 写 visibility）。
- **有意不改**：法规原件取得（`modules/policy/backend/domain/capture.ts`）请求的是 PDF/HTML 等不定类型，不加 Accept；HTTP 429/503 仍按 Retry-After 冷却主机、只等待不计失败（源站明确要求慢下来）；内容跳转到其他主机仍阻止（换地址需人工确认许可范围）；“解析失效”问题类型（0 匹配 / JSON 路径错误保存最后响应并接入预览）本卡未做，见未完成项。
