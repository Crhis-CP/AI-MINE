## 背景（为什么做）

结论：正式站上有几个商务部驻外经商处的列表页常被对方直接断开连接，现在的采集碰到这种情况这一轮就算失败，要等下一轮（至少隔两倍的抓取间隔），马上再取一次其实能成功。本卡让同一请求隔几秒再取一次，第二次仍失败才算失败。

1. **正式站的现象**（2026-10-08，Owner Mac 上的会话在服务器上只读查到，项目对话 13:4xZ 已告诉 Owner 这是要排的小修）：印尼、澳大利亚两个驻外经商处的列表页一直失败，秘鲁、赞比亚偶尔失败；原因是对方服务器把连接直接断开，马上再取一次能成功。这几个列表都是 TASK-0030 接入的网页列表（列表 HTML 装在 JSON 里，`htmlJsonPath: "data.html"`）。
2. **现在的代码怎么处理**（照 AIHOT 原样）：`packages/backend/src/lib/http-fetch.ts:62` 的 `guardedFetch` 不重试；失败一路抛到 `sources/collect.ts:259` 的 catch，记这一轮失败，下次运行推到“现在 + 间隔 ×（连续失败次数 + 2）”，最多 360 分钟（`collect.ts:267`）。AIHOT 碰到断开也是这样等下一轮，它没有更细的做法可照搬，所以本卡只在现有的抓取函数上加一个选项，不另建机制。
3. **断开在代码里长什么样**（本机用 undici 7.30.0 试过）：响应前断开是 `TypeError: fetch failed`，cause 是 `SocketError`（code `UND_ERR_SOCKET`，“other side closed”）；读正文时断开是 `TypeError: terminated`，cause 同上；我们自己的超时是 `TimeoutError`，没有 cause。失败原因现在只记 `error.message`（`collect.ts:260`），后台信源页和周一信源周报只看得到“fetch failed”，看不出是断开、超时还是连不上。
4. **规格怎么说**：BR-ACQ-07（`docs/01-product/07-sources-and-coverage.md:933`）只写了失败后推迟下次运行；BR-ACQ-14 要求不换 UA、不绕过验证页。同一请求原样再取一次不换 UA、不绕过什么，和它不冲突。数值只在 BR-OPS-03 参数表里定义（`docs/02-rules/01-business-rules.md:756` 起），本卡在表里加一行。

## 交付内容（做什么）

1. **抓取函数加一个选项**（`packages/backend/src/lib/http-fetch.ts`）：
   - `GuardedFetchOptions` 加 `retryDropped?: boolean`（默认不重试），注释写明：只限 GET；对方把已建立的连接断开时，隔一会儿把同一请求再发一次，第二次另给一份完整的时间预算；超时、连不上、HTTP 错误码都不重试。
   - 导出 `DROPPED_RETRY = { afterMs: 3000 }`：等待时间取 `afterMs` 到 `2 × afterMs` 之间的随机值（3 到 6 秒，几个同时被断开的来源错开再取）。测试里改小。
   - 导出 `droppedConnection(error)`：沿 `error.cause` 往下找最多 4 层，code 是 `UND_ERR_SOCKET`、`ECONNRESET` 或 `EPIPE` 时为真；`TimeoutError`、`AbortError` 一律为假。
   - 原来 `guardedFetch` 的函数体原样改名为 `fetchOnce`（不导出）；新的 `guardedFetch` 调 `fetchOnce`，出错时满足“选项打开、方法是 GET、`droppedConnection` 为真”三条才等一会儿再调一次 `fetchOnce`（地址检查、跳转与大小上限照旧每次都走），第二次的错误原样抛出。:63 的注释“一个预算包括 DNS、每次跳转和正文”后面补一句：重试的那一次另算一份预算，只有 worker 里的采集打开这个选项。
2. **采集的四处调用打开选项**：`rss.ts:140`、`:143`，`web-list.ts:239`（列表页）、`:361`（详情页），`json-list.ts:151`（配置成 POST 的列表照旧不重试，由 guardedFetch 判断）。付费服务（`providers/jina.ts`、`providers/dajiala.ts`）、正文抽取（`content/extract.ts`，失败后 10 分钟再排，已有自己的重试）、图片（`media/images.ts`）、金属价格（`publication/metal-prices/`）都不打开。
3. **失败原因写出断开类型**（`sources/collect.ts`）：导出 `failureMessage(error)`，在 `error.message` 后面补 cause 的 code 与说明，例如 `fetch failed (UND_ERR_SOCKET: other side closed)`；没有 cause、或 message 里已经有这段时原样不动；结果仍截到 1000 字（`:260` 原来的长度）。`:260` 改用它，`sources.last_error` 与 `fetch_runs.error` 都写这个。退避、健康态与 `next_fetch_at` 一律不动。
4. **测试**：
   - `tests/http-fetch-retry.test.ts`（新文件）：本机起一个假服务器，`DROPPED_RETRY.afterMs` 改成几毫秒，`config.allowPrivateNetworkFetch = true`（同 `tests/web-list-json-html.test.ts:30`）。逐条核对：① 第一次 `req.socket.destroy()`、第二次给 200 → 打开选项拿到 200，服务器收到 2 次请求；② 同样的路径不打开选项 → 抛错，`droppedConnection` 为真，只收到 1 次；③ 每次都断开 → 打开选项也抛错，正好收到 2 次；④ 读正文时断开（先写一段再断开）→ 打开选项再取一次拿到完整正文；⑤ POST 打开选项 → 抛错，只收到 1 次；⑥ 返回 500 → 不重试，拿到 500，只收到 1 次；⑦ 一直不响应、`timeoutMs` 很短 → 超时抛错，只收到 1 次；⑧ `failureMessage` 对 ② 的错误给出 `fetch failed (UND_ERR_SOCKET: other side closed)` 这一类（code 允许是 `UND_ERR_SOCKET`、`ECONNRESET` 或 `EPIPE`），对没有 cause 的错误原样返回，超长时截到 1000 字。
   - `tests/web-list-json-html.test.ts`：加一条，驻外经商处那种列表（`/unit` 的同样内容）第一次请求被断开，`fetchWebList` 第二次取到两条，结果和 `:45` 那条测试一样。
5. **规格写回**：

## 输入输出与错误状态

- 输入：采集的一次 GET（列表页或详情页）。输出：第一次成功就和现在一样；第一次被对方断开、第二次成功，这一轮照常记成功，读者与后台看不出差别；两次都被断开，这一轮记失败，失败原因写 `fetch failed (UND_ERR_SOCKET: other side closed)` 这一类，退避照旧。
- 不变的：超时、连不上、DNS 失败、HTTP 4xx/5xx、验证页、太大的响应、地址检查不通过，处理和现在完全一样，也不多发请求。
- 一轮最多多花：每个被断开的请求多等 3 到 6 秒，再加一次请求的时间（列表页 25 秒、详情页 20 秒封顶）；采集任务的过期时间是 600 秒（`jobs/queue.ts:67`），够用。
