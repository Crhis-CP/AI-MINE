## 背景（为什么做）

TASK-0731 的复审实测结果：
- 两次构建的“稳定层”摘要不一致（运行 44786383147 与 44786932085，`check-dependency-layers.py --all-stable` 退出码 2）。依赖层内容相同，只是层内条目顺序不同；基础工具层里有删父镜像文件时留下的带时间戳删除标记。
- 用同一对制品在本地复演，rsync 实际发送了整包的 97.44%。

也就是说，“只传变化”目前没有生效，每次发布仍按整包传输。这里有两个独立的原因：
1. 层的内容不可复现；
2. 传输的单位是整个 `image.tar.gz`，压缩流中任何一处变化都会让后面的内容全部不同。

## 设计（Claude 定）

1. **层可复现。** 用固定版本的 BuildKit 构建（`docker buildx` 的 docker-container 驱动，`moby/buildkit` 按摘要固定），导出时打开 `rewrite-timestamp=true`，并设置 `SOURCE_DATE_EPOCH`（取提交时间）。父镜像里的日志和缓存文件改为清空，不删除，这样不会产生删除标记。apt 软件源固定到 snapshot，或者在卡上写明 Debian 更新会导致基础层变化。CI 和生产构建用同一套设置。
2. **按层传输。** 制品清单列出每一层的摘要和大小。服务器上保留现役版本的层文件，按摘要存放。传输时只传服务器上没有的层，到服务器后按清单重新组装镜像，再逐层核对摘要。整包 `image.tar.gz` 只作为兜底，旧格式的包仍然兼容。
3. **核对。** 增加一个自检：在两种不同的 GitHub 执行器镜像上各构建一次，除源码层和页面构建层以外，其余各层摘要必须一致。

## 不做

- 不改 `deploy/production-release.sh`（规则同 TASK-0731，没有例外）。
- 不引入镜像仓库、对象存储等任何会花钱的服务。
- 不改迁移、备份、回退和清理的现有行为。

## 验收

- 自测：两次不同执行器镜像上的构建，稳定层全部一致（附运行编号和检查输出）；按层传输在“服务器缺一层”“传输中断后续传”“现役版本在传输过程中变化”三种情况下都能正确处理；任何一层摘要不对就停止，现役版本不受影响。
- 一次真实发布的记录：只改了代码的一次发布，实际传输量不超过整包的 20%；同时记下总耗时和发布后的剩余磁盘。
