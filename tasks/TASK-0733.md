## 背景（为什么做）

TASK-0731 的复审实测结果：
- 两次构建的“稳定层”摘要不一致（运行 44786383147 与 44786932085，`check-dependency-layers.py --all-stable` 退出码 2）。依赖层内容相同，只是层内条目顺序不同；基础工具层里有删父镜像文件时留下的带时间戳删除标记。
- 用同一对制品在本地复演，rsync 实际发送了整包的 97.44%。

也就是说，“只传变化”目前没有生效，每次发布仍按整包传输。这里有两个独立的原因：
1. 层的内容不可复现；
2. 传输的单位是整个 `image.tar.gz`，压缩流中任何一处变化都会让后面的内容全部不同。

## 设计（Claude 定）

**第 0 步：先量，再选路线。** 发布慢的根子不只是“传了多少”，还有“从哪里传”。现在的路线是：先下载到操作机，再从操作机推到服务器。请先只读实测两个数：服务器直接从 GitHub 下载 CI 制品的速度，以及操作机推到服务器的速度，各测 3 次。
- 服务器直连明显更快、而且稳定：服务器自己取制品。这需要一个只读、只限本仓库、有过期时间的令牌，由 Owner 在服务器上自己保存，任何人不经手明文。之后再做下面第 2 条，作为省流量的增强。
- 否则：照下面第 1、2 条做。

1. **层可复现。** 用固定版本的 BuildKit 构建（`docker buildx` 的 docker-container 驱动，`moby/buildkit` 按摘要固定）。导出时打开 `rewrite-timestamp=true`，`SOURCE_DATE_EPOCH` 继续用 Dockerfile 现有的固定值 0，**不要改成提交时间**，否则依赖层每次提交都会变。父镜像里的日志和缓存文件改为清空，不删除，这样不会产生删除标记。CI 和生产构建用同一套设置。
2. **按层传输，不新增存储。** 现役版本的四文件包本来就保留在服务器上，而且 `image.tar.gz` 已经是每层单独压缩。传输时只传摘要不同的层，相同的层直接从现役包里取，到服务器后重新组装。**不新建一个“层仓库”**，也不给清理器增加新的一类东西。组装出来的归档必须和 CI 清单的摘要一致，镜像 ID 也必须和 CI 的一致，否则停止，按整包重传。整包传输仍然是兜底路线，它和按层传输用同一套代码（相当于“服务器一层都没有”的情况），这样兜底路线不会因为平时用不到而失修。
3. **apt 软件源不固定。** 安全补丁比省下的 20MB 更重要。Debian 一出更新，基础层就跟着变，那次发布会多传约 20MB。这一点写进 runbook。

## 二阶、三阶影响（已经考虑，验收时逐条核对）

| 影响到哪里 | 可能出的问题 | 本卡的处理 |
|---|---|---|
| 服务器磁盘 | 存一份层文件，等于再占约 0.6 GB，正好和刚腾出来的空间抢 | 不新建存储，直接从已保留的现役包里取层（设计第 2 条） |
| 版本清理 | 清理器要多认一类东西，误删了就没法组装 | 没有新东西；正在被用作基底的包，按 TASK-0731 已有的保护规则不删 |
| 回退与预览 | 重新组装出来的镜像如果和 CI 不是字节一致，回退和预览的“已核验镜像”检查就会对不上 | 要求归档摘要和镜像 ID 都与 CI 一致，否则不用 |
| 读者缓存 | 文件时间被固定以后，如果网页服务按文件时间判断新旧，读者可能一直拿到旧文件 | 现在的 `apps/web/server.ts` 不发 Last-Modified/ETag，静态文件靠带哈希的文件名和 1 小时缓存，不受影响。加一条测试：发布后，不带哈希的静态文件（图标、robots 等）返回的是新内容 |
| 每个 PR 的检查时间 | 换构建器、导出方式以后，`make-verify` 可能变慢；所有 PR 是一个一个排队合并的，慢几分钟就会拖慢全部工作 | 实现前后各记录一次 CI 用时；变慢超过 2 分钟就先优化，不合 |
| 安全 | 组装时复用服务器上的旧层，如果旧包已经损坏或被改动，新镜像会被污染 | 每一层复用前先核对摘要；服务器直连 GitHub 那条路线用的令牌只读、只限本仓库、有过期时间 |
| 发布频率和 Owner 的负担 | 发布变快以后会发得更勤，清理恢复点要 Owner 同意的次数也会跟着变多 | 本卡不改清理规则；如果要求同意的次数明显变多，另开卡调整（程序镜像自动清理，数据库恢复点只在空间不够时才申请删除） |
| 长期维护 | 多了一套固定版本的构建工具，要定期升级 | runbook 写清楚：怎么升级 BuildKit，升级时怎么重做两次构建的对比 |

## 不做

- 不改 `deploy/production-release.sh`（规则同 TASK-0731，没有例外）。
- 不引入镜像仓库、对象存储等任何会花钱的服务。
- 不改迁移、备份、回退和清理的现有行为。

## 验收

- 第 0 步的实测数据和选定的路线，写进交付记录。
- 自测：
  - 在两种不同的 GitHub 执行器镜像上各构建一次，除源码层和页面构建层以外，其余各层摘要全部一致（附运行编号和检查输出）；
  - 按层传输在“服务器缺一层”“传输中断后续传”“现役版本在传输过程中变化”“复用的层摘要不对”四种情况下都能正确处理，出错时现役版本不受影响；
  - 组装出来的镜像 ID 与 CI 一致；
  - 静态文件在发布后返回新内容。
- CI 用时：改动前后对比，增加不超过 2 分钟。
- 一次真实发布的记录：只改了代码的一次发布，实际传输量不超过整包的 20%（或者服务器直连路线下的实际下载用时）；同时记下总耗时和发布后的剩余磁盘。
