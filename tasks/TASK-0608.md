## 依据与范围

Claude 在看板 #348 的 6803612316 将卡 A 指派给 Codex：先分开生产依赖与源码，再按相同正式流程验证。Dockerfile 改动约 20 行以内；验证只覆盖依赖层稳定、运行等价及包大小，不建立新的构建平台。

## 交付内容与联动

- 复用固定的 base、npm 版本、各工作区 package.json、根锁文件和 .npmrc；独立阶段只安装生产依赖，放在源码及网页构建产物层之前。
- 保留所有工作区的生产依赖及链接，不能只复制根 node_modules 而漏掉嵌套依赖。构建阶段仍可使用开发依赖，运行镜像不带开发依赖。
- 保留运行用户、文件属主、pg_dump、入口、端口和现行环境隔离；不改任何业务模块、数据库、模型或生产配置。
- 现有 toolchain 只认可 npm prune --omit=dev；如采用等价的独立 npm ci --omit=dev，最小调整此检查及反例，继续拒绝开发依赖进入运行镜像，不能靠保留无用命令骗过检查。
- 在现有 compose-smoke 中接入最小的依赖层比对，不新增必过阶段。使用已经隔离的测试源码和独立测试镜像，在同一构建器连续构建两次，仅第二份测试源码改变；实际导出的受测镜像仍绑定准确提交，不用修改过的测试镜像发布。
- 只在有 Docker 的非生产执行器运行真实构建与服务演练；本机没有 Docker 时如实记录未执行，不让静态检查代替。

## 验收

- 两次仅源码不同的构建，依赖层摘要相同；源码/构建产物层应变化。依赖层必须确实处在两份最终运行镜像中，不能仅比较未被使用的中间阶段。
- 服务能启动，现有 compose-smoke、故障回退演练及全部 21 个阶段通过，最终回执绑定最终 SHA。
- 比较前后运行镜像的生产依赖清单、必要工作区链接和运行入口；记录完整发布包的实际字节数，不只看 Docker 显示大小。
- 记录同一构建器复用的边界：没有跨执行器缓存证据时，不承诺跨 CI 运行摘要一定相同或包一定变小。

## 打包边界与停止条件

现有 release_artifact.py 使用完整 docker image save，仍包含所有层；分层不自动等于减少完整归档传输。此问题已在 #348 的 6803899379 交给 Claude 裁定。本卡不改 release_artifact.py、四文件格式、独立清单哈希和同一受测镜像要求，也不自建镜像仓库或缓存服务。正式传输仍须得到与 CI 原件完全相同的文件。

若为达到传输目标必须改变打包格式，或最小真实验证明显超过本卡范围，先回看板由 Claude 明确范围，再修订计划；不先改再补授权。不改变 8 GiB 准入、质量闸门、回退保留范围及 verify_revision 的计算方式。
