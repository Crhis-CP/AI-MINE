## 背景（为什么做）

审计里有一批“随数据增长会变慢”的条目（每次付费调用的统计、分析表扫描、列表全量读取、搜索没走索引、RSS 整体重算），都是读代码推断的。查询线回报线上没有开查询统计（#348 评论 6844826746：`pg_stat_statements` 未开），所以哪条最慢、慢多少，现在没有数据。先开统计，再按数据排优先级，避免凭猜测改查询。

开销：这个扩展是 PostgreSQL 自带的，默认设置下占用很小；它记录的是去掉参数的语句模板，不记录参数值，不会把读者或后台的输入写进去。

## 交付内容（做什么）

1. `docker-compose.yml` 的 `db` 服务加启动参数：
   ```yaml
   command: ["postgres", "-c", "shared_preload_libraries=pg_stat_statements", "-c", "pg_stat_statements.max=5000", "-c", "pg_stat_statements.track=top"]
   ```
2. 新迁移 `database/migrations/platform/ops/202611131200_query_stats.sql`：
   `CREATE EXTENSION IF NOT EXISTS pg_stat_statements;`
   文件头注释写明用途，以及“参数只在数据库重启后生效；重启前视图不可查询，但建扩展本身不依赖重启”。登记到 `database/migration-inventory.json`。
3. `scripts/verify/compose-environment.ts` 如果对 db 服务的字段有白名单，加上 `command`；配一条测试断言预加载参数存在。
4. `docs/04-architecture/07-deployment-and-ops.md` 记一段：怎么看（`SELECT calls, round(total_exec_time) AS total_ms, round(mean_exec_time) AS mean_ms, left(query, 120) FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20`），以及只贴语句前 120 个字符、不贴别的。

代码量预算：编排 1 行；迁移 3 行；检查和测试约 20 行。
