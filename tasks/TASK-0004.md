- **D4 数据库角色与授权**（AC-SEC-02 的 M0 部分；PIT-059 的七类登录）：迁移之后由一个“建角色与授权”步骤，按一张授权表建角色、授权与行级策略。
  - **角色与执行者**：角色名为“前缀_角色”，缺省前缀 `amp`。角色是整个 PostgreSQL 集群共用的：同一集群上的几个库共用一套角色，各库分别授权。测试用随机前缀，跑完（失败时也一样）先删临时库，再逐个 `DROP ROLE`；要保留库时，每个角色单独一条 `DROP OWNED BY`（PostgreSQL 16.14 上，库里有 `ALTER DEFAULT PRIVILEGES FOR ROLE <worker> … TO <private_ops>` 时，把两个角色写进同一条 `DROP OWNED BY` 会报 “could not find tuple for default ACL”，整条回滚；第 2 轮审查实测）。这一步要用超级用户执行，因为 `backup` 要带 `BYPASSRLS`，而 PostgreSQL 只许超级用户或本身带这个属性的角色建这种角色。建出的登录没有口令，口令由部署发放（TASK-0009）。
  - **授权表**：给 `public` schema 的每张表定好七类角色的权限，**有表没分类即失败**。`pgboss` schema 下的表按 D5 的规则算，不逐表分类。
  - `public_read`：只能读公开读取层用到的表与列，`sources`、`articles`、`translations` 只给用到的列；行级策略见下。另外 `NOINHERIT`、限连接数、不给 `TEMPORARY`；撤销 `PUBLIC` 的 `CONNECT`，再逐个角色授权。
  - `feedback_write`：`feedback` 只能 INSERT，另给 `feedback.id` 的 SELECT（`operations/feedback.ts:71-73` 用了 `RETURNING id`）与 `feedback_id_seq` 的 USAGE；`feedback_bans` 只读。
  - `auth`：只碰 `admin_users`、`admin_sessions`（读写）与 `audit_log`（只能追加与读取）。
  - `private_ops`、`worker`：读写业务表，不碰 `admin_users`、`admin_sessions`；`audit_log` 只能追加与读取。
  - `backup`：所有表与序列只读，包括 `pgboss` 下的表（授权见 D5），并带 `BYPASSRLS`。`pg_dump` 不加 `--enable-row-security`（缺省 `row_security = off`）。万一角色没带这个属性，遇到行级策略就报错，不会悄悄少导。序列也要 SELECT：`pg_dump` 读序列用 `SELECT last_value, is_called`，没有授权就报 “permission denied for sequence” 并退出（本机实测）。
  - `migrate`：属主。属主不受行级策略约束（不开 `FORCE`）。
  - **行级策略**开在 `articles`、`translations`、`settings` 三张表上：
    - `public_read` 一条只读策略：`articles`、`translations` 只露出有公开投影行（`publications`）的材料，`settings` 只露出 `selected_ledger_epoch` 一行；
    - `worker`、`private_ops` 各一条读写放行策略（`USING (true) WITH CHECK (true)`）；
    - `feedback_write`、`auth` 对这三张表没有授权；`backup` 有 SELECT，靠 `BYPASSRLS` 读全表。
    
    开了行级策略的表，对既非属主、又没有适用策略的角色是这样的：读到 0 行；UPDATE 不报错，只改 0 行；INSERT 报错。所以每个要用这三张表的角色都必须有策略，真实登录测试逐个验证。
  - **本机实测**（PostgreSQL 16.14，2026-10-03，临时库与临时角色用完已删）：
    - worker 有放行策略时，读、改、插都正常。
    - `backup` 只有 `USING (true)` 的只读策略时，缺省 `pg_dump` 报 “query would be affected by row-level security policy”；加 `--enable-row-security` 才导出全部行。
    - `backup` 带 `BYPASSRLS` 时，缺省 `pg_dump` 导出全部行。
    - 带 `CREATEROLE`、不带 `BYPASSRLS` 的登录去建带 `BYPASSRLS` 的角色，被拒。
    
    所以备份不用审查建议的“只读放行策略”，改用 `BYPASSRLS`：漏配时会报错；而“放行策略加 `--enable-row-security`”在策略漏写时会悄悄导出 0 行。

- **D5 任务队列**：
  - **schema 与安装**：“建角色与授权”步骤先建好 `pgboss` schema（`CREATE SCHEMA IF NOT EXISTS pgboss AUTHORIZATION <前缀>_worker`），属主是 worker。`pgboss` 已经存在而属主不是 worker（例如单一登录时期装好的本地库）时，这一步报错停下，不悄悄跳过：`IF NOT EXISTS` 什么也不做，表仍归原属主，worker 与 private_ops 都没有权限。表与函数照旧由 worker 第一次启动时安装与升级（`jobs/queue.ts:39-47`）。
  - **worker 不建 schema**：worker 没有库级 CREATE 权限，也不给。pg-boss 12.34.0 的 `createSchema` 缺省为 true（`dist/attorney.js:415`），首次安装时先执行 `CREATE SCHEMA IF NOT EXISTS`（`dist/contractor.js:79-90`、`dist/plans.js:139,194-196`）；PostgreSQL 执行这一句时先查库级 CREATE 权限，再看 schema 在不在，所以 worker 会报 `permission denied for database`，什么也装不上（第 2 轮审查实测；上一版写的“不冲突”是错的）。因此配了按角色的地址时，worker 的 PgBoss 用 `createSchema: false` 启动；单一地址的过渡期保持缺省。这一项在 PR4 随 worker 的 pg-boss 按角色取地址一起改，正例在 PR8（见“完成条件”）。
  - **private-api 的权限**：同一步骤给 private_ops 这个 schema 的 USAGE，并执行 `ALTER DEFAULT PRIVILEGES FOR ROLE <前缀>_worker IN SCHEMA pgboss GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO <前缀>_private_ops`，序列同理给 USAGE、SELECT。这样 worker 以后建的表也自动带上这些权限。
  - **备份的权限**：备份作业对整个库执行 `pg_dump`（`packages/backend/src/operations/backup.ts:122`，不限定 schema；由 worker 的定时任务运行，`apps/worker/src/schedules.ts:64`），会连 `pgboss` 一起导。同一步骤给 backup 这个 schema 的 USAGE，并执行 `ALTER DEFAULT PRIVILEGES FOR ROLE <前缀>_worker IN SCHEMA pgboss GRANT SELECT ON TABLES TO <前缀>_backup`，序列同理给 SELECT。必须用默认权限：worker 会按日期不断新建 `queue_stats_YYYYMMDD` 分区，一次性 GRANT 管不到以后的表。漏了这两句，每天的备份在 `pgboss` 上报 `permission denied for schema pgboss` 并退出（第 2 轮审查实测；加上后导出成功）。BYPASSRLS 只跳过行级策略，不能代替 SELECT 授权。
  - **private-api 的 pg-boss**：用 `migrate: false`、`supervise: false`、`schedule: false` 启动，不安装、不维护、不跑定时，只往已有队列发任务。队列只由 worker 建，private-api 上的 `ensureQueue` 只查不建。
  - **队列没就绪时**：private-api 本身照常启动、照常登录；要发任务的后台操作返回 503，写明原因，下次请求再试。三种情况：
    - worker 还没装好：pg-boss 启动抛 “pg-boss is not installed”（`dist/contractor.js:251-254`）；
    - 镜像里的 pg-boss 比库里的新、worker 还没升级：抛 “pg-boss database requires migrations”（`dist/contractor.js:257-258`）；
    - 队列还没建：`send` 抛 “Queue … does not exist”（`dist/manager.js:786`）。
    
    “下次再试”要先清掉 `getBoss()` 缓存的那个失败的 Promise（`jobs/queue.ts:39-49`），否则一直失败。
  - **队列由 worker 全部建好**：现在 worker 在 `COLLECT_ENABLED=false`（开发与测试的缺省）时不建 `sources.fetch`、`sources.mp`（`apps/worker/src/main.ts:16`），后台“立即抓取”却往这两个队列发（`admin/sources.ts:190-191`），原来靠 api 的 `ensureQueue` 顺手建（`jobs/queue.ts:66-72`）。private-api 不再建队列以后，改为 worker 启动时把全部队列名都建好，不论这一类任务这次处理不处理；任务照旧发得进去，等开启采集后处理，读者与后台看到的行为不变。
  - **验证**：授权表按上面的 schema 规则算 `pgboss` 下的表。真实登录测试验证：worker 用自己的登录（没有库级 CREATE）第一次启动能装好 pg-boss 并建队列；private_ops 能向已有队列发一个任务，不能在 `pgboss` 里建表；backup 导整库时包括 `pgboss` 的数据。public-api 不碰队列。
