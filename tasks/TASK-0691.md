审计方：Claude（Issue #495，AUD-14）。实现方：【Codex·审计修复】。依赖 TASK-0686 的 `clientNetwork()`。

## 背景（为什么做）

- `apps/api/src/app.ts:44`：全局 `bodyLimit` 10MB。后台路由在处理函数里才验会话（`packages/backend/src/admin/http.ts:14`），所以任何人都能让 api 先读完、解析完 10MB 的请求体，再拿到 401。
- `apps/api/src/routes/feedback.ts:41` 的 multipart 解析器、`apps/api/src/routes/admin-auth.ts:48` 的表单解析器都注册在根实例上，对所有路由生效。
- `app.ts:51`：读取限流用正则匹配原始 `req.url`。路由器会解码百分号转义，所以 `/api/v%31/items` 照样进 v1 的处理函数，却绕过了限流。`/api/mcp` 不在限流范围内。
- `apps/api/src/http/public-limits.ts:11`：记录表满 5 万条后，新来源一律被拒（429），直到窗口滚过去。

## 交付内容（做什么）

1. `app.ts:44`：全局 `bodyLimit` 改为 `256 * 1024`。需要大请求体的路由各自写 `bodyLimit`：反馈已有 12MB（`feedback.ts:42`）；其余按停止条件第 1 条找出来并单独设置。
2. 解析器挂到用到的路由：
   - 反馈：`registerFeedback` 改成 `app.register(async (scope) => { scope.addContentTypeParser("multipart/form-data", …); scope.post("/api/site/feedback", …) })`。
   - 表单：`/api/auth/password` 和 `/api/auth/logout` 两个路由放进同样的封装作用域，表单解析器只在里面注册。
3. 限流判断（`app.ts:49-53`）：
   - 用 `req.routeOptions.url`（匹配到的路由模式）判断，不用原始 `req.url`；覆盖 `/api/v1/*`、`/api/v3/*` 和 `/api/mcp`。
   - 限流键用 `clientNetwork(req.ip)`（IPv6 按 /64）。
4. `public-limits.ts:11`：表满时删掉最早插入的一条再记新来源，不再拒绝新来源。Map 按插入顺序迭代，删 `keys().next().value` 即可。
5. `app.ts:181` 附近的错误处理：4xx 记 `warn`，5xx 仍记 `error`。

测试：`/api/v%31/items` 计入限流；`/api/mcp` 计入限流；同一 /64 的不同地址共用额度；表满后新来源仍能访问、最早的记录被淘汰；未登录向后台路由发 1MB 请求体得到 413，而不是读完再 401；反馈上传仍可用。

代码量预算：实现约 50 行；测试约 80 行。

- 不把 `/api/site/*` 纳入限流（读者站的主要接口，另行评估）。
