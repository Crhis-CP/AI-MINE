## 背景（为什么做）

Node 在 2026-11-11 发布了 24.22.3 安全版，修了多项高危；fast-xml-parser 的公告 GHSA-474x-hrwr-fgx4 在 11-10 发布。到 11-13 审计时，这两项都没人发现。原因是仓库没有任何定期检查：

- npm 审计只在 PR 的 `make verify` 里跑，而且只拦高危（`scripts/verify/run.ts:386-397`）。没有新 PR，就没人知道锁文件里的老版本出了新公告。
- 基础镜像（`Dockerfile:3` 的 Node、`docker-compose.yml:27` 的 PostgreSQL、`:113` 的 Caddy）从来不检查。
- 技术栈文档定的 Renovate 启用条件是“首次生产部署后”（`docs/04-architecture/02-tech-stack.md:133`），条件早已满足，一直没启用。自动开 PR 的工具在本仓库也行不通：它开的 PR 没有任务卡，过不了路径守卫。

## 交付内容（做什么）

1. 新增 `scripts/dependency-watch.ts`（`node scripts/dependency-watch.ts`），做三项检查，任一项发现问题就打印清单并以非零码退出：
   - **npm 公告**：运行 `npm audit --package-lock-only --audit-level=low --json`，列出所有公告（包名、等级、公告编号、修复版本）。
   - **Node 安全版**：读 `https://nodejs.org/dist/index.json`，与 `Dockerfile` FROM 行的版本比较。同一大版本里有 `security: true`、版本号更高、发布满 1 天的版本，就报出来。
   - **镜像补丁版**：对 `Dockerfile`、`docker-compose.yml` 里每个 `image@sha256` 或 `FROM … @sha256`，读 `https://hub.docker.com/v2/repositories/library/<名>/tags?name=<主.次>.&page_size=100`。同一“主.次”线上有更高补丁版本、且发布满 3 天的，就报出来（PostgreSQL 的“主.次”按“主”算，例如 17.x）。

   网络请求超时 20 秒；网络失败与“发现问题”分开报（退出码 2 对 1），不要把网络故障说成有漏洞。
2. 新增 `.github/workflows/dependency-watch.yml`：
   - `on: schedule: - cron: "17 2 * * *"`（UTC，每天一次），外加 `workflow_dispatch`；
   - `permissions: contents: read`；
   - 步骤只有：checkout、setup-node（两者固定到与 `verify.yml` 相同的提交哈希）、`node scripts/dependency-watch.ts`。不安装依赖，不上传制品。

   定时工作流失败时，GitHub 会按默认通知设置发邮件给仓库所有者，这就是提醒方式，不新建通知通道。
3. 测试 `tests/dependency-watch.test.ts`：用 `tests/fixtures/dependency-watch/` 里的 JSON 夹具（节选的 index.json、Docker Hub 标签页、npm audit 输出），不访问网络。覆盖：有安全版要报；不满 1 天不报；同线无更高补丁不报；网络失败返回 2。
4. `tasks/TASK-0050.md` 的“背景”末尾补一句：新公告由每日检查发现，再按本卡处理。
5. 确认 `scripts/tsconfig.json` 的 `include` 覆盖新脚本，不覆盖就补上。

代码量预算：脚本约 120 行；工作流约 25 行；测试约 70 行。

## 明确不做

- 不启用 Dependabot 版本更新或 Renovate（它们开的 PR 过不了路径守卫）。
- 不自动修复、不开 PR、不发 Issue（不给工作流写权限）。
- 提醒：仓库设置里的“Dependabot alerts”是免费的，打开后 GitHub 会对 npm 公告另发提醒。这要 Owner 在网页上点，不在本卡。
