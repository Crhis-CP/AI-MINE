## 背景（为什么做）

- `packages/backend/src/publication/v3.ts:191-193`：`/api/v3/featured/snapshot` 对整页每一条调用 `v3Item(id)`，用 `Promise.all` 同时发出。默认一页 500 条、最多 1000 条（`packages/contracts/src/http/v3.ts:312`）。
- 每个 `v3Item` 走 `loadItemDetail`，约 15 条串行查询；其中 `eventCoverage` 每条都把整个事件的成员重读一遍（`detail.ts:224-235`）。
- 结果是默认一次请求约 7500 条查询，同时塞进 api 唯一的 10 条连接的连接池。`v3-collections.ts:40`（事件时间线最多 100 条）、`:71-91`、`:114-127` 是同样的写法。
- 响应是 `no-store`，每个来源每分钟可以请求 600 次。一个外部调用方就能让全站读者页的数据请求排队。

## 交付内容（做什么）

1. 新增 `packages/backend/src/lib/concurrency.ts`，导出 `export async function mapLimit<T, R>(items: readonly T[], limit: number, fn: (item: T) => Promise<R>): Promise<R[]>`，保持结果顺序。配 `tests/concurrency.test.ts`。
2. `v3.ts` 和 `v3-collections.ts` 里所有 `Promise.all(xxx.map((item) => v3Item(...)))` 改为 `mapLimit(xxx, 4, …)`。用搜索命令 `git grep -n "v3Item(" -- packages/backend/src/publication` 找全，在 PR 列出每一处。
3. `eventCoverage`：给 `loadItemDetail` 加一个可选的请求内缓存参数（例如 `{ coverage?: Map<string, …> }`），按事件 ID 缓存。同一次 v3 请求里同一个事件只算一次。缓存只活在一次请求里，不跨请求。
4. 整页缓存：`v3Snapshot` 和事件列表的结果按 `(接口, 参数, contentVersion() 返回的版本与撤稿版本)` 做进程内缓存，60 秒，最多 50 项，同一个键并发时只算一次。撤稿会改变撤稿版本，缓存键随之改变，不会继续返回已撤下的内容。
5. 测试：用测试库造 30 条精选，`v3Snapshot({ limit: 30 })` 的结果与改动前逐字段一致；同时在途的 `v3Item` 不超过 4 个（可在测试里包一层计数）；撤稿后再请求拿到新结果。

代码量预算：实现约 80 行；测试约 80 行。
