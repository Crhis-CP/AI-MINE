## 背景（为什么做）

按来源限流有两类同样的问题。一是 IPv6 按单个地址计，换同一 /64 网段里的另一个地址就是一份新额度。二是有的限流键带上了浏览器标识，换个标识写法就是新额度。前面几张卡已经处理了反馈、登录和 api 读取限流，剩下两处：

- `modules/site-admin/backend/visits.ts:108`：信标限流的客户端键是 `HMAC(地址 + 完整浏览器标识)`。每次换标识就是一份新的每分钟 60 次额度。`:142-147` 每个信标都能写一个新的来源网站，`ops.visit_referrers` 每天的条数没有上限（页面每天有 5000 的上限）。
- `apps/web/request-guard.ts:236`：读者站限流按完整地址计。记录表满 5 万条后，`prune()`（`:254-261`）每次都把全表扫一遍才删一条。

## 交付内容（做什么）

1. `visits.ts:108`：限流用的客户端键只用网络地址，用 `clientNetwork()`（来自 `@amp/backend/lib/client-network`，site-admin 本来就依赖 backend）。**访客识别（日活、月活）用的键不动**，只改限流。
2. `visits.ts:142-147`：同一天里不同的来源网站最多记 200 个，超出的计入一个固定的“其他”行（键名用现有表能接受的值，例如 `(other)`）。
3. `request-guard.ts`：
   - `take()` 里计算 key 之前，IPv6 地址取前 64 位（web 不能导入后端代码，所以在文件内写一个约 10 行的小函数，规则与 `clientNetwork()` 一致：IPv4 原样，`::ffff:a.b.c.d` 按 IPv4，IPv6 取前四组加 `::/64`）；
   - `prune()` 的过期循环遇到第一个还没过期的记录就停（Map 按插入顺序排列，续期的记录会重新插入）。
4. 测试：
   - 同一 /64 的两个地址共用信标额度和读者站额度；
   - 换浏览器标识不再得到新额度；
   - 第 201 个来源网站计入“其他”；
   - 表满时 `prune()` 不扫全表（可以断言访问次数，或用计时上限）。

代码量预算：实现约 45 行；测试约 60 行。
