## 背景

数据按模块归属，迁移只增不破（ADR-0003）。AIHOT 存量表暂留默认 schema，登记在《待迁出清单》，只减不增。

原始计划盘点输入为 `ab02b0ec95c3fe68933a97797c0b82ccc988fc53`，实施基点以本卡 base_sha 为准，沿用 TASK-0004 的实际角色登录、数据归属检查与子进程夹具。原 `runtime` 泳道不能覆盖存量 backend 与根测试入口，改用既有 `architect` 集成泳道；`allowed_paths` 仍逐文件约束 backend，不授权 `backend/**`。本计划不表示数据库升级或金额验收已完成。

## 实施边界与最小切片

每片 ≤400 有效行；先独立可用的纯准备，再原子接通依赖它的执行路径。以下顺序不新增产品取舍。

### D1 · 历史原件与唯一迁移目录

- 当前实施基点的 **30 份**（含已合并0038；早期盘点29份的证据保持其原范围） `database/migrations/*.sql` 原路径、名称、字节哈希保持不变，不搬目录、不重编号、不改写旧表定义；后续已合并迁移同样只增不破。存量 `schema_migrations.name` 与已执行身份保持兼容，不清空记录重新执行。
- 新模块迁移用 `database/migrations/<module>/<UTC 时间戳>_<说明>.sql`；模块与 schema 映射依模块地图（`ai-gateway` → `ai`），原 public 存量继续登记，不靠重标归属消债。
- 纯目录实现固定为 `scripts/migrations/inventory.ts`：历史集合、新文件、字节哈希、规范模块/schema、依赖与排序。先拓扑再稳定时间戳/路径排序；拒绝缺依赖、循环、重复身份、未知模块与路径逃逸。历史哈希清单放 `database/`，由固定 Git 原件生成并核对。
- `scripts/migrate.ts`、verify 的迁移 lint / `data-ownership.ts`（C）、`scripts/db-roles{.ts,/catalog.ts,/grants.ts}` 共用这个目录，不能各自递归出不同集合。C 使用 schema-qualified 对象；保留历史债务及 UNKNOWN 的输入/依赖指纹保护，目录拓扑化不等于既有 UNKNOWN 已被证明。
- 第一份新模块迁移与执行器、C、授权目录支持在同一可运行增量接通。每文件 SQL 与执行记录同事务，执行器互斥；失败回滚、连接关闭、重复执行不重做。历史已执行项先按固定原件核对再增量补校验记录；未知已执行名称、对应原件缺失或哈希不符时拒绝，不能静默补成成功。
- 授权目录扩展受控 schema、表、序列、owner、RLS 与默认 ACL；未知对象仍拒绝。新金额表按实际 worker / private_ops / backup 用途给最小权，不默认授予 public_read；原有 48 表角色矩阵保持。

### D2 · PG18 制品与升级证据

- PostgreSQL **18.6** + pgvector **≥0.8.4**，固定补丁版、目标架构与 sha256；应用镜像内 `pg_dump` / `pg_restore` 为 18。只安装扩展，不改 `real[]` 向量列、不建向量索引、不改 embedding 模型或召回。
- Compose 同步 PG18 的 PGDATA / volume 位置；升级使用新数据目录，不能让 PG18 直接打开 PG16/17 卷。空库、上一版本合成快照升级、失败重跑、扩展备份恢复与实际 backup 登录均留证。
- “上一版本”从本新仓库固定 SHA + 合成数据重建，保留迁移账本与有代表性的业务行；不读取旧项目代码、旧数据、现有 `.env` 或生产数据库。
- 本地 arm64 准备镜像不是目标 amd64 发布制品；正式组合镜像与应用镜像、18 客户端及目标架构仍需验证。最终 PG18 行为基线逐项解释差异，保留原始输出，不宣称与早期基线全字节相同。

### D3 · 每文件模板库隔离

- `scripts/verify/test-files.ts` 作为父执行器，复用 `tests/setup.ts` 和现有测试正文；`package.json`、verify 与 `scripts/baseline/run.sh` 接同一入口。先实现隔离，再移除 `--test-concurrency=1`，不靠删测试取得并行。
- 父进程在执行器提供的一次性测试库构建“全部迁移 + topics-only”模板，关闭连接后封存；不放活动 pg-boss、启用信源或付费回执。每文件克隆随机 `*_test`，在任何被测模块导入前传入独立子进程环境。
- 等子进程、after hooks 和连接池结束后清理；失败、超时、取消也清理，只处理父进程登记的库/角色。沿用 role-db、public-role、api-process、private-producer 的隔离夹具；集群级角色仍随机唯一。
- 空库迁移、首次 pg-boss 与恢复测试保留真正空库/restore 目标，不能被已迁移模板掩盖。并行数与总连接有界，日志按文件汇总但不丢失失败。
- 验证两个文件修改同名预算/队列互不影响、子进程只连本文件库，以及失败/取消后无所属库、角色、连接残留；非 `_test` / `_ci` 数据库仍拒绝启动。

### D4 · 数值行边界与原接口兼容

- 不设 OID20/int8、OID1700/numeric 的全局 Number 解析；numeric 保持精确字符串，int8 用字符串/bigint。先完成受影响行 schema 与有界转换，再切换全局 parser；不能把所有结果局部 `Number()` 一遍代替修复。
- `packages/backend/src/lib/db-values.ts` 只承接明确行边界/安全范围；repository 对外查询用同源 Zod 行 schema 解析并与实际列集合核对。金额计算走 D5；计数/评分可在明确范围内保持现有 Number 语义。
- 本次已定位的兼容调用点：`providers/receipts.ts` 的次数/回执 ID，`admin/models.ts` 的用量展示，`publication/{publish,v1}.ts` 的精选序列与水位，`operations/feedback.ts` 的返回 ID。其余消费者先产出精确字段/文件清单，确需修改时补本卡，不扩大为整个 backend。
- HTTP 字段、可空值、分页游标、ETag / 304、媒体类型与错误行为保持原样；不得暗改 bigint 为字符串。若现有 wire 类型无法安全表达，先走 TASK-0005 契约变更，不用类型断言掩盖溢出。

### D5 · 真正的金额预留、结算与既有调用接入

- 当前 `paidRequest` 的 pending 只是请求占位，`budgets` 是次数限制，均不是金额仓储。本卡新增 `providers/money.ts`、`providers/usage-ledger.ts`，由 `providers/receipts.ts` 的实际付费链调用；归属 ai-gateway，新表放 `ai` schema，使用 D1 的增量迁移和授权。
- 内部金额使用币种 + 整数微单位（或等价精确十进制），明确 scale、范围、舍入与非法输入；SQL 绑定规范十进制字符串。费用缺失是未知，不能算零；币种分开求和，不擅加汇率或价格。优先现有工具链，不为值对象增加依赖。
- 预留绑定稳定业务键与报价证据：同键同参数幂等、异参拒绝；结算绑定实际 receipt / attempt，重放不重计。并发用短事务/锁保证原子性，网络调用在事务外；实际金额、估算依据、lane / 能力 / 来源维度按已有规格保存，新增共享载荷先过契约。
- `providers/jina.ts` 的既有浮点估算改为确定性精确计算；`providers/dajiala.ts` 的供应商 number 输入须保留回执并明确有效精度，不能恢复不存在的原始小数。旧 cost / 私有展示含义保留，仅出口可做有界兼容转换，展示估算不能反写精确账本。
- BR-COST-04 / 16 的已批准约束优先于现有实现：结果未知且未确认未计费前，该调用永不重发。在已列的 `providers/receipts.ts`、`admin/runs.ts` 收口回执/重发状态并接账本公开函数；`billed: null` 的 30 分钟自动重排队不得释放未知预留，也不得允许该调用再次付费。有明确未计费证据才能释放对应占用并解锁；`billed: true` 且无实际金额不能虚构结算或重发。其他重试策略、次数熔断、模型路由与阈值不扩改；共享状态/字段改变仍先经 TASK-0005。
- 人工未计费确认须把receipt、attempt和审计作为一个事务提交。现有 `admin/auth.ts` 的 `audit()` 固定使用自身连接，补此准确路径只为增加兼容的可选事务参数并由本片调用；旧调用者含义保持，其他认证、会话和权限行为不变。审计失败或并发重复确认不能留下已放行却无记录的回执；当前接口无法表达的已计费金额核销留后续契约，不在此片伪造结算。
- 用假服务验证真实 `paidRequest → reserve → received → settle`，包括超时未知、明确未计费、重放与并发。同一正式仓储必须同时供实际调用与 10 万笔测试使用；不另造测试专用 SQL 算法。
- 未取得有效报价的 LLM / embedding 成本仍诚实保留未知；本卡不新增其定价、供应商启用或模型设置，不声称全部模型用量能力完成。若需要给其调用新增字段，先契约片与精确路径卡，不在本卡悄然扩接口。

### D6 · 验收与归档

- 空库全量、历史哈希、schema 归属、lint、上一版合成快照升级进入正式 `migrations` 阶段；篡改旧文件、缺依赖/循环、SQL 失败、未知对象/越权各有对应反例。列改名必须使实际 repository 的列/行解析测试失败。
- **10 万笔**通过 D5 正式仓储，交错微小预留/结算、同键重放、并发同键、未知占用与有证据释放；覆盖至少两个币种而不启用外币价格。用独立 BigInt 预期和数据库 `SUM(...)::text` 按币种逐位核对预留、已结算与未知占用，并关联回执总账。孤立 `SUM`、pending 行数或展示金额不能替代此验收。
- 按 T-140 / BR-COST-14 验证配置熔断阈值、70% 预警线、每 100 元提示步长：各边界前 1 微单位、等于边界、后 1 微单位均使用精确金额比较，不因舍入放过或误触发；保留既定 `>` / `≥` 与复合条件含义。这是金额比较验收，不启用新阈值、熔断或通知系统。
- 真实 paidRequest 集成证明使用同一仓储；没有报价的路径明确列为残余，金额缺失不填零。不能以 10 万笔库内一致性冒充真实供应商金额、全量网关政策或业务质量已验收。
- 复用原角色真实登录矩阵、公开路由与行为基线，在 PG18 最终候选记录完整结果；随后取得最终提交及合并 main 的 full 回执。归档到本卡允许的 T-0005 验收正文和 baseline 目录。
