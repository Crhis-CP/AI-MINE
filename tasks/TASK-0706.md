## 背景（为什么做）

`packages/backend/src/enrichment/records.ts:19-33` 的 `recordedMaterialWaits(db, articleId?)` 不带文章条件时，会读出 `analyses` 的每一行，每行解压 `output` 这个 jsonb 两到三次，再对全表做 `DISTINCT ON`。调用方是运营快照和内容清扫（`jobs/content.ts:657`，每 5 分钟）。`analyses` 只增不删，线上现在约 8.7 万行、87MB（#348 评论 6844826746），只有 `(article_id, id DESC)` 一个索引。运营快照有 2 秒超时，表再大一些，后台的“处理进度”会悄悄变成不可用。

## 交付内容（做什么）

1. 新迁移 `database/migrations/enrichment/202611131210_analyses_material_wait.sql`（按仓库惯例：大库先手工 CONCURRENTLY 建好，迁移用 `IF NOT EXISTS`），登记到清单：
   ```sql
   CREATE INDEX IF NOT EXISTS analyses_material_wait_idx ON analyses (article_id)
     WHERE origin = 'model' AND relevance = 'unknown' AND (output->'scores') = 'null'::jsonb
       AND coalesce(output->>'writer', '') = '' AND coalesce(pg_catalog.cardinality(receipt_ids), 0) <= 1;
   ```
2. 改写查询，结果必须与原查询逐行相同。做法：
   - 先取候选：`SELECT DISTINCT article_id FROM analyses WHERE <与索引完全相同的条件> AND ($articleId IS NULL OR article_id = $articleId)`。只有“最新一条完整分析是等待状态”的文章才会出现在结果里，而它必然有一条等待状态的行，所以候选集不会漏。
   - 原来的 `complete`、`latest` 两段只在 `article_id = ANY(候选)` 的范围内计算，走现有的 `analyses_article_idx`。
   - 查询里的等待条件要和索引谓词写法一致，规划器才会用上这个部分索引。
3. 测试：造这几类文章各若干：最新是等待；等待之后又有了完整结果；只有 `relevance='block'`；同一修订有多条等待行；没有任何分析。断言新旧两种写法（旧写法在测试里保留一份原 SQL）结果完全一致，`oldest_at` 取到最早那条。再断言带 `articleId` 参数时结果一致。

代码量预算：迁移约 6 行；实现约 20 行；测试约 70 行。

## 明确不做

- 不改调用频率（运营快照的间隔由 TASK-0702 处理）。
