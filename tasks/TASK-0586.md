Owner 2026-11-07 同意在 `.env` 设 `CLIENT_IP_HEADER`，并由 Codex 让源站只接 EdgeOne 回源，EdgeOne 保持免费版（台账 DEC-78补充·网站安全防护、DEC-78补充·信源扩充）。Codex 核实（看板 6714624954）：
- 免费版不提供回源 IP 段，安全组无法按地址只放 EdgeOne；
- 源站没限制前就相信访客地址头，直连源站的人可以伪造这个头，影响限流、登录次数和反馈次数的计数。

## 背景（为什么做）

- 现在 web 只要连接来自本机代理（Caddy，内网地址），就相信 `CLIENT_IP_HEADER`。直连源站的请求同样经过 Caddy，所以也会被相信。
- 免费版拿不到回源段，但 EdgeOne 回源时可以加一个自定义请求头。只有 EdgeOne 知道这个值，web 可以凭它分辨请求是否经过 CDN。这样不用升级套餐，也不用改安全组。
- 顺带发现：`docker-compose.yml` 的 web 服务只传了列出来的环境变量，TASK-0583 的 `RATE_LIMIT*`、`CLIENT_IP_HEADER` 都没传进容器，所以即使写进 `.env` 也不会生效。
- Codex 无法统计 `EO-Connecting-IP` 的出现情况，因为 Caddy 没开访问日志。

## 交付内容（做什么）

- `apps/web/request-guard.ts`：
  - `originSecret(env)`：`ORIGIN_SECRET` 至少 32 个字符且不含空白；头名默认 `x-origin-auth`，可用 `ORIGIN_SECRET_HEADER` 改。只保存摘要，用定长比较。
  - `clientAddress`：只有请求带对密钥、并且来自本机代理时才相信 `CLIENT_IP_HEADER`。不带密钥或密钥不对时，按代理看到的连接地址（X-Forwarded-For 最后一项）计数，所以直连者无法伪造，也绕不开限流。
  - `guardLimits`：限流在 `CLIENT_IP_HEADER` 和 `ORIGIN_SECRET` 都设了时开启，或者 `RATE_LIMIT=on`；只设访客地址头不再开启。
  - `ORIGIN_ENFORCE=on`：外部不带密钥的请求回 403，源站只接 CDN；服务器自检（内网地址）照常通过；ACME 验证由 Caddy 自己应答，不经过 web。
  - 只观察模式 `RATE_LIMIT_OBSERVE=on`（Owner 2026-11-08：“你先确认一下，就是不会导致正常其他人读这网站读不了”）：照常计数，但不拒绝任何请求。每小时在日志里记一行 `rate limit observe`，内容是本该拒绝的页面、读取、提交请求各多少，涉及几位访客；只记人数，不记地址。要重点看的情况是很多读者共用一个出口地址，比如同一个办公室，或者手机运营商的共享地址。
  - `OriginTally`：每小时在日志里记一行 `origin check`，分别统计带密钥的、带访客地址头的、外部不带密钥的请求数，部署时用它核对 CDN 设置，不需要访问日志。
- `apps/web/server.ts`：按上面的规则取访客地址；转给 api 的请求去掉密钥头；只设访客地址头、没设密钥时，启动日志提示一次。
- `apps/web/runtime-env.ts`：web 允许读取 `ORIGIN_SECRET`、`ORIGIN_SECRET_HEADER`、`ORIGIN_ENFORCE`。web 不持有凭据的检查对 `ORIGIN_SECRET` 单独放行，并写明理由：它只能证明请求经过 CDN，打不开数据库、模型或任何账号。
- `docker-compose.yml`：web 服务补传 `RATE_LIMIT*`、`CLIENT_IP_HEADER`、`ORIGIN_SECRET*`、`ORIGIN_ENFORCE`，不设时为空，即关闭。
- `.env.example`：写明开启步骤：CDN 规则加回源请求头 → `.env` 设同一个值 → 看 `origin check` 日志 → 再设 `ORIGIN_ENFORCE=on`。

- Codex 审查 #387 指出的两处问题，已修：
  - **头名为空时用默认值：**docker-compose 会把没设的变量传成空字符串，空的 `ORIGIN_SECRET_HEADER` 现在按默认头名处理。之前空值会让密钥失效，密钥头也会被传给 api。不论是否配置了密钥，转给 api 时都会去掉默认密钥头。
  - **TRUST_PROXY=false 时不再放过外部请求：**是否来自外部，看连接地址是不是公网地址，或者有没有代理加上的 X-Forwarded-For（`fromOutside`）。以前在 TRUST_PROXY=false、前面又有 Caddy 时，外部不带密钥的请求会被当成服务器自检放过。

## 测试

`apps/web/tests/request-guard.test.ts`，共 14 项：
- 地址判断：带对密钥才相信访客地址头；没带、带错、没配密钥时按代理看到的地址；直连源站时这个头无效。
- 密钥配置：长度、空白、头名；强制只接 CDN 必须先配了密钥；每小时的统计。
- 只观察模式：按类别统计本该拒绝的请求和访客人数，输出里不含任何地址。
- 真实 web 进程：
  - 带密钥经“CDN”的请求照常限流；
  - 直连的请求和猜错密钥的请求回 403，且带安全头；
  - api 收不到密钥头，看到的是 CDN 给的访客地址；
  - 服务器自检通过。

回归：`cache.test.ts` 39 项；`role-config`、`toolchain`、`process-environment`、`feedback-secret`、`egress-routing` 共 24 项。

## 没做什么

- 云端设置：在 EdgeOne 规则引擎里加“回源时添加请求头”，以及给 Codex 开权限，都等 Owner 选方式。免费版是否支持这条规则，由 Codex 查官方文档确认。
- `.env` 由 Codex 按交接设置，顺序如下：
  1. 先只设密钥，看 `origin check` 日志，确认经过 CDN 的请求都带着密钥；
  2. 再设访客地址头，同时设 `RATE_LIMIT_OBSERVE=on`，只观察几天；
  3. 观察期间本该拒绝的请求一直是 0，或者只来自明显的抓取程序，才去掉观察、正式限流；
  4. 最后设 `ORIGIN_ENFORCE=on`。
- 安全组不改：密钥头已经能做到只接 CDN，不依赖回源地址段。
