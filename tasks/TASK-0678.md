> 计划版（status: specified）：下面是实现 PR 要满足的要求，不是本计划 PR 的交付结果。

## 背景

线上 442 个启用资讯源里 174 个七天没有新稿；补读的 200 篇里 174 篇以“正文不可读”结束。审查发现（C1～C3）：采集把“抓到几条”记在过滤之前，地址规则、噪声过滤、日期窗口把条目全挡掉时这次采集仍记“成功”；一条超出许可范围的链接或一个被拦的详情页会让整次采集失败；正文读取失败从不记原因，补读是对同一页面的原样重试。

## 交付内容（做什么）

1. **漏斗计数**（C1）：每次采集在 `fetch_runs.detail` 记录 抓到 / 地址规则挡掉 / 噪声挡掉 / 日期窗外 / 已知 / 新增 / 无日期 / 超出范围。派生三种状态：连续 3 次“抓到但全被挡”、“只有无日期条目”、“列表长期不变而按节奏应该变”。在信源健康和后台显示，并合并成每天一条按原因分组的提醒。
2. **单条隔离**（C2）：超出许可范围的条目不存、记下主机名，其余照常；详情页被拦的条目保留列表元数据、详情标为待补；只有列表本身失败或全部条目失败才算整次失败。
3. **正文失败分类**（C3）：每次正文读取都记原因：HTTP 状态码、太短（附字数）、非网页、扫描 PDF、被拦（附代码）、网络、阅读服务未配置。只对临时原因（网络、5xx、限速、阅读服务待处理）安排补读；补读拿到的内容和上次完全相同就直接结束，不再重试。后台按“原因 × 信源”汇总。
4. 正文阈值：页面上有明确正文容器时，20 字以上即接受（与入库规则一致），不再统一要求 200 字。
5. 交付后用线上数据把 174 个静默源按原因分类，结果贴看板，修复按原因分给后续卡。

## 不做

- 不改“读不到正文不上线”的规则；不自动停用信源（停用由 Owner 决定）；不加新的抓取方式。

## 测试

- 地址规则挡掉全部条目时，这次采集记为“全被挡”，连续 3 次进提醒。
- 一条超范围链接不影响同列表其他条目入库。
- 404、太短、被拦各自记录原因；只有网络错误安排补读；补读内容相同即结束。
