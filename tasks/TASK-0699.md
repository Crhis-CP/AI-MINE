## 背景（为什么做）

- **付费调用**：`packages/backend/src/providers/usage-protection.ts` 的放行、授权、结算三步，每次付费调用都会在全局锁 `usage-protection`（第 41 行）里统计本月以来的 `receipt_attempts`（第 464-468 行：`WHERE a.origin='live' AND a.started_at>=…`），并查 `min(started_at) … WHERE origin='live'`（第 297 行）。
  现有索引的首列都是服务名（`receipt_attempts_service_time_idx (service, origin, started_at)`、`receipt_attempts_quota_time_idx ((coalesce(quota_service,service)), started_at) WHERE origin='live'`），不带服务条件的按时间查询用不上，只能全表扫描。这张表只增不删，所有模型、向量、Jina 调用都在这把全局锁上排队，每次调用的成本随历史总量增长。
- **归组决定**：`events/group.ts:1215-1240`（每小时）在全局锁 `withdrawal-membership` 里按 `created_at > now() - …` 扫 `grouping_decisions`，这张表只有 `(article_id, id DESC)` 索引。
- **待重读文章**：`jobs/content.ts:762-765` 每 5 分钟按 `processing_state='analyzed' AND processing_error LIKE … AND processing_retry_at <= now()` 扫 `articles`。现有的部分索引 `articles_processing_idx` 只覆盖 `'new'` 和 `'failed'`。

## 交付内容（做什么）

三份新迁移，按仓库惯例写（参考 `database/migrations/0030_*.sql` 的注释：大库先手工 CONCURRENTLY 建好，迁移里用 `IF NOT EXISTS` 变成空操作），并登记到 `database/migration-inventory.json`（`name` 和 `dependsOn` 填各目录里最新的一份）：

1. `database/migrations/ai-gateway/202611131000_receipt_attempts_live_started.sql`
   `CREATE INDEX IF NOT EXISTS receipt_attempts_live_started_idx ON receipt_attempts (started_at) WHERE origin = 'live';`
2. `database/migrations/events/202611131010_grouping_decisions_created.sql`
   `CREATE INDEX IF NOT EXISTS grouping_decisions_created_idx ON grouping_decisions (created_at);`
3. `database/migrations/content/202611131020_articles_analyzed_retry.sql`
   `CREATE INDEX IF NOT EXISTS articles_analyzed_retry_idx ON articles (processing_retry_at, id) WHERE processing_state = 'analyzed' AND processing_error IS NOT NULL;`
4. `usage-protection.ts:297`：`min(started_at)` 查到非空值后存在进程内变量里，之后直接用（最早的一次调用时间不会再变）。查到 `null` 时不缓存。
5. 每份迁移文件头写注释：为哪条查询、在哪个文件第几行、预期改善。

PR 说明里附三条查询在测试库上的 `EXPLAIN`（改动前后），能看到用上了新索引。测试库数据少，规划器仍可能选顺序扫描，这时用 `SET enable_seqscan = off` 演示可用即可。

代码量预算：迁移三份各 3 到 5 行；代码约 10 行；测试约 20 行（最早时间只查一次）。
