## 背景（为什么做）

2026-11-08 生产只读数据：695 条资讯过了初筛、被评分，却一直没有公开。其中 667 条（96%）只有标题：正文不到 20 个字，body_status 为 `unconfirmed`，body_mode 为 `summary`，写作步骤没有写出中文导读，稿件停在 `analyzed`。写作返回空文案的 28 条由 TASK-0594 处理，不在本卡。

## 正文读取路径（代码排查结论，行号按 base_sha）

1. 抓取正文：`packages/backend/src/content/extract.ts:115-163` 的 `extractFromUrl`。网页用 Readability 读，少于 200 字返回空（`extract.ts:46,71`）；PDF 用 `readPdfText`（`extract.ts:131-135`）；网络或解析错误被吞掉，也返回空（`extract.ts:138-145`）。返回空时立刻记成 `unconfirmed` 并照常送去分析（`extract.ts:229-235`），没有重试。
2. 只有抛出的错误才重试：`packages/backend/src/jobs/content.ts:50` 的 `MAX_EXTRACT_FAILURES = 3`，每次间隔 10 分钟（`content.ts:517-531`），三次后同样记成 `unconfirmed`。
3. 分析：正文和摘录里一个字母或数字都没有时，不评分、不写作（`editorial/analyze.ts:362,821,834`，`editorial/writing.ts:148-150`），记成“等材料”。只要有字（哪怕一两个字）就评分；写作步骤要求至少 20 个字（`analyze.ts:754-755`，`lib/original-post-admission.ts:6`），不够就返回 `writer: none`、没有导读，`relevance` 记为 `unknown`（`analyze.ts:874`）。
4. 发布：没有中文导读，`chineseCopy` 为假，可见性固定为 `withdrawn`（`publication/publish.ts:489,508-510`）。
5. 续接：`jobs/content.ts:540-615` 的 `resumeMaterialWaits` 只接 `recordedMaterialWaits`（`enrichment/records.ts:12-26`）里的稿件，条件是“分数为空、没有 writer、回执不超过一张”；而且正文或摘录里有任何字就不接（`content.ts:577-578`）；同一个读取键只试一次（`content.ts:597-601`，读取键见 `content/body-reading-key.ts:6-15`，包含文章版本、链接、信源配置、权限版本和读取服务配置）。所以：
   - 一个字都没有的稿件：读取能力或信源配置变化后最多再试一次，之后永远停在 `analyzed`；
   - 有几个字但不到 20 个字的稿件：已评分、`writer: none`，不在续接范围内，从不重试，也不会被标记失败或撤下。
   这两条判断门槛（任何字 vs 20 个字）不一致，是本问题的代码根源；生产上 667 条各占多少，需要 Codex 跑下面的只读统计确认。
6. PDF 读取 2026-10-26 才加入（提交 8f45a9b）。英文公司官网的公告大多直接链到 PDF；10 月中下旬进来的这类稿件当时读不到正文，之后即使能读，如果已经评过分也不会再读。

只读统计（Codex 在服务器上跑，结果贴协作看板）：

```sql
WITH latest AS (
  SELECT DISTINCT ON (article_id) article_id, input_revision, created_at, output
  FROM analyses ORDER BY article_id, input_revision DESC, id DESC
)
SELECT a.source_id,
  coalesce(a.body_text, '') ~ '[[:alnum:]]' AS has_body_chars,
  coalesce(a.excerpt, '') ~ '[[:alnum:]]' AS has_excerpt_chars,
  l.output->>'writer' AS writer,
  l.output->'scores' = 'null'::jsonb AS scores_null,
  l.created_at < '2026-10-26' AS analysed_before_pdf_reader,
  count(*) AS n
FROM articles a JOIN latest l ON l.article_id = a.id AND l.input_revision = a.revision
WHERE a.processing_state = 'analyzed' AND a.body_status = 'unconfirmed' AND length(coalesce(a.body_text, '')) < 20
GROUP BY 1, 2, 3, 4, 5, 6 ORDER BY n DESC
```

## 交付内容（做什么）

- `readable-dom.ts`：新增 `revealDeclared`，在 Readability 之前，只对信源声明的元素去掉 `hidden` 和行内 `display`/`visibility`；其子元素的隐藏保持不变，不执行页面脚本。
- `extract.ts`、`web-list.ts`（详情页顺带读正文）、`admin/content-presentation.ts`（后台正文展示刷新）：三处正文读取入口都传入 `detail.reveal`，与 `detail.preserve` 一致。
- `config-keys.ts`：`detail.reveal` 为 1–10 个非空选择器，格式不对时在配置预览前拒绝。
- `industry/sources.json`：`fj-housing-news` 增加 `"detail": { "reveal": ["div.tabs_bd > div.word_con"] }`。改信源配置会改变正文读取键，导入生产后，“一个字都没有”的该源稿件可以自动再读一次。
- `packages/backend/README.md`：补充 `detail.reveal` 的说明。

同类排查（举一反三）：模式是“正文在 HTML 里，但被行内样式藏起、等脚本显示”。搜了 `detail?.preserve` 与 `readable(`、`extractFromUrl(` 的全部调用点，三处正文入口一起改。福建其他厅（农业农村、人社、商务、国资委）可能用同一套信息公开模板，本次只连上水利厅，其信息公开页没有这种隐藏，所以只给住建厅加配置；其余待服务器上按同一选择器核对。

## Q 卡片：仍然只有标题的稿件怎么处理（本卡的修复不依赖这个决定）

现状：这些稿件评了分（花了钱），却永远不公开，也不在任何页面上显示为失败。

- A（推荐）：统一门槛并有限重试。正文不到 20 个字就按“等材料”处理，不再评分；读取能力或信源配置变化时自动再读（现有续接），另外每条最多再读 3 次（间隔逐步拉长，例如 1 小时、1 天、3 天）；仍然没有正文的标记为“正文读取失败”，在运行页按信源列出数量和样例，读者端不显示。对已评过分的 667 条，先跑一次补读：现在能读的（PDF 信源、福建住建厅等）进入正常流程，重新分析会产生模型调用，按条数估算后再执行。
- B：只有标题也公开，作为标题卡片（只显示中文标题和原文链接）。读者能看到更多条目，但没有导读、无法判断价值，外文标题需要翻译，和“有导读才公开”的现行规则冲突。
- C：维持现状，只在运行页显示数量。

不回复时的默认做法：维持现状（C），不额外花钱；本卡的配置修复照常上线。
