## 背景（为什么做）

Owner 在“网站访问速度慢”那个线程里先说「现在有个问题，上网站访问速度过慢，请排查原因，并修复。」（2026-10-06 11:09:28Z）；查下来是他所在的海外到上海服务器的国际线路远、丢包，网站本身不慢。他 12:05:07Z 回「选A，但是只要免费哈，同意调 BBR，但是也要确保国内访问速度不变。」（A 是“用 EdgeOne 免费版”），12:33:04Z 回「同意你在 EdgeOne 和火山引擎里按上面这些做」。那个线程 13:17Z 报告做完：

- 境外访客经腾讯 EdgeOne（免费版）回源：主域名与 admin 子域都在 EdgeOne 上，火山引擎只给“全球（不含中国内地）”线路加了指向 EdgeOne 的记录；默认记录一条没动，大陆访客与公安备案核验照旧直连服务器。
- EdgeOne 全站默认不缓存，只有一条规则让 `/assets/*` 按源站的 `Cache-Control` 缓存；HTML、`/admin`、`/api`（含 `/api/admin`、`/api/auth`）与 RSS 一律不在边缘缓存，下架照样即时生效。回源的 Host 是被访问的域名，回源协议跟随访客的协议。
- BBR 试过，大陆多人同时访问时会拖慢一部分人，已改回原样。
- 撤下只需删掉火山引擎里那两条境外线路记录，约 10 分钟恢复直连。

境外访客经 EdgeOne 回源时，Caddy 看到的对端是 EdgeOne 的节点，不是访客。现在 Caddy 对任何对端都把 `X-Forwarded-For` 换成对端地址（`deploy/Caddyfile:3-6` 没有任何可信代理设置）；网站进程在 `TRUST_PROXY=true` 时取这个头的最后一项，否则取连接自己的地址，再作为 `x-forwarded-for` 与 `x-real-ip` 交给 api（`apps/web/server.ts:168-176`）。用到访客地址的只有两处：

- 反馈：按“地址 + 浏览器类型”算来源哈希，每分钟 5 次，封禁也按它（`apps/api/src/routes/feedback.ts:45`，`packages/backend/src/operations/feedback.ts:26-67`）；
- 后台密码登录：每个地址 15 分钟 10 次，另有全站 50 次（`apps/api/src/routes/admin-auth.ts:31-43`、`:93`）。
（`apps/api/src/routes/ingest.ts:38` 也用，但这条路由没有注册。）

所以从 13:17Z 起，境外访客在源站看来只是 EdgeOne 的几个节点地址：反馈的次数与封禁互相牵连，后台登录的次数也共用（Owner 在境外登录后台也走 EdgeOne）。这件事与后台搬不搬（TASK-0079、TASK-0080）无关，先做。

怎么认出“这个请求确实是 EdgeOne 转来的”：常见做法是只信任 CDN 的回源地址段，但 EdgeOne 免费版不提供。“网站访问速度慢”线程 13:36Z 在控制台查过：安全防护里没有“源站防护”，腾讯的免费版说明也写着不支持“源站防护 IP 获取”；公开的节点列表接口当时打不开。免费版的规则引擎有“修改 HTTP 回源请求头”，所以改用一个只有 EdgeOne 和服务器知道的密钥头：EdgeOne 回源时加上 `X-Edge-Origin-Key: <密钥>`，Caddy 只对带着这个头、而且值完全相同的请求，采用 EdgeOne 写的访客地址；别的请求照现在一样按对端处理。访客地址取哪个头，按腾讯文档《默认 HTTP 回源请求头》（https://cloud.tencent.com/document/product/1552/87654）：`EO-Connecting-IP` 是连到边缘节点的地址，也就是访客（访客自己用了代理时是代理的地址）；`X-Forwarded-For` 是在访客自带的值后面追加，最后一项才是真的；`EO-Client-IP` 不是默认头，现在也没配。源站上还没实测过，部署第 4 步核对。

另外，规格还写着“共享缓存层：默认不加”（`07-deployment-and-ops.md` 2.4），要补上这条只给境外、只缓存 `/assets/*` 的边缘，并把 Owner 的选择登记下来。

1. **`deploy/Caddyfile`**（注释照现有写法用英文）：主域名那一段（写卡时是 `{$SITE_DOMAIN}, {$PRIVATE_HOSTNAME} {`；TASK-0080 先合并时只剩主域名，照样只改这一段）改为

   ```
   	encode zstd gzip
   	# EdgeOne adds X-Edge-Origin-Key to its back-to-origin requests; only a request carrying the exact
   	# shared key (EDGE_ORIGIN_SECRET, 32+ characters) may name the visitor, from EO-Connecting-IP.
   	# Without the key every request keeps its direct peer as the visitor, as before.
   	@edge expression `{http.request.header.X-Edge-Origin-Key} == "{$EDGE_ORIGIN_SECRET}" && size("{$EDGE_ORIGIN_SECRET}") >= 32`
   	handle @edge {
   		reverse_proxy web:3000 {
   			header_up X-Forwarded-For {http.request.header.EO-Connecting-IP}
   			header_up -X-Edge-Origin-Key
   		}
   	}
   	handle {
   		reverse_proxy web:3000 {
   			header_up -X-Edge-Origin-Key
   		}
   	}
   ```

   效果：
   - 没配密钥（`EDGE_ORIGIN_SECRET` 为空）时，`size` 那一半永远不成立，所有请求走第二个 `handle`：Caddy 照现在一样把 `X-Forwarded-For` 换成对端地址，行为与改之前相同。
   - 配了密钥时，只有密钥头的值与它完全相同的请求走第一个 `handle`：`X-Forwarded-For` 被换成 `EO-Connecting-IP` 这一个值，网站取最后一项正好是它，网站与 api 都不用改。访客自己伪造的 `X-Forwarded-For` 不起作用。
   - 两路都在转给网站之前去掉密钥头，网站、api 与它们的日志都见不到密钥。
   - 密钥要求至少 32 位，防止误把很短的值当密钥。只用十六进制字符（`0-9a-f`），这样不会弄坏表达式里的引号。

## 输入输出与错误状态

- 输入：服务器 `.env` 的 `EDGE_ORIGIN_SECRET`（不填为空，即关闭）；EdgeOne 回源请求带的 `X-Edge-Origin-Key` 与 `EO-Connecting-IP`。输出：交给网站的 `X-Forwarded-For` 只有一个地址；密钥头不出 Caddy。

## 部署（生产变更，Owner 当时同意后执行；本卡的合并不等于上线）

0. 前提：本卡已合并；Owner 对这一次部署打字同意。请他同意时说清三件事：Caddy 要重启两次，每次中断几秒；他要在 EdgeOne 控制台贴一次密钥（只贴不看，不发到聊天）；第 4 步会往反馈接口发 6 个格式不对的请求做核对，不写入任何东西。与 TASK-0080 一起部署时，第 2 步合成一次重启。
1. 在服务器上只看一行：`grep -E '^TRUST_PROXY=' .env`；不是 `true` 就改成 `true` 并重建 web（现在若是 `false`，网站把 Caddy 容器的地址当成每个访客的地址，所有访客已经在共用反馈与登录的次数，与 CDN 无关）。
2. 换上新的 Caddyfile，先校验：`docker compose --profile https run --rm --no-deps caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile`，要看到 `Valid configuration`；再 `docker compose --profile https up -d --force-recreate caddy`（单文件挂载，要重建容器才换到新文件；中断通常几秒，最长十几秒）。这时还没有密钥，行为与改之前相同。
3. 生成并放好密钥：由 Owner Mac 上的会话在他电脑上本地生成 64 位十六进制（例如 `openssl rand -hex 32`），不显示在屏幕和会话里，经 ssh 写进服务器 `.env` 的 `EDGE_ORIGIN_SECRET`，同时放进 Owner 的剪贴板。再做一次第 2 步的校验与重建（EdgeOne 还没带这个头，行为仍不变）。然后 Owner 自己在 EdgeOne 控制台的规则引擎里加一条规则：两个域名，操作“修改 HTTP 回源请求头”，设置 `X-Edge-Origin-Key`，值粘贴剪贴板里的密钥；规则能只对 HTTPS 请求生效时就只对 HTTPS（`http://` 的请求 Caddy 只做跳转，用不到访客地址，这样密钥不在明文里走）。会话只用文字告诉他点哪里，不看、不截取填了密钥的页面。
4. 读回：
   - 从主机之外分别走大陆直连与境外（经 EdgeOne）打开首页与后台登录页，返回 200。
   - 核对 Caddy 认出的是访客本人、伪造的头没用（不写入任何东西）。先看 `packages/backend/src/operations/feedback.ts` 仍是先限流、后查截图格式（写卡时 :67 限流，:71 查截图格式）；不是就不用这个办法，回到架构 Agent。然后在 Owner 的电脑上（境外）发 6 个请求，都用 `curl -4`、同一个 User-Agent，都是 `POST https://<主域名>/api/site/feedback`，正文都是 `{"content":"部署核对","screenshot":{"mime":"image/bmp","data":"AA=="}}`：
     - 前 5 个直连源站（`--resolve <主域名>:443:<服务器地址>`，地址取自部署记录，不写进仓库），应各返回 400（截图格式不对，什么也不写入）。这 5 次算在 Owner 自己的地址上。
     - 第 6 个走正常解析（经 EdgeOne），多带一个伪造的 `EO-Connecting-IP: 192.0.2.1`，应返回 429（提交太频繁）：说明 Caddy 采用了 EdgeOne 写的访客地址，也就是 Owner 自己的地址，伪造的头没起作用。
     - 第 6 个返回 400，说明 EdgeOne 的规则没生效，或者伪造的头被原样送到了源站：按第 6 步清空密钥退回，回到架构 Agent（改取 `X-Forwarded-For` 最后一项另议）。
   - 结果（只写状态码，不写地址）记进部署记录与本卡交付记录。
5. 证书续期：HTTP-01 经 EdgeOne 已试通（见交付内容第 5 条），本次不做别的；约 2026-12-02 续期窗口打开后看一次 Caddy 日志里两个域名的续期结果，失败时另报。
6. 快速退回：把服务器 `.env` 的 `EDGE_ORIGIN_SECRET` 清空并重建 caddy，就回到现在的行为；EdgeOne 里那条规则可以留着（Caddy 不认、也不转给网站），Owner 方便时删掉。密钥疑似泄露时，照第 3 步换一个新的；换的那几分钟里境外访客的地址暂时退回成节点地址。

## 明确不做

- EdgeOne 本身的其他设置：DNS 境外线路、回源 Host 与协议、缓存规则、证书，都在“网站访问速度慢”那个线程；本卡部署只在规则引擎里加那一条回源请求头，由 Owner 自己贴密钥。撤下 admin 子域在 EdgeOne 上的接入是后台搬家（TASK-0080）以后的 DNS 变更，要 Owner 同意。
- 不按 EdgeOne 的节点地址段放行：免费版没有。
- 不关掉 TLS-ALPN-01 验证：HTTP-01 经 EdgeOne 已试通，Caddy 在 TLS-ALPN-01 失败时会改用它；在配置里写死签发方式会顶掉 Caddy 默认的备用签发机构。续期日志真出问题再另开卡。
- 网站与 api 取访客地址的规则不改；登录限流的全站总闸不改（另开卡）。
- 密钥不自动轮换：疑似泄露时手动换。
- 不删 `Forwarded`、`X-Real-IP` 等其他转发头（06-security 2.2 的其余项另有任务包；网站转发给 api 时自己会覆盖 `x-real-ip`）。
