## 背景（为什么做）

Owner 在“网站访问速度慢”那个线程里先说「现在有个问题，上网站访问速度过慢，请排查原因，并修复。」（2026-10-06 11:09:28Z）；查下来是他所在的海外到上海服务器的国际线路远、丢包，网站本身不慢。他 12:05:07Z 回「选A，但是只要免费哈，同意调 BBR，但是也要确保国内访问速度不变。」（A 是“用 EdgeOne 免费版”），12:33:04Z 回「同意你在 EdgeOne 和火山引擎里按上面这些做」。那个线程 13:17Z 报告做完：

- 境外访客经腾讯 EdgeOne（免费版）回源：主域名与 admin 子域都在 EdgeOne 上，火山引擎只给“全球（不含中国内地）”线路加了指向 EdgeOne 的记录；默认记录一条没动，大陆访客与公安备案核验照旧直连服务器。
- EdgeOne 全站默认不缓存，只有一条规则让 `/assets/*` 按源站的 `Cache-Control` 缓存；HTML、`/admin`、`/api`（含 `/api/admin`、`/api/auth`）与 RSS 一律不在边缘缓存，下架照样即时生效。回源的 Host 是被访问的域名，回源协议跟随访客的协议。
- BBR 试过，大陆多人同时访问时会拖慢一部分人，已改回原样。
- 撤下只需删掉火山引擎里那两条境外线路记录，约 10 分钟恢复直连。

境外访客经 EdgeOne 回源时，Caddy 看到的对端是 EdgeOne 的节点，不是访客。现在 Caddy 对任何对端都把 `X-Forwarded-For` 换成对端地址（`deploy/Caddyfile:3-6` 没有任何可信代理设置）；网站进程在 `TRUST_PROXY=true` 时取这个头的最后一项，否则取连接自己的地址，再作为 `x-forwarded-for` 与 `x-real-ip` 交给 api（`apps/web/server.ts:168-176`）。用到访客地址的只有两处：

- 反馈：按“地址 + 浏览器类型”算来源哈希，每分钟 5 次，封禁也按它（`apps/api/src/routes/feedback.ts:45`，`packages/backend/src/operations/feedback.ts:26-67`）；
- 后台密码登录：每个地址 15 分钟 10 次，另有全站 50 次（`apps/api/src/routes/admin-auth.ts:31-43`、`:93`）。
（`apps/api/src/routes/ingest.ts:38` 也用，但这条路由没有注册。）

所以从 13:17Z 起，境外访客在源站看来只是 EdgeOne 的几个节点地址：反馈的次数与封禁互相牵连，后台登录的次数也共用（Owner 在境外登录后台也走 EdgeOne）。这件事与后台搬不搬（TASK-0079、TASK-0080）无关，先做。

怎么认出“这个请求确实是 EdgeOne 转来的”：常见做法是只信任 CDN 的回源地址段，但 EdgeOne 免费版不提供。“网站访问速度慢”线程 13:36Z 在控制台查过：安全防护里没有“源站防护”，腾讯的免费版说明也写着不支持“源站防护 IP 获取”；公开的节点列表接口当时打不开。免费版的规则引擎有“修改 HTTP 回源请求头”，所以改用一个只有 EdgeOne 和服务器知道的密钥头：EdgeOne 回源时加上 `X-Edge-Origin-Key: <密钥>`，Caddy 只对带着这个头、而且值完全相同的请求，采用 EdgeOne 写的访客地址；别的请求照现在一样按对端处理。访客地址取哪个头，按腾讯文档《默认 HTTP 回源请求头》（https://cloud.tencent.com/document/product/1552/87654）：`EO-Connecting-IP` 是连到边缘节点的地址，也就是访客（访客自己用了代理时是代理的地址）；`X-Forwarded-For` 是在访客自带的值后面追加，最后一项才是真的；`EO-Client-IP` 不是默认头，现在也没配。源站上还没实测过，部署第 4 步核对。

密钥头还要挡在日志外面：上游出错（例如部署时重建网站那几秒的 502、上游超时）时，Caddy 的错误日志会带上整份请求头。第 1 轮审查用离线配置把上游停掉复现过：不加过滤时测试密钥原样出现在日志里。06-security 2.2 的“日志脱敏”一行本来就要求入口删掉敏感值。

另外，规格还写着“共享缓存层：默认不加”（`07-deployment-and-ops.md` 2.4），要补上这条只给境外、只缓存 `/assets/*` 的边缘，并把 Owner 的选择登记下来。

## 交付内容（做什么）

1. **`deploy/Caddyfile`**（注释照现有写法用英文，不写上游项目的名称）：
   - 文件开头那两行注释之后，加一个全局选项块，让 Caddy 写日志时删掉密钥头：

     ```
     # Caddy's error log carries the request headers: never write the CDN's back-to-origin key.
     {
     	log {
     		format filter {
     			request>headers>X-Edge-Origin-Key delete
     		}
     	}
     }
     ```

   - 主域名那一段（写卡时是 `{$SITE_DOMAIN}, {$PRIVATE_HOSTNAME} {`；TASK-0080 先合并时只剩主域名，照样只改这一段）改为

     ```
     	encode zstd gzip
     	# EdgeOne adds X-Edge-Origin-Key to its back-to-origin requests; only a request carrying the exact
     	# shared key (EDGE_ORIGIN_SECRET, 32+ characters) may name the visitor, from EO-Connecting-IP.
     	# Without the key every request keeps its direct peer as the visitor, as before.
     	@edge expression `{http.request.header.X-Edge-Origin-Key} == "{$EDGE_ORIGIN_SECRET}" && size("{$EDGE_ORIGIN_SECRET}") >= 32`
     	handle @edge {
     		reverse_proxy web:3000 {
     			header_up X-Forwarded-For {http.request.header.EO-Connecting-IP}
     			header_up -X-Edge-Origin-Key
     		}
     	}
     	handle {
     		reverse_proxy web:3000 {
     			header_up -X-Edge-Origin-Key
     		}
     	}
     ```

   效果：
   - 没配密钥（`EDGE_ORIGIN_SECRET` 为空）时，`size` 那一半永远不成立，所有请求走第二个 `handle`：Caddy 照现在一样把 `X-Forwarded-For` 换成对端地址，行为与改之前相同。
   - 配了密钥时，只有密钥头的值与它完全相同的请求走第一个 `handle`：`X-Forwarded-For` 被换成 `EO-Connecting-IP` 这一个值，网站取最后一项正好是它，网站与 api 都不用改。访客自己伪造的 `X-Forwarded-For` 不起作用。
   - 两路都在转给网站之前去掉密钥头，网站、api 与它们的日志都见不到密钥。
   - 全局的日志过滤对 Caddy 的默认日志生效（访问日志没开）：错误日志里的请求头没有 `X-Edge-Origin-Key`，日志仍是 JSON，其余照旧。
   - 密钥要求至少 32 位，防止误把很短的值当密钥。只用十六进制字符（`0-9a-f`），这样不会弄坏表达式里的引号。
2. **`deploy/Caddyfile.test`**：已有的全局块（`auto_https off`、`admin off`）里加同样的 `log` 一段；主域名一段同样改，`reverse_proxy {$WEB_UPSTREAM}` 两处各带同样的 `header_up`。计划修改时用 caddy 2.11.4 对两份草稿跑过：不配密钥、配假密钥各 `validate` 一次都有效，`fmt` 没有改动。
3. **`docker-compose.yml`** caddy 的 environment 加一行：`EDGE_ORIGIN_SECRET: ${EDGE_ORIGIN_SECRET:-}`。不填时为空，等于关闭。
4. **`.env.example`**：照文件现有的中文写法，在“选填：其他”里 `TRUST_PROXY` 那几行后面加一项，默认注释掉：“前面加 CDN（例如 EdgeOne 境外线路）时，CDN 与 Caddy 约定的回源密钥：随机十六进制、至少 32 位（例如 64 位），只在服务器 `.env` 与 CDN 控制台各存一份，不进聊天、仓库与日志。CDN 回源时带请求头 `X-Edge-Origin-Key: <密钥>`，只有带对的请求才采用 CDN 给的访客地址（`EO-Connecting-IP`）；不填就是关闭，所有请求按直接连来的地址算” 和一行 `# EDGE_ORIGIN_SECRET=`。`TRUST_PROXY` 的说明（写卡时 :92-93）补一句：用本仓库的 Compose 加 Caddy 部署时，网站只从 Caddy 收请求，生产要设 `true`。

## 输入输出与错误状态

- 输入：服务器 `.env` 的 `EDGE_ORIGIN_SECRET`（不填为空，即关闭）；EdgeOne 回源请求带的 `X-Edge-Origin-Key` 与 `EO-Connecting-IP`。输出：交给网站的 `X-Forwarded-For` 只有一个地址；密钥头不出 Caddy，也不进 Caddy 的日志。
- 密钥里有引号、反引号这类字符会弄坏表达式，Caddy 起不来、整站停，而且校验的报错会把整条表达式连同密钥打印出来，所以只用十六进制，写进 `.env` 后先查格式、再校验（下节第 3 步）。密钥不对或 EdgeOne 没带时，请求按对端处理，不会出错，只是访客地址变回节点地址。
- 数据与事件所有权：不涉及。

## 部署（生产变更，Owner 当时同意后执行；本卡的合并不等于上线）

0. 前提：本卡已合并；Owner 对这一次部署打字同意。请他同意时用平实的话说清四件事：
   - 网站入口要重启两次，每次全站打不开几秒；第 1 步若要改一项网站设置，网站本身还要重启一次，同样几秒。这项设置改成“相信前面的入口转来的访客地址”是安全的：网站的端口只对服务器自己开放（`docker-compose.yml:108-109`），外面的人只能经入口访问。
   - 他要在 EdgeOne 控制台贴一次密钥（只贴不看，不发到聊天），贴完清空剪贴板。
   - 第 4 步会用他的电脑向反馈功能发 6 次测试提交，都会被拒收，不留下任何东西。
   - 与 TASK-0080 一起部署时，两张卡的入口重启合成一次（TASK-0080 部署第 4 步）。
1. 在服务器上只看一行：`grep -E '^TRUST_PROXY=' .env`；不是 `true` 就改成 `true`，再重建 web：`docker compose up -d --no-deps --force-recreate web`（`.env` 里的值只在重建容器时换上）。现在若是 `false`，网站把 Caddy 容器的地址当成每个访客的地址，所有访客已经在共用反馈与登录的次数，与 CDN 无关。
2. 换上新的 Caddyfile，先用线上同一个镜像校验：`docker compose --profile https run --rm --no-deps -e PRIVATE_HOSTNAME=admin.<主域名> caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile`，要看到 `Valid configuration`。`run` 会顶掉 compose 里算私有主机名变量的启动命令（`docker-compose.yml:119-128`），不带 `-e PRIVATE_HOSTNAME` 时，主域名那一段地址里的 `{$PRIVATE_HOSTNAME}` 是空的，校验一定失败（报 `Expected another address but had '{'`）；TASK-0080 上线以前需要带，之后多给无害。再 `docker compose --profile https up -d --force-recreate caddy`：换了文件，运行中的容器仍读旧内容，第 3 步的密钥又只在重建时换上，所以用重建，不用 restart；中断通常几秒，最长十几秒。这时还没有密钥，行为与改之前相同。
3. 生成并放好密钥：由 Owner Mac 上的会话在他电脑上执行下面一条命令。`<主机别名>` 是他 ssh 配置里服务器的别名，`<部署目录>` 取自部署记录；以平时部署登录服务器的同一个用户执行。命令文字里没有服务器地址，密钥不出现在屏幕、会话记录、命令参数、shell 历史和服务器的进程列表里，只经 ssh 的标准输入写进 `.env`，同时放进 Owner 的剪贴板：

   ```
   KEY="$(openssl rand -hex 32)" && printf 'EDGE_ORIGIN_SECRET=%s\n' "$KEY" | ssh <主机别名> 'cd <部署目录> && umask 077 && { grep -v "^EDGE_ORIGIN_SECRET=" .env; cat; } > .env.new && chmod --reference=.env .env.new && mv .env.new .env' && printf '%s' "$KEY" | pbcopy; unset KEY
   ```

   然后只核对格式，不显示值：`ssh <主机别名> 'cd <部署目录> && grep -cE "^EDGE_ORIGIN_SECRET=[0-9a-f]{64}$" .env'` 应输出 `1`。不是 `1` 就不往下做（例如值里混进了引号，下一步的校验报错会把它打印出来），把这一行删掉，重做本步。是 `1` 才再做一次第 2 步的校验与重建（EdgeOne 还没带这个头，行为仍不变）。然后 Owner 自己在 EdgeOne 控制台的规则引擎里加一条规则：两个域名，操作“修改 HTTP 回源请求头”，设置 `X-Edge-Origin-Key`，值粘贴剪贴板里的密钥；规则能只对 HTTPS 请求生效时就只对 HTTPS（`http://` 的请求 Caddy 只做跳转，用不到访客地址，这样密钥不在明文里走）。贴完马上清空剪贴板：会话执行 `pbcopy </dev/null`（苹果设备之间的通用剪贴板会把它同步到手机）。会话只用文字告诉他点哪里，不看、不截取填了密钥的页面。
4. 读回：
   - 从主机之外分别走大陆直连与境外（经 EdgeOne）打开首页与后台登录页，返回 200。
   - 先认出 EdgeOne 的标记头：在 Owner 的电脑上（境外）`curl -sI https://<主域名>/`，看 EdgeOne 加在响应上的是哪个头。腾讯文档写的是 `eo-log-uuid`，线上没实测过；不叫这个，就把下面脚本里的名字换掉。
   - 再看 `packages/backend/src/operations/feedback.ts` 仍是先限流、后查截图格式（写卡时 :67 限流，:71 查截图格式）；不是就不用这个办法，回到架构 Agent。
   - 然后由 Owner Mac 上的会话在他电脑上（境外）一次跑完下面这段。服务器地址从部署记录读进变量，不出现在命令文字和输出里；curl 的错误信息丢弃；每个请求只打印状态码，以及“直连”或“经EdgeOne”：

     ```
     D=aiminingpolicy.com
     ORIGIN_IP="$(cat <部署记录里只存服务器地址的那个文件>)"
     UA='amp-deploy-check/1'
     BODY='{"content":"部署核对","screenshot":{"mime":"image/bmp","data":"AA=="}}'
     check() {
       curl -4 --noproxy '*' -m 20 -s -o /dev/null -D - -A "$UA" -H 'Content-Type: application/json' --data-binary "$BODY" "$@" "https://$D/api/site/feedback" 2>/dev/null |
         tr -d '\r' | awk 'NR==1{s=$2} tolower($1)=="eo-log-uuid:"{e="经EdgeOne"} END{print (s?s:"无响应"), (e?e:"直连")}'
     }
     start=$(date +%s)
     for i in 1 2 3 4 5; do check --resolve "$D:443:$ORIGIN_IP"; done
     check -H 'EO-Connecting-IP: 192.0.2.1'
     echo "用时 $(( $(date +%s) - start )) 秒"; unset ORIGIN_IP
     ```

     前 5 个用 `--resolve` 直连源站，这 5 次算在 Owner 自己的地址上；第 6 个走正常解析（经 EdgeOne），多带一个伪造的 `EO-Connecting-IP`。六个请求的正文、User-Agent、`Content-Type` 都一样：不写 `Content-Type: application/json` 时，接口要么按格式拒掉、要么读不出内容，在限流之前就返回 400（`apps/api/src/routes/feedback.ts:7-41`、`operations/feedback.ts:59`），第 6 个就不会是 429。`-4` 让两条路都用 IPv4，出口地址才一样；`--noproxy '*'` 不走电脑上的代理设置。
   - 判读，只有这一种算通过：前 5 个都是“400 直连”，第 6 个是“429 经EdgeOne”，用时不超过 60 秒。说明 Caddy 采用了 EdgeOne 写的访客地址，也就是 Owner 自己的地址，伪造的头没起作用。
   - 前 5 个都是“400 直连”、第 6 个是“400 经EdgeOne”、用时不超过 60 秒：先确认电脑没开 VPN 或代理（两条路的出口地址要相同），等一分钟（让限流窗口过去）再跑一遍；仍是这样，说明 EdgeOne 的规则没生效，或者伪造的头被原样送到了源站：按第 6 步清空密钥退回，回到架构 Agent（改取 `X-Forwarded-For` 最后一项另议）。
   - 其他任何结果（出现 415、403、5xx 或“无响应”，前 5 个里有“经EdgeOne”，第 6 个是“直连”，用时超过 60 秒）：算没核对成，不退回，也不宣布通过，记下状态码，回到架构 Agent。限流窗口是 60 秒、5 次（`operations/feedback.ts:38-46`），超过 60 秒第 1 个请求就出了窗口。
   - 结果（只写状态码与“直连”“经EdgeOne”，不写地址）记进部署记录与本卡交付记录。
5. 证书续期：HTTP-01 经 EdgeOne 已试通（见交付内容第 5 条），本次不做别的；约 2026-12-02 续期窗口打开后看一次 Caddy 日志里两个域名的续期结果（只看续期那几行，例如 `docker compose --profile https logs caddy | grep -i -E 'certificate|renew|obtain'`），失败时另报。
6. 快速退回：把服务器 `.env` 的 `EDGE_ORIGIN_SECRET` 清空，再 `docker compose --profile https up -d --force-recreate caddy`，就回到现在的行为；EdgeOne 里那条规则可以留着（Caddy 不认、也不转给网站），Owner 方便时删掉。密钥疑似泄露时，照第 3 步换一个新的；换的那几分钟里境外访客的地址暂时退回成节点地址。

- EdgeOne 本身的其他设置：DNS 境外线路、回源 Host 与协议、缓存规则、证书，都在“网站访问速度慢”那个线程；本卡部署只在规则引擎里加那一条回源请求头，由 Owner 自己贴密钥。撤下 admin 子域在 EdgeOne 上的接入是后台搬家（TASK-0080）以后的 DNS 变更，要 Owner 同意。
- 不按 EdgeOne 的节点地址段放行：免费版没有。
- 不关掉 TLS-ALPN-01 验证：HTTP-01 经 EdgeOne 已试通，Caddy 在 TLS-ALPN-01 失败时会改用它；在配置里写死签发方式会顶掉 Caddy 默认的备用签发机构。续期日志真出问题再另开卡。
- 网站与 api 取访客地址的规则不改；登录限流的全站总闸不改（另开卡）。
- 密钥不自动轮换：疑似泄露时手动换。
- 不删 `Forwarded`、`X-Real-IP` 等其他转发头：06-security 2.2“代理身份改写”一行的其余项还没有卡号；网站转发给 api 时自己会覆盖 `x-real-ip`。
- 不开 Caddy 的访问日志。
