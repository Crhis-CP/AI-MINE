## 背景（为什么做）

英文界面（`/en`）的界面文字已经是英文，但资讯卡片和文章页的标题、导读仍是中文：发布时只把分析步骤写的中文标题和中文导读（`analysis.title_zh` / `summary_zh`，在 `publish.ts` 里投影到 `publications.title` / `summary`）放进条目。英文读者打开英文页，看到的主体内容还是中文。

## 交付内容（做什么）

- **单独一步写英文**：每条公开资讯一次小请求，输入是已经发布的中文标题、中文导读和原文标题，不送正文。英文原稿直接用原文标题当英文标题，只写英文摘要。评分与导读的提示词一个字没改，评分版本不变。提示词在 `industry/prompts/english-copy.md`。
- **哪些条目写**：公开、在阅读池里、有中文导读的资讯；原帖（X 帖子）不写，卡片本来就显示原帖本身（`editorial/english-copy-input.ts`）。
- **花钱的规矩照旧**：走“全文翻译”那一路模型（后台“模型”页的同一行，名称改为“全文翻译；英文界面的英文标题与摘要”，用途记为 `english_copy`），同一份额度、回执与用量记账、当前来源许可（与正文翻译同样取材料许可后才发）。同样的输入只付一次费：输入（中文标题、导读、原文标题）算一个哈希，存过就不再请求；回执层对完全相同的请求也会直接复用。
- **排队与时段**：用现有翻译队列 `content.translate`，任务里多一个 `english: true`，键名 `en:<ID>`（精选）和 `en-later:<ID>`（其余），与正文翻译互不合并。精选立即写；其余在 DeepSeek 高峰时段等到非高峰，后台任务只用每小时、每天额度的一半（TASK-0579/0580 同一套判断，领任务时再判断一次）。发布时只给两天内发现的新稿排队，重新发布某个来源不会把它的历史全部排进付费队列。
- **存放与显示**：写好的英文存进新表 `enrichment.english_copies`（按条目和输入哈希）；发布时把与当前中文完全对得上的那一份投影到 `publications.title_en` / `summary_en`。中文导读被人工改过或重新分析后，旧英文立刻不再显示（英文页先显示中文），新的一份排队重写，旧的一份保留。
- **页面**：英文页的资讯卡片（`FeedItem.tsx`，全部动态、精选、搜索、主题、收藏都用它）和文章页的标题、AI 导读、网页标题与描述用英文；没有英文的条目照旧显示中文，并标注 `lang="zh-CN"`。英文原稿不再在英文标题下重复显示同一个原文标题。中文页面不变。
- **接口**：网站接口的卡片和文章详情多一个可选字段 `english: {title, summary}`，没有时不出现，旧响应字节不变。API v1、RSS、MCP、同步出口不带这个字段（机器详情明确去掉）。
- **开关**：`EN_COPY_ENABLED`，默认关闭，仅精确 `true` 开启（`.env.example` 有中文说明）。关闭时不排队、不付费；已经写好的英文照常显示。
- **旧资讯补写**：`scripts/en-copy-backfill.ts`，默认只预演（条数、英文原稿数、发现时间范围、token 估算），不排队、不调模型；`--apply --limit N` 从新到旧最多排 N 条（硬上限 20000），打印下一次用的 `--before`；开关没开时拒绝执行。重跑安全：已显示英文的条目掉出，已排队的不重复排。
- **迁移**：`enrichment/202611081000_english_copies.sql`（新表）、`publication/202611081001_publication_english_copy.sql`（`publications` 加两列，两列同时有或同时空）；已登记到 `database/migration-inventory.json`、权限表 `database/roles/table-grants.json`（worker 读写、后台只读）与数据归属表。
- **契约（追加类）**：`http/public.ts` 新增 `EnglishCopy`，`FeedItemSummary` 加可选 `english`；`site.ts` 的 `ItemDetail` 加可选 `english`；`jobs.ts` 的 `content.translate` 加可选 `english`。已重新生成 `reference/contracts`。按规则契约要单独先合：集成时把三个契约文件和 `reference/contracts` 拆成一个只改契约的 PR 先合并，再合本卡其余文件。

## 费用估算（未调用模型）

按仓库里的数字算，给的是范围和假设，不是上限。

- **每次请求的输入**：系统提示词 477 字，按 `promptTokenEstimate` 约 234 token（每次相同，可命中提供方前缀缓存，下面保守地全按未命中价算）；用户消息是中文标题（25–45 字）、中文导读（按 `summarize-article.md` 要求 80–160 字）和原文标题（60–110 个拉丁字母），约 94–169 token；加对话包装约 10。合计约 **340–415 token**。
- **每次请求的输出**：英文标题不超过 20 词、摘要不超过 70 词，约 **80–135 token**（英文原稿只写摘要，约 105 以内）。
- **价格**：仓库记录的 DeepSeek 报价快照为每百万 token 输入 2 元、输出 8 元（`docs/research/optimization-plan-20261022/README.md`），非高峰半价（`providers/peak-hours.ts`）。生产实际登记价格未核实。
- **每条**：高峰价约 0.0013–0.0019 元，非高峰价约 0.00065–0.00095 元。
- **每天**（假设工作日 700–900 条、周末 200–370 条，全部写一次）：工作日约 **0.46–1.7 元**（下限是全部非高峰、短文案；上限是全部高峰价、长文案。实际多数非精选在高峰时段会等到非高峰，靠近下段）；周末全天非高峰，约 **0.13–0.35 元**。另有少量输出不合格的重试（同一请求最多再付两次），估计不超过几个百分点。和 Owner 同意的每天 0.5–2 元相符。
- **请求次数**：每天多 200–900 次。仓库默认 DeepSeek 额度是每小时 2000、每天 20000 次（`0022_receipt_attempts_budgets.sql`；生产实际值未核实），约占日额度 1–5%。非高峰开始的那一小时，上午攒下的非精选会一起开始，约一两百次，低于后台任务可用的一半额度。
- **旧资讯补写**：一次性，每 1000 条约 0.65–0.95 元（非高峰）。总条数未知，以服务器上预演的结果为准。补写和正文翻译共用后台那一半额度，建议每批 `--limit 2000`。
- **未知项**：生产登记价格与缓存命中价、真实中文导读长度分布、每天公开条数的实际值、输出不合格的比例。

## 没做什么

- 报告（日报、周报、月报）、热点榜、事件页、阅读组里“其他来源”列表、分享海报和 OG 图片里的资讯标题，英文页仍是中文：它们来自各自的数据（报告引用、事件标题等），不经过条目卡片。是否也要英文由 Owner 决定，另开卡。
- 原帖（X 帖子）不写英文。
- 后台人工直接填写英文标题、摘要的入口没有做；人工改中文后英文会自动重写。
- 英文页的 canonical 和 sitemap 语言互指等 SEO 由 TASK-0590 负责，本卡只换标题和描述文字。
- 提示词以后改了措辞，不会让已有英文全部重写（避免整批重付费）；需要重写时另开卡。
- `admin/runs.ts` 对“结果未知”回执的自动放行和重排只认原有几个用途，`english_copy` 的未知回执不会自动重排，等下一次发布或补写脚本再排。
- 读者更新日志：开关默认关闭、读者暂时看不到变化，只附运营片段，不改公开发布说明；Owner 开启后再按《读者更新日志标准》写一条读者片段。
- 改版区说明：`FeedItem.tsx` 和 `item.tsx` 在改版区内，只改了标题、摘要取值和 `lang` 标注，需在协作看板 #348 记一笔，集成分支吸收。
- 同类问题（举一反三）：模式是“英文页显示的资讯文字是否来自条目本身的标题和导读”。搜索方式：`grep -rn "item.title\|item.summary\|\.title}" apps/web/app`。条目卡片与文章页已改；上面第一条列出的几处数据来源不同，有意不改。
