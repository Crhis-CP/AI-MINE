## 背景（为什么做）

`packages/backend/src/events/group.ts` 的每小时重新合并（`events.remerge`）把最近 72 小时每条“只有一篇报道的事实”和 14 天窗口里的每篇报道两两比较。没有向量的那一对走 `lexicalSimilarity`（`packages/backend/src/events/relate.ts`），它每次调用都把两边文本重新拆成字符二元组、各建一个 Set。同一篇文本在一轮里会被重复拆几百到几千次，而且整个双重循环是同步的，会占住 worker 的事件循环，期间心跳和其他队列都得等。

## 交付内容（做什么）

1. `relate.ts`：
   - 导出 `export function bigrams(text: string): Set<string>`，内容就是现在 `lexicalSimilarity` 里的 `grams`。
   - 导出 `export function bigramSimilarity(g: Set<string>, h: Set<string>): number`，内容是现在的求交集和相除。
   - `lexicalSimilarity(a, b)` 改为 `bigramSimilarity(bigrams(a), bigrams(b))`，对外行为不变。
2. `group.ts` 的重新合并（`const similarity = (x, y) => …` 那一段）：
   - 建一个本轮内的 `Map<string, Set<string>>`，按文章 ID 懒计算二元组；没有向量时用 `bigramSimilarity` 比较两边缓存好的集合。
   - 两层循环里每比较 2000 对，`await new Promise((r) => setImmediate(r))` 让出一次。外层函数已经是 async。
3. 举一反三：`group.ts` 里其余调用 `lexicalSimilarity` 的地方（第 443、491、551、786 行附近）如果也在循环里对同一段文本反复计算，同样改成先算一次集合；只算一次的不动。PR 里逐处写明改或不改。
4. 测试：
   - `tests/relate.test.ts`：对 20 组文本（含空串、单字、中英混排、带空白），`bigramSimilarity(bigrams(a), bigrams(b))` 与改动前的 `lexicalSimilarity(a, b)` 完全相等。
   - 重新合并的现有测试结果不变。

代码量预算：实现约 30 行；测试约 30 行。
