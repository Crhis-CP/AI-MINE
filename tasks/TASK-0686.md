## 背景（为什么做）

反馈是公开接口（`POST /api/site/feedback`）。代码现状：

- `packages/backend/src/operations/feedback.ts:81-118`：截图的解码和重新编码（`feedbackImage()`，sharp，最大 6000 万像素，动图会解所有帧）和写文件都放在 `sql.begin` 事务里，事务开头还拿了两把 advisory 锁。处理一张大图的这几秒里，一直占着一条数据库连接。
- 连接池默认 10 条（`packages/backend/src/process-config.ts:134`），用单一 `DATABASE_URL` 时主查询、登录、反馈共用这一个池。反馈占满连接池时，读者页、登录和健康检查都会一起卡住。
- 限额的来源键是“IP + 浏览器标识里匹配到的前四个词”（`feedback.ts:34-37`），换个浏览器标识写法就是新的限额；IPv6 按单个地址计。
- 没有全站总量上限，截图会一直写到数据目录。

## 交付内容（做什么）

1. **网络地址归并**：新增 `packages/backend/src/lib/client-network.ts`，导出
   `export function clientNetwork(ip: string): string`。IPv4 原样返回；IPv6 返回前 64 位（例如 `2001:db8:1:2::/64`）；IPv4 映射的 IPv6（`::ffff:1.2.3.4`）按 IPv4 处理；无法解析的原样返回。配 `tests/client-network.test.ts`。
2. **来源键只看网络地址**：`feedbackSourceHash(ip, userAgent)` 改为只用 `clientNetwork(ip)` 算 HMAC，去掉浏览器标识部分。签名可以保留第二个参数但不再使用，或者同步改调用方。已存的旧来源键会自然过期（限额按小时滚动），不做迁移。
3. **截图在事务外处理，进程内只允许一个在做**：
   - 在 `submitFeedback` 进入 `sql.begin` 之前调用 `feedbackImage()`，拿到处理好的字节再进事务。事务里不再调用 sharp。
   - 用一个进程内的单槽信号量包住 `feedbackImage()`：拿不到槽时最多等 3 秒，还拿不到就返回 503，错误码 `busy`，带 `Retry-After: 10`，文案“提交的人有点多，请稍后再试。”
   - 进事务前先做一次只读的封禁和限额预检（不加锁、不占名额）：已被封禁或已超额的请求直接拒绝，不再处理图片。事务里仍按现有逻辑正式占名额。
4. **动图只取第一帧**：`packages/backend/src/operations/feedback-validation.ts:51` 的 `animated: true` 改为 `false`，并删掉第 57 行按帧数乘的像素计算里的 `pages`（只算第一帧）。输出格式保持原样。
5. **全站每小时总上限**：在事务里统计最近一小时 `feedback` 表新增的行数，达到 60 条后拒绝新提交，返回 429，错误码 `rate_limited`，文案沿用“暂时无法提交反馈。”；同一小时内第一次触发时写一条现有告警（用 `operations/alerts` 或反馈模块已有的通知方式，不新建通道）。
6. **路由**：`apps/api/src/routes/feedback.ts:45` 的来源 IP 改为只用 `req.ip`，不读请求头 `x-real-ip`。`req.ip` 已按 `trustProxy` 从 web 转发的头里取得（web 是唯一入口）。如果改完测试显示 `req.ip` 拿不到真实来源，就保留原写法，在 PR 里说明。

代码量预算：实现约 120 行；测试约 120 行，覆盖：并发两个带图提交时第二个在 3 秒后得到 503；预检拒绝时不调用 `feedbackImage`；同一 /64 下不同 IPv6 共用限额；第 61 条提交被拒；动图只保留一帧。
