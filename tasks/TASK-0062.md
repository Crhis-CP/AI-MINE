## 背景（为什么做）

结论：运行提醒（即时告警、每日摘要、周一信源周报、worker 看门狗）的代码在 main 上都在，发送方式就是 Owner 2026-10-06 02:15:27Z 选的“自建应用”（卡片选项原文：“照〔上游〕原样不改代码；你要在飞书开放平台建应用、开权限、发布，多几步。”）。服务器上填好应用凭据、打开开关、填上群号就能发；但现在没有办法在部署时确认“接通了”：群号要自己去飞书里找，填错了或机器人没进群，发送时才失败，开关开着却没填群号时什么也不说（`packages/backend/src/notify/feishu.ts:109-110`）。本卡加一个只读检查脚本，部署时一条命令看清楚设置对不对、机器人在哪些群里、群号是多少，需要时发一条测试消息。

Owner 在飞书里要做的事（建自建应用、开权限、发布、建群、把机器人拉进群）另有一页操作说明，本卡不重复。

## 交付内容（做什么）

1. `notify/feishu.ts` 新增两个导出：
   - `listBotChats()`：用已有的 `tenantToken()`（:12-29）取令牌，调飞书“列出机器人所在的群”接口（`GET /im/v1/chats`，按 `page_token` 翻页，最多翻 20 页），返回 `{ chatId, name }[]`。飞书返回非 0 的 `code` 时抛错，错误里只带飞书的 `code` 与 `msg`。接口路径、参数与所需权限以飞书开放平台文档为准，实现时核对一次，测试只用桩。
   - `feishuSettingsSummary()`：开关照 `feishuInternalEnabled()`（:10）只看进程环境里的 `FEISHU_INTERNAL_ENABLED`；`FEISHU_APP_ID`、`FEISHU_APP_SECRET`、`FEISHU_ALERT_CHAT_ID`、`FEISHU_INTERNAL_CHAT_ID` 与发送时一样经 `credential()` 读。返回开关原样的值是不是 `"true"`、应用两项各填了没有（只返回是否填了，不返回值）、两个群号（群号不是密钥）、提醒实际会发到哪个群（照 :109 的规则：提醒群号，没填时用反馈群号）。
2. `notify/deliver.ts` 加一行再导出：`feishuInternalEnabled`、`feishuSettingsSummary`、`listBotChats`、`sendAlert`。
3. 新脚本 `scripts/feishu-check.ts`：导出 `main(argv, print)`，返回退出码；直接运行时用 `console.log` 打印并以返回的退出码退出。只引用 `@amp/backend/notify/deliver` 与 `node:` 模块，不连数据库。用法（部署会话在服务器上跑，属于部署步骤）：`docker compose run --rm --no-deps worker node scripts/feishu-check.ts [--send]`。逐项用白话打印：
   - 提醒开关：写的是 `true` 就是开着；写了别的（例如 `1`）说明“开关只认 true，现在等于关着”。
   - 应用凭据：App ID、App Secret 各写“已填”或“没填”。缺任何一项，说明“先经安全录入填好”，退出码非 0，不发任何请求。
   - 取令牌：失败时说明“飞书没有接受这对应用凭据”并带上飞书的说明，退出码非 0。
   - 列群：失败（多半是没开“获取群组信息”权限或应用还没发布）时用一句白话说明，退出码非 0；成功时逐个打印“群名（群号）”；一个群也没有时说明“先把机器人拉进提醒群”，退出码非 0。
   - 提醒群：没填任何群号时说明提醒发不出去；填了但不在机器人所在的群里时说明“先把机器人拉进群，或改正群号”，退出码非 0。只填了反馈群号时，说明提醒会发到反馈群。
   - 反馈群：没填时说明“不转发读者反馈”（这是 Owner 确认隐私说明之前的正常状态，不算失败）；填了但机器人不在群里，退出码非 0。
   - 两个群号相同时，提示“提醒群和反馈群是同一个群；反馈里有读者的联系方式和截图，建议分开”，只提示，不算失败（分不分开由 Owner 设群号时定）。
   - `--send`：开关是 `true` 且有提醒群时，用 `sendAlert` 发一条标题为“【测试】运行提醒已接通”的消息（正文一句“这是接通检查发的测试消息，不用处理。”），打印“已发到提醒群，请在飞书里看一眼”；开关没开或没有提醒群时什么也不发，说明原因，退出码非 0。
   - 不认识的参数：打印用法，退出码非 0。
   - 任何时候都不打印 App Secret、tenant token 或请求头。
4. `.env.example` 只改注释（:67-77）：:68 的后台页面名（“设置”里的“推送目标”）改为“用量与模型密钥”里的“通知与请求频率”；:72 拆成两行，告警那行改为“运行提醒（告警、每日摘要、周报）发到飞书群，需要一个飞书自建应用；开关只认 true；群号用 `node scripts/feishu-check.ts` 列出来”，反馈那半句“读者反馈只留在本站，不转发”原样单独成行，留给 TASK-0065；:77（`FEISHU_ALERT_CHAT_ID`）上面加一行“提醒群号；没填时提醒改发上面的反馈群号（FEISHU_INTERNAL_CHAT_ID）”。
5. 测试 `tests/feishu-check.test.ts`：桩 `globalThis.fetch`，只放行 `open.feishu.cn` 的取令牌（`POST /open-apis/auth/v3/tenant_access_token/internal`）、列群（`GET /open-apis/im/v1/chats`）、发消息（`POST /open-apis/im/v1/messages`）三个接口，其余任何请求都让用例失败。环境变量用假值（如 `test-app`、`test-secret`、`oc_alert_test`、`oc_feedback_test`，写法照 `tests/feedback.test.ts:20-23`）。用例：
   - 设置齐全：退出码 0，列出两页共 3 个群；输出里没有假的 App Secret 和假令牌。
   - 开关写成 `1`：说明只认 true。
   - 缺 App Secret：退出码非 0，没有发出任何请求。
   - 取令牌被拒（`code` 非 0）、列群被拒（没权限）：退出码非 0，各一句白话。
   - 提醒群号不在列表里：退出码非 0。
   - 两个群号相同：只提示，退出码 0。
   - `--send`：正好一个发消息请求，发到提醒群，正文含“【测试】运行提醒已接通”；开关关着时没有发消息请求，退出码非 0。
   - 注意 `feishu.ts` 的令牌缓存（:12-29）在同一个进程里跨用例保留，“取令牌被拒”的用例要排在拿到令牌的用例之前，或用别的办法避开缓存，不为测试改缓存的行为。

## 输入输出与错误状态

- 输入：服务器设置（开关只看进程环境；其余四项经 `credential()`：先读进程环境，没有再读凭据目录里的 `integrations.env`，`packages/backend/src/config.ts:84-98`）与命令行参数 `--send`。输出：白话的检查结果与退出码（全部通过为 0，否则非 0）。
- 错误：飞书超时或返回非 0 的 `code` 都算失败，打印飞书的说明（不含凭据）；脚本可以重复跑，只读，`--send` 每跑一次发一条。
- 数据：不读写数据库，不写 settings，不写运行记录。
