## 背景（为什么做）

- 首页、全部动态、话题页、国家页每次打开都把全部符合条件的条目读出来，再在程序里分组、排序，最后只切一页（`report-group-reading.ts:54-88`、`:94-149`，`groups.ts:473-502`）。来源筛选的统计 `loadPoolSourceFacets`（`pool.ts:313-337`）每次也要全量 GROUP BY。读者页都是 `no-store`，没有任何缓存。现在约 7 千条，一年后约 7 万多条，每次打开的成本随之线性增长。
- RSS `/feed/all.xml`（`feeds.ts:225-246`，响应头 `s-maxage=0`）每个订阅器每次拉取都重新计算。
- 站点地图（`sitemap.ts:27-103`）每请求一个分页文件就重建全部条目，其中法规报告是逐条调用 `policyReport()`。这段在 TASK-0696 里已经搬到法规扩展，本卡在新位置上改。

## 交付内容（做什么）

1. 新增 `packages/backend/src/lib/version-cache.ts`：
   ```ts
   export function versionCache<K extends string, V>(opts: { ttlMs: number; max: number }): { get(key: K, version: string, load: () => Promise<V>): Promise<V> };
   ```
   - 同一个 key 在途时并发请求共用一次计算；
   - 版本变了就重新计算；
   - 超过 `max` 时淘汰最早插入的一项。

   配 `tests/version-cache.test.ts`。
2. 版本取 `contentVersion()`（`publication/availability.ts:32`）返回的 `version` 和 `withdrawalVersion` 拼接。撤稿会改变 `withdrawalVersion`，缓存随即失效。
3. 套用到这些地方：
   - `report-group-reading.ts` 里分组前的整组计算（`plans()` 或等价的函数）：30 秒，最多 200 项。缓存键 = 绑定参数的完整序列化（窗口、话题、国家、筛选、语言、页码以外的所有条件），页码在缓存结果上切。
   - `pool.ts` 的 `loadPoolSourceFacets`：60 秒，最多 200 项，同样的缓存键规则。
   - `feeds.ts` 生成整份 RSS 的函数：120 秒，最多 50 项。
   - 站点地图条目的整体构建：120 秒，最多 10 项。
4. 站点地图的法规报告：改为一条 SQL 取出全部“当前有内容的报告”（`item_count > 0` 的判断放进查询），去掉逐条调用 `policyReport()`。代码在法规扩展的 `sitemap.entries` 钩子里。如果这一步要改 `modules/policy`，就在 PR 说明，审计方补路径。
5. 测试：同一版本内重复请求只计算一次；撤稿版本变化后立即重新计算；不同国家、话题、筛选不会互相命中缓存；并发 10 个同样的请求只算一次。

代码量预算：实现约 90 行；测试约 90 行。
