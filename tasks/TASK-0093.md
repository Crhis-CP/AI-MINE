## 背景（为什么做）

结论：法规政策动态要和资讯线隔离运行——法规文书不过资讯的预筛和评分，不进“全部矿业动态”和精选，暂停或调整新闻也不影响法规（ADR-0016 第 3、5 条，F-POL-08）。上游没有第二条业务线；这张卡照上游的采集与材料库原样复用（信源、采集器、去重、修订、来源日期都不变），只在信源上标明属于哪条线，并让资讯线的几个环节只处理资讯信源的材料。

现在 `sources` 没有业务线字段（`database/migrations/0001_core.sql:10-36`），采到的材料一律进资讯处理：`store()` 对新材料排 `queueProcessing`（`packages/backend/src/sources/collect.ts:124`），兜底的 `sweepUnprocessed` 会把所有 `processing_state = 'new'` 的材料再排一次（`packages/backend/src/jobs/content.ts:284-288`）。法规信源一旦建起来，它的材料就会被当成新闻去预筛、评分。

## 交付内容（做什么）

1. 迁移 `database/migrations/sources/<时间戳>_source_lane.sql`：`ALTER TABLE sources ADD COLUMN lane text NOT NULL DEFAULT 'news' CHECK (lane IN ('news', 'policy'))`；现有 22 个信源都是 `news`。`database/migration-inventory.json` 照 metal_prices 的先例登记。
2. `sources/types.ts`：`SourceRow` 加 `lane: "news" | "policy"`。后台“修改信源”的可改字段（`admin/sources.ts` 的 `EDITABLE`）不加 `lane`：业务线建信源时定下，之后不改。
3. `sources/collect.ts`：
   - `requireDateCollection` 的许可判定用信源自己的 `lane`，不再写死 `"news"`（:67）。
   - `store()` 收到 `lane`：元数据变化时法规信源不排 `publication.republish-source`（:126，资讯线的重新发布）。新材料照旧调 `queueProcessing`（:124），由它统一拦下（见第 4 项）。材料本身照旧经 `upsertMaterial` 存进材料库，去重、修订、来源日期证据都不变。
   - `adaptIntervals`（:296-315）只调资讯信源；法规信源的采集间隔照建信源时写的值，不按资讯的条数调快调慢。
4. `jobs/content.ts`：
   - `queueProcessing`（:87-114，“把材料交给处理的唯一入口”）：`route()` 已经联表读信源，多取 `lane`；不是资讯线就返回 `null`，不排任何资讯任务（在“语言未识别”的判断之前，法规材料不会被资讯规则标成失败）。
   - `sweepUnprocessed`（:282-291）与 `requeueFailed`（:300-308）排除法规信源的材料（经 `sourceIdsOnLane("policy")`），法规材料积压时也不会占满兜底重排的 500 条。
5. `events/hot.ts`：`sourceClocks`（:40-44）只数资讯信源，法规信源慢了不影响热度证据是否完整的判断。
6. 测试 `tests/source-lanes.test.ts`（合成信源与材料，不连外网）：
   - 一个 `lane = 'policy'` 的信源采到两条材料：材料存进了，但 `content.analyze`、`content.extract-body`、`events.group` 队列里没有它们的任务，`publications` 没有它们的行；跑一遍 `sweepUnprocessed` 仍然不排。
   - 同样的材料来自 `lane = 'news'` 的信源：照旧排进处理（与现有行为一致）。
   - `requeueFailed` 只把资讯信源的失败材料放回队列。
   - `sourceClocks` 不含法规信源；`adaptIntervals` 不改法规信源的间隔。
   - 迁移后已有信源都是 `news`；`lane` 只能是两个值之一。
