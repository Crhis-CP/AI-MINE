## 背景（为什么做）

结论：法规政策动态要和资讯线隔离运行——法规文书不过资讯的预筛和评分，不进“全部矿业动态”和精选，暂停或调整新闻也不影响法规（ADR-0016 第 3、5 条，F-POL-08）。上游没有第二条业务线；这张卡照上游的采集与材料库原样复用（信源、采集器、去重、修订、来源日期都不变），只在信源上标明属于哪条线，并让资讯线的几个环节只处理资讯信源的材料。

现在 `sources` 没有业务线字段（`database/migrations/0001_core.sql:10-36`），采到的材料一律进资讯处理：`store()` 对新材料排 `queueProcessing`（`packages/backend/src/sources/collect.ts:124`），兜底的 `sweepUnprocessed` 会把所有 `processing_state = 'new'` 的材料再排一次（`packages/backend/src/jobs/content.ts:284-288`），运行告警按 `processing_state = 'new'` 且等了 2 小时的条数推“新内容卡住了”（`packages/backend/src/operations/alerts.ts:55-78`）。法规信源一旦建起来，它的材料就会被当成新闻去预筛、评分；要是只拦住处理、让它停在 `new`，又会每小时误报一次“新内容卡住了”。

所以法规材料在交给处理的唯一入口（`queueProcessing`）就照“非编辑信源”的现成写法（`settleNonEditorial`，`jobs/content.ts:125-134`）标成 `skipped`：兜底重排只找 `new`、失败重排只找 `failed`、积压告警只数 `new` 和 `failed`，都自然不再碰它，不用在每处加筛选；发布规则本来就把 `skipped` 的材料挡在外面（`publication/publish.ts:216-219`），万一有人对它调了发布也不会公开。法规线自己处理到哪一步，记在法规线自己的表里（TASK-0096 起），不靠 `processing_state`。

技术取舍（DEC-66）：上游 AIHOT 一条 `sources` 行就是一个采集入口（配置、游标、启停、健康都在行上），没有 acquisition_profile 这一层；本卡照上游在信源行上加 `lane`，不建第二张表。功能上不需要复制信源：同一个官方入口两条线都要时，按 ADR-0016 第 3 条，材料仍从资讯线采集，交法规线做确定性文书识别，命中才进法规线，不靠建第二条信源（`createSource` 按规范化网址判重，`admin/sources.ts:184-196`，复制信源本来也会被挡住，且许可会被拆成两份）。按业务线暂停不受影响：`lane` 在信源行上，“暂停法规线”就是按 `lane` 批量暂停，没有站点级单开关（铁律 8）。与此不一致的三处规格——`docs/01-product/09-glossary.md` 的 ENT-56 行、`docs/02-rules/02-core-flows.md:123`、`docs/01-product/04-private-operations.md:391` 的 OP-04 第 2 项——写的按业务线分版本、分预览、分启停暂不实现；规格回写另开一张规格卡（作者卡段，TASK-0112），本卡不改 docs。

## 交付内容（做什么）

1. 迁移 `database/migrations/sources/<时间戳>_source_lane.sql`：`ALTER TABLE sources ADD COLUMN lane text NOT NULL DEFAULT 'news' CHECK (lane IN ('news', 'policy'))`；现有 22 个信源都是 `news`。`database/migration-inventory.json` 照 metal_prices 的先例登记。
2. `sources/types.ts`：`SourceRow` 加 `lane: "news" | "policy"`。后台“修改信源”的可改字段（`admin/sources.ts` 的 `EDITABLE`）不加 `lane`：业务线建信源时定下，之后不改。`readSourceDateContext`（:258，采集读信源用它）多取 `lane`。
3. `sources/collect.ts`：
   - `requireDateCollection` 的许可判定用信源自己的 `lane`，不再写死 `"news"`（:67）。
   - `store()` 收到 `lane`：元数据变化时法规信源不排 `publication.republish-source`（:126，资讯线的重新发布）。新材料与修订照旧调 `queueProcessing`（:124），由它统一处理（见第 4 项）。材料本身照旧经 `upsertMaterial` 存进材料库，去重、修订、来源日期证据都不变。
   - `adaptIntervals`（:296-315）只调资讯信源；法规信源的采集间隔照建信源时写的值，不按资讯的条数调快调慢。
4. `jobs/content.ts` 的 `queueProcessing`（:87-114，“把材料交给处理的唯一入口”）：`route()` 已经联表读信源，多取 `lane`；不是资讯线的，照 `settleNonEditorial` 的写法把材料标成 `skipped`（`processing_attempts = 0`，`processing_retry_at`、`processing_queued_at` 清空），不调发布、不排任何资讯任务，返回 `null`。这一步排在“语言未识别”的判断之前，法规材料不会被资讯规则标成失败。`sweepUnprocessed`、`requeueFailed` 不用改。
5. `events/hot.ts`：`sourceClocks`（:40-44）只数资讯信源，法规信源慢了不影响热度证据是否完整的判断。
6. `site/stats.ts`：关于页的“N 个信源”与按类型的分类（:22-31）只数资讯信源；法规栏目上线（TASK-0099）时再决定怎么显示法规信源。
6b. `operations/alerts.ts`：“网站停止收录新内容”（:39-40）只看资讯信源的材料与启用的资讯信源；否则法规信源一直有新文书进来，资讯线停采也不会告警（INV-42）。法规线自己的新鲜度告警归后续法规卡。
7. 测试 `tests/source-lanes.test.ts`（合成信源与材料，不连外网）：
   - 一个 `lane = 'policy'` 的信源采到两条材料：材料存进了、状态是 `skipped`，`content.analyze`、`content.extract-body`、`events.group` 队列里没有它们的任务，`publications` 没有它们的行；把它们的创建时间往前拨 10 分钟再跑 `sweepUnprocessed`，仍然不排。
   - 同样的材料来自 `lane = 'news'` 的信源：照旧排进处理（与现有行为一致）。
   - 一个法规信源采到 20 条材料、发现时间拨到 3 小时前：`collectFindings()` 里没有 `content.process`（“新内容卡住了”）；20 条同样的资讯材料停在 `new`：照旧告警。
   - 资讯信源 7 小时没有新材料、法规信源刚采到文书：照旧推 `content.collect`（“网站停止收录新内容”）。
   - 建一个启用的法规信源后，关于页的 `sources` 与 `sourceKinds` 不变。
   - `sourceClocks` 不含法规信源；`adaptIntervals` 不改法规信源的间隔。
   - 迁移后已有信源都是 `news`；`lane` 只能是两个值之一。
