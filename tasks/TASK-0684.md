## 背景（为什么做）

生产是一台 4 核 4G 的主机（`docs/04-architecture/07-deployment-and-ops.md` 第 3 行）。编排里：

- **没有日志轮转**：所有服务都用 Docker 默认的 json-file 日志，不限大小，日志会一直涨到磁盘满。发布工具已经要专门管磁盘空间（发布空间门槛 7.5 GiB）。
- **只有 db 有健康检查**（`docker-compose.yml:35-39`）。`web` 只等 `api` 进程启动（`condition: service_started`，第 108-110 行），不等它能服务；api 卡死时 `docker ps` 也看不出来。

## 交付内容（做什么）

1. 顶部加一个日志锚点，并用到所有服务（db、setup、api、worker、web、caddy）：
   ```yaml
   x-logging: &logging
     driver: json-file
     options: { max-size: "20m", max-file: "5" }
   ```
   每个服务 `logging: *logging`；`x-app` 锚点里加一次即可覆盖 setup、api、worker。
2. api 健康检查（用镜像里已有的 node，不装 curl）：
   ```yaml
   healthcheck:
     test: ["CMD", "node", "-e", "fetch('http://127.0.0.1:3001/api/health').then(r=>process.exit(r.ok?0:1),()=>process.exit(1))"]
     interval: 30s
     timeout: 5s
     retries: 3
     start_period: 30s
   ```
   `/api/health` 由 `apps/api/src/app.ts:137` 提供，会查一次数据库。
3. web 健康检查：同样写法，打 web 自己的 3000 端口。地址要满足：只读、不进访问统计、不触发整页渲染。优先用 web 自己直接返回的静态地址，例如 `/robots.txt`；请求要带公开站点的 Host（取 `SITE_URL` 的主机名），否则会被入站 Host 检查拦下。PR 里写明选了哪个地址、为什么。
4. `web` 的 `depends_on.api.condition` 从 `service_started` 改为 `service_healthy`。
5. `Dockerfile` 不加 HEALTHCHECK：同一镜像要跑 setup、api、worker、web 四种角色，健康检查放在编排里按服务写。

代码量预算：编排约 30 行。

## 明确不做

- **不加内存上限**：先由查询线回报各容器的实际峰值（见 #495 的查询请求），再按峰值的 1.5 倍另开卡。不按设计文档里的估算值直接设，设低了会被系统杀进程。
- 不给 worker 加健康检查（它没有 HTTP 端口；发布脚本的就绪检查在 TASK-0685）。
- 说明：Docker 不会自动重启“不健康”的容器（`restart: unless-stopped` 只管退出的进程），健康检查的作用是启动顺序、发布判断和排查时看得见。
