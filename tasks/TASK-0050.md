## 背景（为什么做）

2026-10-06 约 01:20Z，公告 GHSA-68fv-2mgg-jv7q（source-map-js 1.2.1，高危）让 `make verify` 的 audit 阶段在所有 PR 上失败，和这些 PR 的改动无关。当时借用 TASK-0002 的允许路径发了只改锁文件的 #167（合并为 `ded1f2d`），在 TASK-0002 的交付记录里加了一行。PIT-072 要求保留“仅依赖升级”的通道、功能 PR 不夹带依赖升级；`lanes.yaml` 的 root-config 共享区也写了这条通道。TASK-0002 是早已完成的去品牌卡，不该一直被借用，所以开一张常设卡，以后同类升级都用它。

## 交付内容（做什么）

每次出现新的高危公告时：

1. 先合并已经有完整通过回执的 PR（之后任何新的运行都会卡在 audit）。
2. 从集成人的分支发一个只改依赖的 PR，描述写“任务卡：TASK-0050”：`npm explain <包名>` 查清它从哪里进来（写进 PR 描述），先看它是不是某个 package.json 直接写了版本的依赖：是就照停止条件第 2 条，只改那一个版本号、再更新锁文件；不是，`npm update <包名> --workspaces --include-workspace-root` 升到修复版本，只改锁文件。锁文件改不动（上游包锁死了旧版本）时，才在根 `package.json` 的 `overrides` 加一项（只用于间接依赖），PR 描述写公告编号。基础镜像（Node、PostgreSQL、Caddy）出安全版时，只改 `Dockerfile` 的 FROM 行或 `docker-compose.yml` 的 image 行，版本号和多架构索引摘要一起换。
3. 本卡交付记录加一行：日期、公告编号、包名与前后版本、改了哪几个文件、PR 号。
4. 合并后，请各个开着的 PR 合入新的 main 再跑检查。
