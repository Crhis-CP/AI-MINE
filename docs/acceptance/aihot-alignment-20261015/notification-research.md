# 飞书通知：固定上游对照、含义与频率研究

2026-10-15，基线读取当前统一分支及固定AIHOT `540c47788eb6475c7ad8819d36733eda81dca20d`。主任务仍在并行修改，不把未上线源码当作用户已收到的消息。仅只读代码；未读取凭据、聊天记录或生产通知配置，未发送飞书消息，未修改产品代码。

**目前没有用户提供的通知原文。** 以下结论定位代码中的真实问题，不猜测用户具体困惑来自哪个群、哪一种消息。主线程已请求1–3条原文，收到后应逐条映射到触发函数再决定改动。

## 1. 结论

现有通知并非都需要重写：精选卡片的标题/导读/来源/查看按钮、告警的影响/自动恢复/所需操作结构、按事故去重、未知投递不盲重发、周月费用实际与估算分列均可保留。

需要优先修的是**消息事实与动作不一致**：系统日报说“你不用处理”却列费用/投递待核；所有未知请求都被叫作“自动重试过一次”；固定旧后台名称找不到；模型故障泛称所有步骤及日报停止；底层技术细节直接混进Owner消息。此外精选缺上游T1/T1_5过滤与重归组后的同事实已发去重，可能增加通知数量。

**“系统日报”不是资讯日报。** 当前本站及固定上游的 `notify` 内容投递主体均为selected，没有发现把读者日报/周报/月报自动投到飞书的调用链。`reports/compose`负责网站刊期；`ops.digest`发送运维跟进汇总。消息标题必须区分，不能为了“对齐”新增未经要求的日报群发。

## 3. 必须先修的事实/交互问题

1. **系统日报头尾互相矛盾。** digest实际包含未知费用、投递待核、后台任务排队、备份/价格/来源跟进。不要再写“全都不影响读者，你不用处理”；采用上游“需要跟进，具体影响见各条”再给各条动作。
2. **未知结果并未逐条证实已经自动重试。** 当前SQL没有join自动释放标记却直接如此命名；应按真实attempt/audit/当前队列状态统计，不把“已释放”又说成“已实际重试成功”。
3. **旧后台名称与URL已漂移。** “用量与模型密钥”“模型与近期用量”“通知与请求频率”与当前菜单/目标菜单不一致。统一从已确定的后台路由生成链接：运行 `/admin/runs`、模型 `/admin/models`、设置 `/admin/settings`、来源 `/admin/sources`；在新页未实现上线前链接仍须指当前实际可达页面或redirect。
4. **告警的影响描述过度确定。** 近1h历史拒绝不证明此刻所有功能停止；默认服务文案还把日报列作模型依赖，与本轮日报规则编排冲突。使用当前capability路由和真实积压描述“哪一环节、多少稿、是否仍可阅读、是否自动继续”。
5. **技术细节淹没动作。** 当前即时消息带`job_runs/pgboss/structure_article/docker compose`等。正文显示“文章结构整理”“事件归组”等中文名；保留短错误摘要和后台详情，不让用户猜术语。
6. **精选重复风险。** 同一新闻曾分成多个fact分别推送，后来合并再出现新稿时，仅当前fact dedupe无法发现旧事实已发。采用上游siblings投递检查；sent或unknown兄弟都挡重复，避免未知送达又多推一遍。
7. **重发旧卡片风险。** 本站resendDelivery直接用保存的payload，上游共享selectedContent重查当前公开资格；应拒绝已下架/不再合格稿的重发，使用当前合格文案但保留原发送审计。
8. **“已恢复”只说真实恢复的层级。** 心跳恢复、额度窗口腾出、某来源抓取成功、报告确实补刊是不同事实。旧报告finding按类型而非刊期命名有跨日误关闭风险，上游日报按日期跟踪；不要因为今日查询不再列旧缺期就发“已恢复”。

补充投递状态缺口：本站和上游`checkAlerts`都会忽略sendAlert返回的disabled而更新sentAt；watchdog也先claim状态再发。若发送关闭时记录成已通知，重新启用后可能在重复窗口内静默；远端已收但本地保存前崩溃也可能重复。应区分观察到事故与确实通知成功，已知disabled不记sent；未知结果保留待核。这个属于两边共存的可靠性问题，不能说“照搬上游已解决”。不需要因此引入第二套消息平台。

## 4. 频率建议：先分清自动等待与需要操作

建议保持现有重要事故分级骨架：真实读者影响首次通知、最多每小时提醒；Owner需要做账号/余额处理最多每天；其他跟进集中一次每日汇总；没有待跟进项不发。采用上游对于请求次数用完的轻处理，不额外增加短时配额告警。

周一目前会有08:00反馈周汇总、09:00运行汇总和来源周报、09:05用量周报，若月首还有月报；这些是不同内容，不能在没有样例与用户偏好时自行合并成一封超长信息。优先让零事件周汇总安静、重复事故不要跨多种摘要重复解释；用户原文确认后再决定是否合并周报。频率变更应给出具体“由什么改成什么”，不要凭感觉增加提醒。

未知费用的30分钟自动恢复是**后台工作策略**，不必每次都发一条“恢复中”。若尚在自动等待且没有持续读者影响，可以后台可见/汇总记录；一次自动恢复仍unknown才明确“需要人工核对”。发生真实内容积压由归组/处理告警提供业务影响，避免同一问题费用消息、队列消息、模型消息连续三次要求用户操作。

本研究不创建任何额外Codex定时任务，也不直接改现有飞书发送开关/群路由。

## 6. 验收入口与完成边界

复用 `tests/alerts.test.ts`、`deliveries.test.ts`、`source-health-report.test.ts`、`usage-weekly.test.ts`、`usage-monthly.test.ts`、`usage-protection.test.ts`、`feedback-forward.test.ts`、`feedback-maintenance.test.ts`。不为每一句文字写脆弱快照；测试真实语义：首次unknown不声称已重试、每类事故去重/恢复、disabled不算sent、已发/unknown兄弟阻重复、撤回稿不可重发、旧金额事件不报现役暂停、零待办不发送、汇总不一概说无需操作。

浏览器只需确认消息中的目标地址和对应操作确实存在；真实消息发送必须由主任务取得具体发送授权后再做。收到用户样例后，补“原消息→触发函数→真实含义→是否需要操作→具体修改”逐条对照，不能凭此报告宣称已优化用户实际收到的全部通知。
