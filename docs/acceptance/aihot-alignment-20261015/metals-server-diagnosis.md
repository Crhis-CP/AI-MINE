## 1. 结论

**服务器自动更新正常运行，六种LME金属已经在本次核查期间自然更新到10月15日。** 生产任务 `job_runs.id=290467` 在10月15日13:45:20 UTC（北京21:45:20，用户本地10:45:20）启动，13:45:59完成，Cochilco 15日六条报价正常入库。此前用户看到14日，不能据此判定任务停了；现行每天三次轮询加最长5分钟公开缓存，确实会造成来源已更新而页面尚未跟上的时间差。

**金、银、铂、钯仍显示14日，有另一层日期语义。** 俄罗斯央行官方最新记录为15日起生效，按其官方方法学对应14日定价，本站减一天不是随意造日期。目前尚未查到16日起生效的新记录，不能把这些值强改15日。

**上一有效报价比较当前正确。** 公网10个日价系列全部按其最新已存有效前值重算，结果与API一致；六个Cochilco日价均为15日对14日，四个CBR转换日价均为14日定价对13日定价。日价不会机械减一个日历日取前值，周末可以跨过；但“最近有效存储报价”仍不自动证明来源所有中间交易日都已完整采到。

**当前没有必须扩容的证据，建议暂时保留4核4GB。** 最近24小时CPU平均约7%、10分钟平均峰值24.25%，可用内存最低约1049MiB；磁盘等待和利用率低。价格的新鲜度问题应先改调度和展示，升级CPU不能解决轮询时段。扩大到200个新增源及完成架构整合后再复测；如出现持续内存压力，优先考虑4核8GB，而非先增加CPU。

## 3. 代码事实与建议修复

### 已有实现，应保留

- `packages/backend/src/publication/metal-prices/read.ts::loadMetalPrices` 在只读repeatable-read事务中按系列选最新版本，日价前值用 `period_start < current` 倒序第一条，不要求昨天；单位/币种/换算率一致才比较。
- `change.ts::percentVersusPrevious` 用十进制定点BigInt，SQL用numeric；都保留一位、half-away-from-zero，不应改成浮点数展示前相减。
- `cochilco.ts::cochilcoPeriod` 核报价日期、LME现金市场和美元/吨单位，忽略图表、期货、锂旧观察；PDF内容哈希组成版本。坏PDF按期held，`refresh.ts` 的daily分支不会让一个坏日阻止后续新日。
- `refreshMetalPrices` 已支持 `opts.source`，来源失败相互隔离；同版复读只touch，修正版保留release身份。
- `apps/api/src/routes/site.ts` 公开价格缓存300秒，ETag排除generatedAt；读者访问不触发采集或模型。

### 需要改的机制

1. **按来源频率调度，而不是五个来源共用三个中国时段。** `apps/worker/src/schedules.ts` 当前固定北京09:45/15:45/21:45，最长间隔12小时；适合部分国内发布时点，却不能及时覆盖欧美新发布。建议日价来源每小时检查，旬/月/周源继续较低频检查。利用现有 `source` 参数拆调度；不要简单把整批五源每半小时全量重跑。
2. **保留真实调度证据。** 当前 `operations/metal-price-runs.ts::readMetalPriceRuns` 只认识 `metals.prices` 和 `.manual`。如果拆为每源任务，必须同步它和alerts的读取/聚合，或继续由统一任务返回按源结果；不能改cron名称后让后台看不到任务。任务整体ok时仍显示每源error/held。
3. **区分“报价日、定价日、生效日、最近核查、来源是否已发布下一期”。** 页面“fresh”当前只是未超staleDays（Cochilco5天、CBR14天），不是“当日最新”证明。建议显示“最新已公布报价：10月15日；最近核查：…”，CBR明确“10月14日定价，15日起适用”。未见新一期时说明待来源发布；抓取失败说明沿用上一有效期。不要缩短staleDays后把每个周末误报故障。
4. **CBR提前公布下一日生效价的查询边界存在潜在延迟。** `cbr.ts` 查询终点为北京时间today，并过滤effective day>today；官方日内可能先公布次日生效价格。可把请求窗口终点扩大到today+1，并核真实生效日/定价日及当地日期后接纳已正式发布的新记录；这不是推算价格。本次未查到16日记录，所以不能称今天已发生这一漏采。
5. **严格说明“上一有效交易日”的覆盖。** 现有查询可跳过坏期/缺汇率期，得到最近已存有效报价；如果官方存在中间交易日但被held，比较跨度会变大。应显示具体比较日期，并在存在已知held缺期时注明“较上次有效报价”；不要一律写“较昨日”。需要完整逐日覆盖时，另外补缺期恢复策略，不能为了补洞重新使用无效值。
6. **更频繁轮询要避免反复下载同一PDF。** 先检查官方索引，只下载新日期/需要重核的版本；若官方提供可靠ETag/Last-Modified则用条件请求，否则设置有界同日修正版复核节奏。不能永远跳过旧日期而漏掉官方修正，也不能每次全历史重新解析。

建议验收入口：`tests/metal-prices-cochilco.test.ts`、`metal-prices-cbr.test.ts`、`metal-prices-read.test.ts`、`metal-change.test.ts`、`metal-prices-check.test.ts`。本次没有运行这些测试。新增场景应覆盖：来源在两次计划运行之间发布；未来生效日已正式公布；周一比周五/俄罗斯假期；已知held中间期；同日修正版；无新一期不伪造今天；拆来源调度后后台/告警仍可定位；正常API缓存到期读到新价。

AIHOT固定版本 [deploy.md](https://github.com/KKKKhazix/AIHOT/blob/540c47788eb6475c7ad8819d36733eda81dca20d/docs/deploy.md) 仅建议至少2核4GB，且提到构建镜像需要内存；**这不是AIHOT真实线上服务器配置证据**，也不能替代本站的负载测试。本文未取得峰时用户并发/P95延迟、扩源后自然负载、发布构建瞬时峰或未来增长测算，因此不作“永远不用升级”的结论，也未采购或申请扩容。
