# 页面打开与切换速度：本地前后对照（TASK-0593）

- 日期：2026-11-08　记录人：Claude
- 线上改前基线（Owner 提供，2026-11-08，优化前）：电脑打开首页约 1.8 秒，手机打开文章页约 2 秒，站内切换约 1 秒。
- 被比较的版本：改前是 main `992067036167ec91aa5632e7715a79569a90b566`；改后是同一基础上本任务的提交（见 `tasks/TASK-0593.md`）。
- 环境：本机容器，Node 24.22.1，Playwright 自带的 Chromium 153（无界面）。生产构建（`npm run build --workspace @amp/web`），web 进程照生产方式启动，数据来自演示接口（`e2e/demo-api.ts`，合成数据；没有数据库，没有调用任何模型）。web 前面加了一层 gzip 压缩，作用相当于线上 Caddy 的 `encode zstd gzip`，所以字节数是压缩后的数字，和线上口径接近。
- 测量脚本：`docs/acceptance/speed-20261108/measure.mjs`，本地和线上用同一个脚本（用法见文末）。每项测 5 次，取中位数；每次都开一个全新的浏览器，相当于第一次访问、没有缓存。
- 两种设备：电脑 1440×900，不限速；手机模拟 iPhone 13，限速为下行 1.6 Mbps、上行 750 kbps、往返 150 毫秒。

## 结论

1. 读者看到的页面、文字和排版都没有变化。第一次打开时少下载约 29 KB 脚本；电脑上每页少 1 个请求，手机上少 2～3 个，带图文章少 3～8 个。
2. 手机限速下，页面能点击的时间（下表“可交互”）缩短 0.26～0.32 秒，约 11%～14%；带 8 张图的文章缩短 0.5 秒（16%），传输量从 671 KB 降到 466 KB。
3. 首次出现内容的时间（FCP）和最大内容出现的时间（LCP）在手机上基本不变，因为它们主要由网页本身和样式表决定，这次没有动这两样。电脑上的毫秒级差异在误差范围内。
4. 站内切换的时间没有变化，差异都在误差范围内。同一个构建在电脑上反复测，切换时间会在 53～101 毫秒之间波动。线上切换约 1 秒，主要花在服务器读数据上，前端改动帮不上，见“还没做的较大改进”。
5. 本地的 TTFB（收到第一个字节的时间）只有十几毫秒（手机加上模拟的 150 毫秒往返），因为演示接口立即返回，不能代表线上。线上首页 1.8 秒里，服务器读数据和真实网络占了大头。

## 改了什么，各自的效果

| 改动 | 为什么 | 测到的效果 |
|---|---|---|
| 1. 英文界面的词表只给英文页面（`apps/web/app/i18n/index.ts`、`apps/web/app/entry.server.tsx`） | 英文界面的词表（`phrases.ts`，约 80 KB）原来打包在所有页面共用的脚本里，中文页面也要下载。现在服务器启动时就把词表装好，两种语言都照常直接渲染；浏览器只有打开英文页面、或者从中文切到英文时才去取词表。取到之前，页面保持原样，不会闪出中文。 | 共用脚本从 118.0 KB 降到 89.6 KB（压缩后），每个中文页面少 28.4 KB，约 24%。英文页面多一个约 29.6 KB 的请求，总量和原来基本一样。 |
| 2. 网站标识只下载正在显示的那一版（`apps/web/app/components/Logo.tsx`） | 每个页面都带着浅色、深色、小尺寸三版标识（顶栏、手机顶栏、页脚），原来三个文件都会下载，每个约 11.5 KB。现在改为按需加载（`loading="lazy"`），被主题或屏幕宽度隐藏的那版不再下载。 | 电脑少 1 个请求，手机少 2 个；每页少下载 11～23 KB。显示出来的标识照常加载，回归测试里专门检查了这一点。 |
| 3. 文章正文的图片从第二张起按需加载（`apps/web/app/lib/body-images.ts`、`apps/web/app/features/item/ArticleBody.tsx`） | 正文图片原来在打开页面时全部下载，在手机上会和脚本抢带宽。现在第一张照常加载（它可能就在屏幕上），后面的图等读者滚动到附近再加载。接口返回的正文不变，只在网页渲染时给后面的图片加上 `loading="lazy"`。 | 手机打开带 8 张图的文章，传输量从 671 KB 降到 466 KB，少 8 个请求（其中 4 张图），可交互提前 0.5 秒。什么时候开始加载由浏览器决定：Chrome 会提前加载离屏幕不远的图（手机限速时约 1250 像素以内，网速未知时更远）。演示文章较短，所以电脑上 8 张图仍然都加载了；线上正文越长，省得越多。 |

缓存头没有改：带哈希的静态文件本来就是 `public, max-age=31536000, immutable`，其他静态文件是 1 小时，都合理。字体没有改：字体文件、子集范围和 `font-display: swap` 都保持原样，常规字重仍然预加载。没有引入任何动画库。

## 按项目规则检查过、没有改的地方

- **悬停预取**：`IntentLink` 只在按下链接时预取。TASK-0367 规定悬停、键盘聚焦和触摸滚动都不能额外发请求，所以这里没有改成 `prefetch="intent"`。
- **数据串行读取**：首页、全部动态和文章页的读取函数都只调用一次接口；全部动态里的法规搜索本来就和资讯并行；布局的读取在切换时不重复执行。这几处没有可以改成并行的地方。
- **后台代码混进读者页面**：读者构建的模块清单里没有后台代码，`motion` 动画库只在后台使用，`web-split` 检查通过。
- **重复依赖**：没有发现。zod 在读者脚本里只有一份。

## 还没做的较大改进（估计收益）

1. **服务器先把样式和脚本地址发给浏览器（103 Early Hints）**。现在浏览器要等服务器读完数据、拿到整页网页，才开始下载约 240 KB 的样式和脚本。如果 web 进程先回一个 103 响应，列出固定要用的样式、框架脚本、共用脚本和字体，浏览器就能在服务器读数据的同时下载这些文件。线上首次打开估计能快 0.2～0.5 秒，大约等于服务器读数据的时间。前提是 Caddy 和 EdgeOne 会把 103 转给浏览器（Caddy 支持；EdgeOne 要在服务器上确认）。本地用的是 HTTP/1.1，Chrome 不处理这种情况下的 103，所以在本地测不出效果。
2. **静态文件预先用 brotli 压缩**。带哈希的脚本在构建时压成 `.br`，比 gzip 小 15%～20%，第一次打开约少下载 35 KB。要先确认 EdgeOne 的缓存会区分 `Accept-Encoding`，否则不支持 brotli 的客户端可能拿到无法解压的文件。
3. **第一次打开时的那次重读**。页面在浏览器里接管后，撤回检查会把本页数据再读一遍（`ContentVersionGuard`，用来防止共享缓存里留着已撤回的内容），所以每次首次打开，服务器都要读两次。可以在页面数据里带上生成时的撤回版本号，版本没变就不再重读。这样首次打开时服务器的读取量减半，服务器忙的时候 TTFB 会受益；但这个改动涉及撤回规则，需要单独开卡并请 Codex 审查。
4. **线上站内切换约 1 秒，主要是服务器的时间**。切换时取的 `.data` 不能缓存，每次都要经过源站、API 和数据库。前端能省的只有路由脚本那一个往返，本地切换本来就只有 0.06～0.27 秒。建议 Codex 在服务器上给 `/api/site/pool`、`/api/site/timeline` 和 `/api/site/items/:id` 加上 `Server-Timing`，量出各段耗时，再决定是加索引还是给匿名读取加短时缓存。
5. **读者脚本里的 zod 和整套接口定义**（压缩后约 45 KB）。客户端只为校验几种返回结果，却引入了整个 `schemas` 对象，连法规和 v3 接口的定义也一起带上。把契约包拆成按需引用，估计能再少 15～25 KB；这属于契约区的改动，要单独提 PR。
6. **列表页空闲时预载文章页的脚本**（约 14 KB）。手机上从列表打开文章，估计能快 50～80 毫秒。它会多发一个请求，和“只在按下时预取”的规则在精神上冲突，需要 Owner 决定。
