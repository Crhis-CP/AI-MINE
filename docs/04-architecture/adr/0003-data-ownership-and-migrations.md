# ADR-0003：每个模块独占一个数据库 schema；迁移按模块分目录、时间戳命名

- 状态：【设计】工程基线提案（M0 结束前由架构 Agent 定稿）
- 修订：2026-10-01 按 Owner 答复复核——本 ADR 的“迁移”只指数据库结构迁移，与旧站数据无关：Owner 2026-10-01 决定旧站生产数据一概不导入、新站从空库开始（全重做，DEC-20）；第 7 条的“数据迁移”只指 AIHOT 基线表内的开发与预发数据随表搬迁；“预算账本”改“用量账本”（DEC-08）。
- 类别：工程基线
- 关联：`03-module-map.md` 第 4 节、`05-engineering-conventions.md` 第 7 节；对应 B：`B:architecture/03-stack-decisions.md` ADR-N04（B 的“集成者统一分配迁移编号”与单一 `intelligence` schema 不采用，理由见下）

## 背景

AIHOT 与旧项目都使用全局递增编号的迁移目录（AIHOT 0001–0038，已出现跳号），多个 Agent 同时新增迁移会冲突；AIHOT 的 60 张表全部在默认 schema、37 处外键；旧项目多个服务共享同一批表、迁移回滚困难。集中分配编号会让每个带表结构变化的任务都等集成人。

## 决定

1. 每个模块一个 PostgreSQL schema（与模块同名；`ai-gateway` 用 `ai`；entities、events、policy 各自独立，不合并成一个 `intelligence`）；平台包 identity 用 `identity` 与 `audit`，ops 用 `ops`，queue 用 `pgboss`（任务类型前缀取 schema 名，见 `03-data/03-internal-contracts.md` 第 3 节）。模块只写自己的 schema。
2. 跨模块读取只通过对方公开函数；确需 SQL 共享时由拥有方在自己 schema 提供只读视图并登记在 README。
3. 跨模块引用使用稳定字符串 ID，不建跨 schema 外键；由事件处理与对账任务保证一致。
4. 迁移文件位于 `database/migrations/<module>/<UTC 时间戳 YYYYMMDDHHMM>_<说明>.sql`。只做向后兼容的增量，结构变更走 expand → 迁移数据 → contract 三步，破坏性步骤需要 ADR。
5. 执行顺序：先按迁移文件头部声明的依赖（`-- depends-on: <module>/<文件名>`）做拓扑排序，再按时间戳；创建跨 schema 只读视图的迁移**必须**声明依赖。
6. 已合并的迁移不可修改（统一验证入口比对已合并迁移的内容哈希）。
7. 过渡期（资讯线绞杀式拆分，见 `03-module-map.md` 第 9 节）：AIHOT 原表暂留默认 schema，登记在“待迁出清单”；某模块第一次被改动时，连同数据迁移（只指基线表内的开发与预发数据随表搬迁，不涉及旧站生产数据；旧站数据一概不导入，DEC-20）把它拥有的表移入自己的 schema，并从清单删除。法规线、权限矩阵、用量账本等新能力从第一天起在自己的 schema 建表，不从 AIHOT 表结构派生。

## 后果

- 并行新增迁移不冲突，不需要集中分配编号；模块数据边界可由静态检查验证；
- 失去数据库层面的跨模块外键保护，需要对账任务与测试补位；
- 过渡期内“待迁出清单”是已知违规，只减不增。

## 推翻条件

依赖声明遗漏导致的迁移顺序故障在一个季度内出现两次以上，再评估改为集中编号或迁移工具内建依赖图。
