## 2. 目标部署拓扑（首期单机）

### 2.1 环境与规格：先基准，再决定（DEC-18，Owner 2026-10-01 已定）

**【Owner 决定】2026-10-01（DEC-18）**：先做容量基准，达标沿用现有 4C4G，切换演练临时租按量机器；Owner 强调这是全新重写的项目。落地如下，背景如下——A 直接定“复用已购 4C4G”，B 定“不默认复用、按容量档基准”，两边各缺一半：A 的依据是 Owner 2026-07-26“服务器尽量考虑性价比，未来可以扩容”（OWN-10）、旧ADR-0010 的已购拓扑和旧站实测；B 的依据是“旧数字不等于未来容量”（H-041）和影子运行需要并行环境。本包写成四步：

1. **M0 容量基准**：在本地或隔离的“4C4G 等价档”环境，用目标数据量与两条业务线的 lane 份额做基准。全部满足才算达标：内存占用 <75%（MemAvailable ≥25%，口径见 7.2）且无 OOM；系统盘已用 <20,000,000,000 字节且发布前可用 ≥4GiB；公开接口 p95 ≤300ms、首屏桌面 ≤2s 手机 ≤3s；各 lane×stage 最老积压不持续增长；出口带宽与月流量在 7.3 预算内。
2. **达标**：最终生产就用现有腾讯云大陆 4C4G（保留备案与域名）。**不达标**：按基准结果选规格，费用须 Owner 批准；4C4G 等价档作对照档保留。
3. **预发与影子运行**放在本地 Compose 预发，或临时租用的按量实例（演练完退租，费用须 Owner 批准）；**不在旧生产机上与旧站并行**（内存相加超过 4GB，见第 1 节）；**不在生产主机上构建**。
4. **换云商或换主机的备案约束**：公网入口指向任何新实例之前，先向备案接入商确认是否需要变更接入信息（同厂商也要确认）；换云商前必须先确认备案信息变更；列入 `08-open-questions.md` 的环境选型约束（原 B:O-05，其中“云区域”一项已删除）。

### 2.2 容器与内存初值

| 容器 | 职责 | 内存初值 |
|---|---|---|
| `caddy` | HTTPS、按 Host 路由、安全响应头、代理身份改写、屏蔽私有路径并去 `Set-Cookie`、日志脱敏、超时与头大小限制。**不做限流**：限流在应用层（`06-security-and-access.md` 2.2） | ~50MB |
| `web` | 读者站 SSR + 私有路由组（只在 `PRIVATE_HOST` 响应）；不持数据库与模型凭据 | ~200MB |
| `public-api` | 公开只读查询、反馈提交（`/api/` 下不存在的路径，含旧站的 `/api/v1`、`/api/v2`，统一返回错误体 `not_found`，不做兼容） | ~200MB，1 核上限 |
| `private-api` | 最小私有页面接口、只读运维 MCP（`/mcp-ops`）；与 public-api 同镜像 | ~150MB |
| `worker` | 调度、加工、归组、法规处理、投影、报告、告警；两条业务线 lane×stage 调度 | ~600MB |
| `fetcher` | 抓取、解析、PDF/OCR（浏览器渲染默认关闭） | ~300MB（硬上限 512MB） |
| `postgres` | PostgreSQL 18（扩展以 `02-tech-stack.md` 为准） | ~1.2GB（`shared_buffers` 约 512MB） |
| `migrate`、备份作业 | 一次性任务容器：迁移；每日备份（5.2），临时目录有上限 | 临时 |

合计约 2.7GB，给系统、页面缓存与发布预检（可用内存 ≥1GiB）留出余量。**没有 `admin-web` 容器**（ADR-0018）。初值按基准调整；资源限额写在版本化的编排文件里，线上与期望配置的差异被自动发现，不在线上手工改配额（PIT-057）。所有基础镜像写“具体补丁版本 + sha256 摘要”，不写浮动标签（`06-security-and-access.md` 6.1）：起点为 `postgres:18.6-trixie`、`node:24.21.0-trixie-slim`、`caddy:2.11.4-alpine`（2026-09-30 已在 Docker Hub 确认标签存在；摘要在 T-0001、T-0005 拉取镜像时写入，不写在本文以免漂移，`02-tech-stack.md` 4.2）。更新节奏：基础镜像摘要随依赖升级批次更新，PostgreSQL 小版本随季度发布评估，安全公告按需，均走 `make release-check` 与回滚演练。备份作业的镜像从 PGDG 安装 `postgresql-client-18`（`pg_dump` 不能导出比自己新的主版本）。若首次生产部署前决定上 Node 26，镜像内改为显式安装固定版本的 pnpm——Node 26 文档站已无 corepack 页，按“不再随 Node 分发”处理，**未实测**（`02-tech-stack.md` 2.1）。

### 2.3 网络分段【设计】

纵深防御，也是 SSRF 的第二道闸（`06-security-and-access.md` 6.3）：

| 网络 | 成员 | 出网 |
|---|---|---|
| `ingress` | caddy（发布 TCP 80/443 与 UDP 443） | 仅证书签发与续期 |
| `edge`（内部） | caddy、web、public-api、private-api | 无 |
| `db`（内部） | postgres、public-api、private-api、worker、migrate、备份作业 | 无 |
| `work`（内部） | worker、fetcher（内部有界 HTTP） | 无 |
| `egress` | **只有** fetcher（抓取信源）与 worker（模型提供商、告警渠道、对象存储） | 有；对私有网段、链路本地与云元数据地址设出口丢弃规则 |

Docker 的 `internal` 网络不发布端口，回环发布无效，探针须在容器内执行或走独立网络（PIT-056）。

### 2.4 共享缓存层：默认不加

AIHOT 的缓存头与图片代理是按“前置缓存 nginx/CDN”写的（`X-Accel-Expires`、`auth_request`），仓库自带的部署只有不缓存的 Caddy，README 的“页面中位数约 10ms”测量条件不明、可能含前置缓存，**不作证据**（D14b-aihot-web-009）。决定：**默认无缓存直连，以目标机实测为准**；只有基准显示首屏 p95 不达标、且确认瓶颈在重复渲染与读取时，才按顺序评估应用层短缓存、Caddy 缓存插件、自建 nginx `proxy_cache`。任何缓存层都必须满足“下架 60 秒内所有出口不可见、JSON 与 RSS `max-age=0, must-revalidate`”（`03-data/contracts/interface-behavior.md` 1.4）。`X-Accel-Expires`、图片代理 `auth_request`、后台 `auth_request` 的去留写入 T-0008 任务卡。

## 3. 发布流程（ADR-0012、ADR-0017）

### 3.1 制品、信任根与传输（补 D12-architecture-011）

旧主机只认旧仓库的 GitHub OIDC 签名和固定云角色；A 只写“拉取新镜像”，B 只写“可信 artifact”。留空的结果是实施者用最省事的办法（SSH 进服务器 `git pull`/`docker build`、写入长期 AccessKey），这恰是旧站交付链过重与泄漏风险的来源。规则如下（ADR-0017 第 5–9 条的落地）：

| 环节 | 规则 |
|---|---|
| 验证与构建 | 仓库唯一验证入口 `make verify` / `make release-check`，在指定完整 SHA 的干净检出上运行并产出验证回执；镜像按 SHA 构建（linux/amd64），附 manifest、SBOM 与离线签名；执行者是独立构建机或开发机上的隔离环境，**不得是生产主机**；执行器不可用时换执行器，不跳过检查 |
| 信任根 | Owner 一次性生成离线签名私钥（或选定独立签名服务）；公钥指纹经受保护通道装到主机 root 专属路径；主机**只接受该公钥对“镜像 digest 清单 + 验证回执”的签名**；候选制品不得自带验证器或信任配置；更换信任根须 Owner 明确授权并在同一次迁移中验证，不能先关验签来上线（ADR-0017 第 6 条；旧ADR-0038:38-41@policy） |
| 旧信任锚 | 旧主机的验签硬绑定旧仓库的发布流程与 GitHub OIDC 签发方（`docs/policy-upgrade/delivery-audit.md:19,21,152@policy`），新仓库与新产物形态不适用。旧部署器与信任锚在新链路演练通过前**保留作回退**，退役见第 8 节 |
| 传输 | 受控的开发机或构建机上的命令行（不是生产主机），经云主机命令通道的**固定命令** + 短期 STS 凭据（云角色由 Owner 创建，最小权限，写明 principal、期限与审计主体）；**禁止长期 AccessKey**；禁止 SSH 进服务器手工构建 |
| 镜像仓库 | 国内可稳定拉取的镜像仓库；主机只持**只读拉取令牌**，**按 digest 拉取，不按可变 tag**；若用腾讯云镜像仓库（TCR）个人版，是否已开通由 Owner 确认（第 1 节，Q-60），其配额与保留策略在 M0 核实（旧站曾因制品存储配额用尽而签名包上传失败，PIT-055） |
| 发布请求 | 至少绑定 `request_id`、`actor`、`target_main_sha`、`quality_receipt_digest`、`artifact_digest`、`expires_at`、`allowed_action`（`docs/policy-upgrade/actions-transition.md:126@policy`）；唯一部署锁，串行，不自动取消执行中的主机切换 |
| “已上线”的证据 | 公开响应带**发布标识头**（旧站为 `X-GMPI-Release`，`infra/tencent-cloud/caddy/Caddyfile.live:85@main`；新站名称在 M0 写入契约）；以**从主机之外读回**该头且等于目标 SHA 作为“已上线”证据；**验证通过或 CI 绿 ≠ 上线** |
| 恢复已安装版本 | 已安装且验证过的版本可在不重新构建的情况下恢复运行（旧ADR-0034） |
| 不依赖交付链 | 新闻线与法规线的采集、加工、发布在服务器上常驻运行，**不依赖执行器、构建机、代码托管平台或任何开发会话**；它们不可用只影响软件发布（BR-OPS-01；Owner 要求） |

### 3.2 发布步骤（七步）

```text
验证与构建（开发机/构建机）：make verify → make release-check → 镜像 + manifest + SBOM + 离线签名 → 推送到国内镜像仓库
部署（主机，唯一部署锁）：
  1. 预检（在暂停处理之前完成）：可用内存 ≥1GiB、可用磁盘 ≥4GiB、当前版本健康、没有并发部署或回收、
     Docker/runc 版本门禁通过、制品验签通过。不足则先做 3.4 的有界清理再重检；仍不足则失败，且不新增任何暂停
  2. 按 digest 拉取新镜像并验签
  3. 执行迁移（只增不破；失败即停，不影响当前版本）
  4. 替换 public-api / private-api / web / worker / fetcher（始终保留当前与上一版本）
  5. 健康检查 + 公开读取冒烟（首页、详情、搜索、RSS、私有主机名登录页、公开新鲜度探针）
     + worker 在 120 秒内通过当次启动的就绪探针并跑通一轮 + 从主机之外读回发布标识头
  6. 成功：登记本版本的产品更新（幂等；登记失败保留“待补记”并重试，不回滚健康的站点）
     失败：自动回滚到上一版本镜像，并验收回滚
  7. 回收：按 3.4 有界回收旧容器、旧镜像标签、旧发布目录与泄漏的网络
```

- **回滚也要验收**：回滚后对上一版本重跑同一套检查（健康 + 公开读取冒烟 + worker 一轮）；失败则非零退出、进入**维护态**（公开入口改为只读静态页或关闭）、告警、不登记产品更新、不打印成功。旧仓库在首次部署之前，由独立核验员发现过部署脚本的缺陷：回滚到上一版本后冒烟检查失败仍打印成功、入口保持开放（Issue #46 / PR #47，2026-08-15，已修复；没有线上事故记录）；旧手册还写明进程被杀、断电后不会自动回滚（PIT-091）。验收：AC-OPS-06、T-149。
- 发布状态机持久化每个阶段；进程被杀或断电后，下次启动（或定时对账）检查未完成的激活或回滚，并给出恢复命令。自动检查：在“上一版本冒烟失败”“数据库已激活但主机切换未完成”两点注入故障。
- 发布成功 = 健康检查通过 + 公开读取冒烟通过 + worker 完成至少一轮处理 + 外部读回发布标识头（PIT-054）。
- **三类回退分开演练**（B:M5）：代码回退（上一版本镜像）、内容指针回退（把公开读取层退回上一个已验证的内容版本）、数据回退（从备份恢复，见第 5 节）。
- 产品更新只在发布成功且健康后登记，规则取 `01-product/04-private-operations.md` OP-17 C（页面已废弃，规则转交发布流水线）：把本次版本的产品更新片段（`changes/*.md`）合并为一条登记；类型只能是“公告/更新/优化/下线”四种固定值并带要点列表，在合并前（`make verify` 的产品更新片段检查）和登记前**两次校验**，不合格阻断并告警，不得静默丢失；同一版本重试不重复登记（BR-SITE-01）；没有新产品说明的版本登记一条简短的“例行维护”；只写读者与运营者能懂的变化，不写提交编号、迁移与部署命令；登记暂时失败不回滚已经健康的站点，记为“待补记”并告警，由发布流水线幂等重试，不设人工补记页面。

### 3.3 生产变更授权矩阵

旧站用逐次显式确认串（如 `GMPI_DEPLOY_APPROVED`）落实“大范围预授权、保留关键边界”（OWN-05）。新站同样：

| 类别 | 内容 | 怎么授权 |
|---|---|---|
| **预先授权** | 在隔离环境运行验证；只读检查；按 digest 部署已签名制品（可逆发布）；回滚；发布流程内置的有界回收（仅限 3.4 列出的受管对象）；备份与恢复演练（恢复到隔离库） | 不需逐次确认 |
| **须 Owner 逐次显式确认** | 创建或采购云资源；DNS 变更；开放公网入口；创建或轮换凭据与签名密钥；更换信任根；数据库恢复到生产库；超出 3.4 范围的手工或批量磁盘回收；不可逆删除；启用出口代理或境外节点；启用 GitHub Actions 或注册 runner；修改分支保护 | Owner 在对话或图形化入口明确批准；批准记录（request_id + actor + allowed_action）写入回执；Owner 不需要使用终端 |

### 3.4 磁盘回收与日志体积（20GB 目标）

A 只写“保留当前与上一版，删更旧镜像与构建缓存”，极易被实现成定时 `docker system prune`（含卷），这正是旧站明令禁止的；“构建缓存”在“服务器只拉取、不构建”的架构里本不存在，是抄自 AIHOT 的服务器上 `compose up --build`。规则如下（旧 `docs/reviews/storage-retention-20260920.md:4-39@main`、`docs/runbooks/automatic-live-intelligence.md:529-575@main`）：

| 项 | 规则 |
|---|---|
| 口径 | 系统盘已用字节 **< 20,000,000,000**（严格判定，不把“仍有部署余量”视为达标）；每次发布前可用磁盘 **≥4GiB**、可用内存 ≥1GiB。20GB 是 Owner 对该 40GB 主机的要求，若换规格，按新盘容量的同一比例另定并由 Owner 确认 |
| 回收对象 | 已停止且身份匹配的受管旧容器；没有被保留对象引用的旧镜像标签；通过完整性核验的旧发布目录；泄漏的 Compose 网络（防 Docker 地址池耗尽，PIT-053） |
| 保留 | 当前版本、上一版本、在用引用、未核验对象 |
| **禁止** | 全局 prune、强制删镜像、删卷、重装服务器、为达标删除业务数据或证据。给 Owner 的手册同样禁止（旧 `docs/runbooks/AI矿策服务器与系统交接说明.md:380-382@main`） |
| 顺序 | 预检不足先做有界清理；仍不足则**失败且不暂停处理**。旧站曾因“先暂停、后发现余量不足”让部署保护把 worker 停着等人救（`insufficient_staging_disk`） |
| 失败 | 回收失败或未达标只告警，**不回滚已成功的发布**，也不删业务数据 |
| 互斥 | 回收与处理/发布共用一把锁，删除前核对现役状态 |
| 日志与临时目录 | 容器日志驱动设大小上限（旧站 10MB × 3）；备份临时目录有上限；二者计入 20GB 预算 |
| 自动检查 | 连续发布 N 次后，残留容器、镜像、网络、发布目录数量恒定（PIT-053） |

### 3.5 部署暂停与 Owner 暂停怎么区分（D15-secops-018）

旧站把“部署暂停”与“Owner 暂停”共用一个开关，靠“记录原状态 + 比较并交换（CAS）”避免互相覆盖（`infra/tencent-cloud/LIVE_DELIVERY.md:150-164@main`；`docs/policy-upgrade/operations-exit.md:28-31@policy` 指出该开关做不到“暂停新闻、法规继续”）。新站用业务线运行控制 `LaneControl`（ENT-54，`platform/queue`；采集、处理、公开三个开关加“紧急全停”）写成带持有者的记录：

| 字段 | 说明 |
|---|---|
| 业务域 | `news`（资讯线）、`policy`（法规线）、`all`；每条业务线各自记录 |
| 持有者 | `owner`、`deploy`、`system`（原 `budget` 持有者取消：不设月度额度，没有额度类暂停；异常熔断是独立的熔断状态 ENT-82，与暂停互不覆盖） |
| 原因与到期时间 | 必填；暂停全部业务线的全部自动处理最长 24 小时，可续期；到期未恢复告警，不自动恢复（INV-30、PIT-052） |
| 版本号 | 用于比较并交换 |

规则：部署保护**只创建和释放 `holder=deploy` 的 `LaneControl` 暂停**（经 `setLaneControl(…, expectedRevision)` 比较并交换），不触碰其他持有者；释放时对版本号做比较并交换，**版本已变则不恢复、保留事实并推送告警**；成功路径释放，失败路径保持 deploy 暂停并带到期与告警，同时提供固定的“恢复被持有的 worker”动作（精确目标、单飞、可重入，不要求手工清理回执）；已有的 Owner 暂停保持有效；比较并交换只检测漂移，不阻止 Owner 在部署期间改暂停；漂移未解决时保留原暂停事实并阻止重试，不当作新的 Owner 暂停。预检在暂停之前完成（3.2 第 1 步）。

### 4.1 原则与两种形态

- **全部排期功能完成并通过各自验收后，一次性全面切换**【Owner 决定】2026-10-01（DEC-19）：旧站在此之前照常服务；“全部排期功能”指功能全集中除“候选（不排期）”以外的全部功能（资讯线、法规线、事件、精选与热点、报告、主题、搜索、收藏、对外出口、最小私有页面、告警）；不分批，不再有“能力对等即切换、其余切换后陆续上线”。
- **不迁移旧站任何生产数据**【Owner 决定】2026-10-01（DEC-20）：新站从空库开始，由新系统按信源表重新采集、处理、公开；M4 影子运行是新站用自己采集的数据与旧站并行对比，旧站仍是正式站。因此**没有“导入”“最终增量”“对账”“账本迁移”这些步骤，也没有新旧两站之间的数据回写**；`03-data/04-legacy-migration.md` 已改写为“旧站数据处置：不迁移，全重做”，本节只补主机、入口层与同机窗口。

- **新站上线当天旧站停止服务**【Owner 决定】2026-10-03（更正裁决表 DEC-19：「旧站只读不保留」）：新站读回发布标识、记为已上线后，旧站停止对外服务与 worker，不再启动；不保留只读，也不切回旧站；切换后出问题只在新站内处理（4.3 第 4 点）；**新旧两站之间不回写数据**。
- 新栈同一时刻只有一个实例（影子实例或正式主机）运行 worker 并产生付费调用，两处换手时先停前者；旧站 worker 在切换日之前照常运行；新旧两站各用独立的模型密钥与独立的数据库，互不读写。
- 旧站过渡期维护（含 2026-10-13 到期的旧站模型价格表）见 Q-56 与路线图 T-0806（M0 第 1 周交 Owner；新团队不改旧仓库、不动旧站），本文不重复定义；旧站在全面切换前仍按其自身的上限与价格表运行，与新项目无关。

| | 形态 1：同机切换（**默认**，基准达标时） | 形态 2：换机切换（基准不达标或 Owner 选择） |
|---|---|---|

| **T-24 小时** | 在预发或临时实例上预演入口切换（4.3）；如需变更 A 记录，提前降低 TTL 并验证；私有主机名沿用旧站已有记录，通常无需追加 | 预演通过 |
| **T-0 切换窗口**（形态 1，说明见下） | 公告；停影子实例的 worker，对其数据库做最后一次加密备份；停旧栈（公开站短暂不可用，旧栈数据卷原样保留）；把该备份恢复到本机；启动新栈并按 4.3 切入口。新栈起不来或入口验证没过（4.3 第 3 点）、发布标识还没读回时，中止切换：停止公网入口，停新栈，旧栈原样启动、照常服务，切换改期（旧栈数据卷不可用时用存档备份恢复旧库，须 Owner 授权；旧站已按 Q-56 确认停用的，只是新栈回到私有预览、切换改期） | 新栈健康；发布标识头外部读回一致 |
| **激活与读对照** | 激活新站；实测核心阅读、隔离、用量与熔断、持续任务；**读回成功才记为已上线**（即“切换完成”），此后旧站不再启动，实测出问题按下面“出问题时”一行处理；切换当天的更新日志记录是手写的“重大更新 2.0”（用平实中文说明新站上线、比旧站多了哪些功能，Owner 2026-10-05 认可，TASK-0038；不是专页，也不涉及旧站地址） | 对照差异可解释 |
| **T+24 小时 / T+7 天观察** | 启动命令退出不计观察完成，须独立探针证明（`docs/policy-upgrade/actions-transition.md:128@policy`）；旧站已停止服务、不再启动（形态 2 的旧主机同样停止对外服务），旧 worker 保持停止；每日核对新站的用量与熔断状态 | 24 小时与 7 天观察达标 |
| **出问题时** | 只在新站内处理：撤回公开入口（4.3 第 4 点），或代码、内容指针、数据三类回退（3.2）；**不切回旧站**【Owner 决定】2026-10-03；新旧两站之间不回写数据 | 预发演练通过（撤回公开入口与窗口内中止切换各一次，AC-OPS-09；三类回退各一次，AC-OPS-10）；原 T-143 已废弃 |
| **退役** | 新站上线当天旧站已停止服务；按第 8 节退役（先吊销凭据，再回收旧栈与销毁数据，须 Owner 授权）；回收前确认存档备份已校验 | 第 8 节验收 |

**同机切换的窗口【设计】**：旧栈（内存上限合计约 3.2GB）与新栈（约 2.7GB）在 4GB 主机上不能同时运行（第 1 节）。形态 1 因此这样做：影子运行与验收都在**临时实例**上完成；T-0 窗口内先停旧栈（公开站短暂不可用，提前公告），把影子实例最后一次备份恢复到本机，启动新栈并按 4.3 切入口；旧栈数据卷原样保留到第 8 节退役，窗口内中止切换时据此原样启动旧栈，新站上线后旧栈不再启动。窗口长度在预发演练中实测并写入公告，目标与恢复目标同量级（≤2 小时）；窗口需 Owner 知情。窗口内新站未采集到的内容由新站启动后的回填窗口补齐（资讯线按回填规则，法规线按现行有效文本），不从旧站导入。形态 2 没有这个问题。

### 4.3 入口层切换（D15-secops-012）

A 的新栈自带 caddy 容器，与旧站 Caddy 同机争用 80/443，且证书状态不同卷；B 的 M5 只有一句“激活公开入口”。两个 Caddy 无法同时绑定同一地址的 80/443，HTTP-01 验证也要占 80 端口；切换日若新 Caddy 用空数据卷启动，会向证书机构重新签发顶域与私有子域证书，一旦失败或触发频率限制就是整站 HTTPS 中断。

1. **入口所有权**：切换日只留**一个**监听 80/443 的 Caddy。默认采用新 compose 自带 Caddy：先把旧 Caddy 的数据目录（证书与账户）**复制**（不是移动）进新 Caddy 数据卷，再停旧 Caddy、启新 Caddy，并提前通告“可能出现秒级中断”。替代做法：保留现有 Caddy，把新栈作为按应用分片的站点片段接入，保留 `/etc/caddy/readonly-mcp/*.caddy` 这类由 root 管理、不随发布覆盖的片段（旧站曾因升级器整份替换 Caddyfile 而抹掉私有 MCP 路由，PIT-056）；升级只替换自己的片段。
2. **顺序**：新栈内部健康与内部冒烟通过 → 开放入口 → 验证证书有效、HTTP→HTTPS 重定向、**每个公开 HTML 页面页脚同时显示 ICP 备案号（链接 `beian.miit.gov.cn`）与公安联网备案号（带公安备案图标，链接全国互联网安全管理服务平台），任一未配置则不开放** → 外部读回发布标识头 → 才记为已上线。DNS 只追加记录，先确认内部健康再切 DNS。
3. **失败处置**：ICP 展示、HTTPS 或 DNS 验证任一失败，立即停止公网入口，不得靠公网 IP 或跳过证书继续（`docs/runbooks/production-deployment.md:540-563@main`）。发布标识读回之前失败，新栈回到私有预览，按 4.2 中止切换（各形态的做法见第 4 点）；已记为上线之后失败，撤回公开入口（第 4 点），不切回旧栈。
4. **上线后回退只在新站内**：“撤回公开入口”（只关入口，保留数据与证书状态），或新站自身的代码、内容指针、数据三类回退（3.2）。新站上线后不切回旧栈（Owner 2026-10-03）；切换窗口内、发布标识读回之前出问题，按 4.2 中止切换：形态 1 停新栈、原样启动旧栈（前提是旧栈仍可在内存与磁盘预算内启动，数据卷不可用时用存档备份恢复旧库，须 Owner 授权），形态 2 让 DNS 留在或指回旧主机；旧站已按 Q-56 确认停用的，只是新栈回到私有预览、切换改期；都不回写数据。撤回公开入口与窗口内中止切换都在预发演练过。
5. **入口层没有任何旧站地址的特殊规则**：新站不为旧站的任何地址做兼容或重定向，没有 301 表、410 说明页与旧 ID 别名表，也不查库；旧站的链接与接口地址在新站都是不存在的地址，由新站通用的 404 处理（4.4）；验收：固定样本逐条断言 404、无 `Location`（AC-OPS-15）。

### 4.4 旧站地址：一概不做兼容，不存在的地址一律 404（DEC-21）【Owner 决定】2026-10-01

Owner：“旧文章链接也全都不要，相当于从 0 开始做文章内容。”**新站不为旧站的任何地址做兼容或重定向**：没有旧链接对照表、没有 301 映射、没有“本站已改版”专页、没有旧接口适配期；新站只有自己的路由与接口，入口层与应用层都不为旧站地址设任何特殊规则。

| 对象 | 处理 |
|---|---|
| 旧站的条目、事件、报告等链接，栏目路径，旧 RSS 地址（含 `/items/itm_…`、`/events/…`、`/reports/…` 一类形态） | 在新站是不存在的地址，走通用“页面不存在”页（HTTP 404，带首页与搜索入口，PG-17）；不跳转、不猜测对应内容、不按形似旧 ID 的字符串查新对象；不带 `Location`、`Set-Cookie` |
| 旧机器接口 `/api/v1`、`/api/v2`（含旧读者接口路径） | 同样是不存在的地址，返回统一错误体 `not_found`（HTTP 404）；不带 `Location`、`Deprecation`、`Sunset` 头，不设适配期，也不设 410 专门响应 |
| 新公开接口 | `/api/v3` 前缀，只为避免旧客户端打到同名路径拿到形状不同的响应，不承担任何兼容义务 |
| 浏览器里的旧本地收藏 | 指向旧 ID，新站忽略、不报错 |
| 公开 ID | 新站自己生成、不复用（INV-18）；这是新站自身的规则，与旧站无关 |

## 5. 备份与恢复

A 写“每日 `pg_dump` 压缩后上传、保留 30 天 + 12 个月、沿用 AIHOT 备份脚本”，B 只有 RPO≤15 分钟/RTO≤60 分钟的建议、没有机制。三种口径并存，A 还把自拟的保留期标成了【Owner 要求】。本节以旧站已批准的机制为底稿（旧ADR-0010:27@main；旧 `docs/runbooks/infrastructure.md:103-133@main`；旧 `docs/testing-strategy.md:382@main`），叠加 A 的“每月演练 + 失败告警”与 B 的恢复不变量。

### 5.1 目标（默认值，需 Owner）

| 指标 | 默认（M1 验收用） | 说明 |
|---|---|---|
| RPO（最多丢多少数据） | ≤24 小时 | 每日备份一次。最坏会丢失最近 24 小时的人工下架、人工修订和费用记录 |
| RTO（最久多久恢复） | ≤2 小时 | 旧站已批准的恢复目标 |
| 升级条件 | 数据库 >12GB、恢复 >2 小时，或 Owner 提高要求 | 升级到 pgBackRest 2.59 或 WAL-G 3.0.9 做时间点恢复，目标 RPO ≤15 分钟、RTO ≤60 分钟（B 的建议值）。15 分钟 RPO 需要持续 WAL 归档，与“4C4G 单机、极致成本压缩”不匹配且 B 没给机制，所以不作 M1 验收 |

需 Owner：可以接受最长丢失多久的数据（RPO）、最长多久恢复（RTO）？默认如上。

### 5.2 机制与凭据

| 项 | 做法 |
|---|---|
| 备份内容 | `pg_dump` custom 格式（备份镜像从 PGDG 安装 `postgresql-client-18`）；北京时间每日一次；周一额外写周备份前缀 |
| 加密 | **客户端加密**：age 公钥在主机上，**私钥由 Owner 离线保管，不在主机、不在对象存储**；明文 dump 含管理员口令哈希、会话、反馈联系方式与截图、付费回执，一旦对象存储静态密钥泄漏就等于全库泄漏，所以不上传明文 |
| 目的地 | 私有、版本化、开启服务端默认加密的 COS 备份桶，`daily/`、`weekly/` 前缀；桶不允许强制清空与销毁（旧站配置为 `force_clean=false`、`prevent_destroy=true`，旧 `infrastructure.md:105-111@main`）；上传密文与 SHA-256 侧文件 |
| 凭据 | **只写**（Put/List、无 Delete）的专用子账号，或 STS 短期凭据；放 root 专属文件，不用主账号 AK，不存数据库设置表，不在命令参数与日志中出现；只接受 `cos://` 路径，不接受签名 URL。AIHOT 的 `operations/backup.ts` 用环境变量或设置表里的静态密钥，不沿用其凭据方式，只沿用“校验过的 custom dump + 上传”思路并升级到 PostgreSQL 18 客户端 |
| 备份角色 | 专用备份数据库登录，只读；与公开响应、通用管理入口无关（`01-target-architecture.md` 9.1） |
| 对象存储创建 | 创建桶、命令行工具、子账号是 Owner 逐次批准的云写操作（第 1 节），M0 前置 |

### 5.3 保留与体积

- 默认保留 **7 个日备份 + 4 个周备份**；月备份是可选项（成本极低，开不开由 Owner 定）。**以上数字是默认值，可配置，不是 Owner 要求**：A 把“30 天日备份 + 12 个月月备份”与【Owner 要求】任务书 §43 并列，而任务书 §43 只要求“显示备份状态”；A 自己的 PIT-058 引用的也是旧站“7 日 + 4 周”。A 原写法作废。
- COS 生命周期按北京时间每日异步扫描，服务端用 8 天与 35 天的安全边界（含非当前版本）：扫描窗口内对象数可能短暂多于 7/4，这不是恢复点丢失；**不得宣称精确到秒删除**。
- 备份体积与临时 dump 目录计入 20GB 系统盘预算，临时目录有上限；本机只保留最近 3 份（AIHOT 同款做法）。

### 5.4 恢复演练（每月一次）

旧站备份脚本早已写好，但生产备份与隔离恢复始终没有完成记录（PIT-058）。演练规则：

1. 频率：**公网发布（首次生产部署）前完成一次空机隔离恢复演练**（旧ADR-0010:27@main）；切换（M5）前再做一次；此后**每月一次**。
2. 恢复到**随机命名的隔离库**，禁止指向生产库。覆盖三个点：**最新日备份、最旧保留日备份、最新周备份**。先做“只下载、校验 SHA-256、解密、`pg_restore --list`”，再完整恢复。
3. 核对：迁移版本、发布标识或活动内容版本、各表计数、用量账本（已花/预留/未知）、下架集合、人工修订；记录实际 RTO（目标 ≤2 小时）。
4. **失败不覆盖现有库**：保留当前数据库与上一份可验证备份，调查后重新演练；演练结束清理隔离环境与短期凭据。
5. 结果**经告警推送**（成功一条摘要、失败即时告警、超期 >35 天未成功告警）并可由只读运维 MCP 查询，**不做页面**（不设运营台）。
6. 演练记录表同时收录“负责人恢复”季度演练（`06-security-and-access.md` 3.1），字段：日期、类型、点位、耗时、结果、发现的问题。
7. “备份文件存在”不算恢复成功（F-044）。

### 5.5 恢复不变量（从 B:BR-52、T-084 移植）

- 恢复后**先套用最新抑制集**，不复活已撤回（下架）内容；恢复后仍须做当前权限与撤回检查。
- **不重复收费**：账本恢复后对账；结果未知（unknown）的预留保留，不因恢复而“释放”。
- 许可已到期的原文，不因备份恢复而重新公开（F-044；`06-security-and-access.md` 第 5 节）。
- 恢复不能让已下架的对象在任一出口重新可见：演练用例含“下架 → 备份 → 恢复 → 各出口不可见”。

### 5.6 原件与对象存储

- 获准保存的原始网页、PDF、附件、截图与报告产物存对象存储（ADR-0005），数据库只存键、哈希、大小、媒体类型、权限版本与到期时间；原件与备份**分桶、分权限**（备份桶只写、无删除；原件桶按进程前缀授权，见 `06-security-and-access.md` 4.2）。
- 原件桶开启版本控制；数据库 dump 含对象键、不含对象本身；恢复演练增加“悬空对象键”检查。保存与否由权限矩阵的“保存全文”能力决定，未获准的只存元数据与链接。

## 6. 可观测与告警

### 6.1 日志与业务运行记录

- 结构化 JSON 日志（带 `trace_id`、业务线、模块、任务、信源、材料 ID），不记录密钥与正文全文；按日轮转保留 14 天，**并设体积上限**（容器日志驱动 10MB × 3，3.4）；脱敏键见 `06-security-and-access.md` 2.2。
- 业务运行记录（采集运行、模型调用、发布、失败任务）写入业务表，明细保留 30–90 天后汇总为日聚合（ADR-0020）；由只读运维 MCP 查询，不设运行页。
- 代码层用 OpenTelemetry API 打点、默认不导出；trace 后端在“跨进程排障连续两次依赖手工拼日志”后再引入。

### 6.2 健康检查

| 端点 | 规则 |
|---|---|
| `/healthz` | 进程存活；不碰数据库；**只在内部网络可达** |
| `/readyz` | 数据库与发布读取可用；**不对公网开放**（旧站曾因公网 `/readyz` 暴露数据库就绪检查被当作缺陷，`docs/runbooks/production-deployment.md:77,130@main`） |
| 公开新鲜度探针 | 公网唯一探针（`GET /api/v3/freshness`，OUT-16，契约 §2.13）：经限流，返回各业务线最近公开时间、最近一次计划检查成功时间与发布标识；供外部拨测使用（契约写入 `03-data/02-public-api-contract.md`） |
| worker 心跳 | 每个实例有自己的心跳键；另有 lane × stage 的队列最老年龄 |

**页面正常、容器健康、worker 心跳都不能单独证明内容在持续更新**（INV-30；旧站 2026-09-15 起停更 5 天，进程心跳与容器健康全程“正常”，`docs/reviews/product-production-audit-20260920.md:16-20@main`）。

### 6.3 三层告警（D15-secops-007；F-057）

应用内告警在最需要它的时候（主机宕机、Docker 挂掉、磁盘写满、证书过期、worker 被暂停但进程还在）恰恰最先失效，所以必须有独立于应用的检查：

| 层 | 谁发出 | 内容 |
|---|---|---|
| **(a) 应用内业务告警** | worker 的 ops 定时任务计算 → 推送 | 6.4 的业务条目：新鲜度（两线分别）、暂停超时、单源连续失败、队列积压、用量提示、用量预警与异常熔断、发布、备份、磁盘、登录异常、高风险私有操作 |
| **(b) 独立于应用的外部检查** | 云监控 + **不在同一主机上的**外部拨测 | 云监控：CPU、内存、磁盘、带宽与流量包、实例到期。外部拨测：每 5 分钟探测公开首页与公开新鲜度探针，首页非 200 连续 2 次，或新鲜度超过阈值，即告警。拨测服务选型与费用由 Owner 批准（腾讯云云监控站点拨测或等价的外部服务） |
| **(c) 日程型到期预警** | 同一外部渠道 | 服务器、域名、证书剩余少于 14 天；模型供应商余额或预付额度低于预计 7 天用量；COS 容量超过 80%；互联网新闻信息服务许可证有效期临近（有效期由 Owner 提供；默认提前 60 天预警，可配置，【设计】） |

### 7.2 内存与资源口径

监控与验收统一使用 **MemAvailable** 与容器 cgroup **工作集（working set）**；不把低 MemFree、页缓存或“used”当作内存耗尽依据（旧仓库观察器用 MemAvailable <10% 连续 3 个采样）。告警阈值见 6.5。

### 7.3 带宽与流量

服务器 3Mbps 出口、300GB/月流量是硬顶：月流量 70%/90% 告警；首屏字节预算、图片代理缓存命中率进入容量记录；图片不在站内托管第三方 Logo、徽章与附件（`06-security-and-access.md` 第 5 节）。

### 7.4 扩容触发线（旧ADR-0010:29-34@main，默认值，可配置，接入外部云监控告警）

| 触发线 | 动作 |
|---|---|
| CPU 持续 >70%，或高优先级来源连续两轮漏调度 | 增加 worker（当前节点转采集节点） |
| 内存长期 >75%、数据库 >12GB 或恢复 >2 小时 | 迁移托管 PostgreSQL；同时评估 5.1 的时间点恢复 |
| 公共文档 >10 万，或搜索 p95 >300ms 且独立搜索引擎基准显著改善相关性 | 先评估 PostgreSQL 内的中文分词扩展，再评估独立搜索服务 |
| 流量、攻击或带宽成本达预警线 | 评估 CDN/WAF（内容版本号作缓存键，下架仍即时生效） |
| 浏览器/OCR 池成为测得的瓶颈，或发生隔离事故 | 水平扩展 fetcher 或迁到第二台机器（接口不变） |

不为未来规模预购闲置资源；任何扩容都需要成本与恢复方案，并经 Owner 批准费用。B 的压测基准任务保留，4C4G 等价档作对照档。

### 7.5 旧机数据点（仅作参考，不是规则）

- API 给 1 核、256MiB 才使冷读过 10 秒超时；只给 0.5 核时冷读超时（`docs/architecture/decisions/0035-measured-reader-capacity.md:8-26@main`）。
- worker 在 640MiB 下一次只能抓一个信源；API 曾用到 234.9/256MiB（PIT-057）。
- 4GB 节点 24 小时浸泡无 OOM、磁盘保留 30% 以上（旧ADR-0010:42@main）。

### 7.6 扩源批次记录

每次新增信源批次后记录资源占用与单位成本；扩源容量按实测推算，不按预估承诺。

## 10. 验收要点（AC-OPS）

编号 AC-OPS-nn 为本包新增，与 `06-security-and-access.md` 第 7 节的 AC-SEC-nn 配套；A 的 AC-M1-14 只说“备份成功并完成一次恢复演练”，AC-M1-03 是 24 小时内容无人值守而不是资源浸泡，都没有可判定的阈值。建议在 `05-quality/04-acceptance-criteria.md` 的生产切换关（G5）引用。

| 编号 | 验收 | 判定 | 来源 |
|---|---|---|---|
| AC-OPS-01 | 备份加密与凭据 | 桶私有、版本化、服务端加密；对象是 age 密文（未解密不能 `pg_restore --list`）；凭据为只写子账号或短期凭据，无 Delete；仓库与日志无密钥 | D15-secops-001 |
| AC-OPS-02 | 隔离恢复 | 随机命名隔离库；最新日备份、最旧保留日备份、最新周备份三点都恢复成功；RTO ≤2 小时；迁移版本、计数、用量账本、下架、人工修订核对通过；恢复后不复活撤回、不重复收费、unknown 预留保留 | 旧ADR-0010；B:T-084 |
| AC-OPS-03 | 旧库存档备份（不导入） | 切换前旧生产库加密全量备份在隔离库恢复校验通过；用于存档，兼作切换窗口内中止切换的兜底，不导入新系统，切换完成后不再用于恢复旧站服务；默认保留至旧站退役后 ≥30 天（Owner 可改） | D15-secops-002 |
| AC-OPS-04 | 24 小时资源浸泡 | OOM = 0；非预期重启 = 0；磁盘余量 ≥30%；已用 <20,000,000,000 字节；以 MemAvailable 与工作集为口径 | 旧ADR-0010:42@main；R16-docs-003 |
| AC-OPS-05 | 磁盘回收 | 连续发布 N 次后残留容器、镜像、网络、目录数量恒定；无 prune、无删卷；预检不足时发布失败且不新增暂停 | PIT-053；D15-secops-013 |
| AC-OPS-06 | 发布与回滚 | 在每一步注入失败都回滚，且回滚后重跑检查；“上一版本冒烟失败”与“数据库已激活但主机切换未完成”两点注入通过；进程被杀后对账成功；Owner 暂停在部署期间保持有效；从主机之外读回的发布标识头等于目标 SHA | D17-pitfalls-003；D15-secops-018 |
| AC-OPS-07 | 外部告警演练 | 人为停掉 worker、再人为停掉整个应用，外部渠道在阈值内各收到告警；资讯线与法规线分别停更各触发并指明业务线；推送失败下个周期重试 | D15-secops-007；F-057 |
| AC-OPS-08 | 告警内容与去重 | 消息不含密钥、正文、个人信息；每 100 元用量提示在跨档时各触发一次且不重复刷屏；逐步上升的熔断指标达到阈值的 70% 时先收到预警（只提醒、不暂停，写明指标、当前数值与涉及的能力或来源），达到阈值才熔断；异常熔断触发一次推送并写明范围与恢复入口；恢复后收到“已恢复” | OP-20；F-057；BR-COST-19、20 |
| AC-OPS-09 | 入口层切换演练（预发） | 证书状态迁入后没有重新签发；HTTP→HTTPS；每个公开页同时显示 ICP 备案号与公安联网备案号且链接正确；发布标识头读回一致；“撤回公开入口”与“窗口内中止切换、原样启动旧栈”各演练一次（都不回写数据） | D15-secops-012 |
| AC-OPS-10 | 三类回退分开演练 | 代码回退、内容指针回退、数据回退各一次，记录耗时与结果 | B:M5 |
