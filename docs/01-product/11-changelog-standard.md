# 读者更新日志标准

Owner 2026-11-06 确认（“可以，按这个标准执行，旧条目也按你的建议处理”），TASK-0564。适用于所有改动网站的人和 Agent；与 `03-reader-pages.md` PG-13“内容规则”冲突时，以本标准为准。

适用于所有改动网站的人和 Agent。目的：读者打开更新日志，看到的每一条都是对自己有用的变化，用的是读者能直接看懂的话。

## 一、写不写

先问三个问题，三个都答“否”就不写：
1. 读者会注意到这个变化吗？
2. 注意到以后，读者能多做一件事、换一种用法，或者明显更方便吗？
3. 不告诉读者，读者会困惑、找不到东西吗？

写：
- 新功能、新栏目、新页面、新入口。
- 读者的用法变了：栏目位置、筛选方式、首页内容、默认设置。
- 内容范围变了：新增某类来源、某个栏目暂停或恢复更新。
- 读者明显能感到的改进，如同一件事不再重复出现、返回列表不丢位置。几项小改进先攒着，合成一条再写。
- 功能下线、栏目暂停。写过暂停公告的，恢复时必须再写一条。

不写：
- 小的视觉调整：图标、颜色、动画、间距、字号。
- 读者察觉不到的修复和改进：提示文字措辞、备案号显示、浏览器标签和搜索结果里的站名与图标、小幅提速。
- 只影响后台、运营或开发的改动：模型、评分规则、缓存、测试、部署、Agent 协作。
- 更新日志页面自己的改动。
- 每天新收录的新闻（这不是网站更新）。

拿不准就先不写，在 PR 说明里写“更新日志：未写，理由……”，由 Owner 决定。

## 二、类型

- 重大更新：大版本改版，带版本号（如 2026.11）。只用于 Owner 认定的大版本，上线前给 Owner 看预览。
  - 界面改版的重大更新要配“改版前后”对比图（Owner 2026-11-06：“这些应该用图片说，以前什么样子现在什么样子”）：每项界面变化一组，旧版和新版是同一页面、同一份演示数据、同样大小的浏览器截图；标识和手机页并排放，其余叠放可拖动比较。截图不得出现备案号；图片放在 `apps/web/app/features/changelog/compare-<版本>/`，由该版本的展示组件引用（2026.11 见 `Showcase202611.tsx`）。
- 更新：新功能、新栏目、新入口。
- 优化：已有功能更好用。
- 公告：测试版、暂停、恢复、规则变化这类需要读者知道的事。上线前给 Owner 看。
- 下线：去掉某个功能或栏目。

## 三、怎么写

- 标题：不超过 24 字，写读者得到什么，不写我们做了什么工作。
  - 好：“首页新增资讯地图”“同一件事的报道不再重复占精选”。
  - 不好：“优化内容版本校验”“若干体验优化”。
- 要点：普通条目 1–3 条，重大更新最多 10 条。每条一句话，先说变化，再说对读者有什么用。
- 举例：不拿具体公司、人名或品牌举例（Owner 2026-11-06：“不要说必和必拓这些举例”），写规则本身即可。
- 用词：
  - 用读者的话，不用技术词（接口、缓存、模型、部署、服务器、HTTPS、连接之类，已有自动检查）。安全、速度这类改进写读者能感到的结果，如“网站安全防护更强了”“页面打开更快了”，不写用了什么技术（Owner 2026-11-07）。
  - 不写空话：“若干优化”“提升体验”“全面升级”“例行维护”。
  - 不写测试数量、调用次数这类内部数字；读者关心的数字可以写，如“9 个分类”。
  - 不夸大：没全部完成就写清进度，不写“全部”“彻底”。
- 不写：提交号、PR 号、任务卡号、内部人员和 Agent 的名字。
- 一次上线最多写一条；同一主题几天内的连续改动，合成一条。

## 四、怎么做（每个 PR 都照做）

1. 按第一节判断写不写：
   - 写：在 `changes/` 写 `audience: 读者` 的片段，并更新 `industry/release-note.json`。
   - 不写：写 `audience: 运营` 的片段，只留内部记录，不进读者更新日志。
2. 重大更新和公告，上线前给 Owner 看预览。
3. 已上线的条目要改写或去掉：在 `industry/changelog-copy-edits.json` 里改写（`copy`）或去掉（`copy: null`），原始登记记录保留。
4. 审查时核对：标题字数、类型、技术词由程序自动检查；是否该写、是否空话由审查人按本标准检查。
