# 包二上线前的生产只读测量

最后核对：2026-11-21。

包二（内容）里有一批规则门槛先用了起始值：判“旧闻”的天数、事件归组的相似度门槛、PDF 页算“有文字”的字数等。这些值要用生产数据定下来再上线。本页说明部署端怎么在生产库上**只读**地跑 `scripts/measure/package2/` 里的三份 SQL，以及回传什么。

| 文件 | 内容 |
|---|---|
| `scripts/measure/package2/events.sql` | 跨稿件：哪些报道是同一件事、新旧判断、日报头条与热榜（编号 M） |
| `scripts/measure/package2/articles.sql` | 单篇稿件：公司名、电头、国家、核对的成本（编号 L） |
| `scripts/measure/package2/policy-pdf.sql` | 法规 PDF 每页的文字量（编号 N） |

## 只读怎么保证

1. **文件本身**：每条都是单独一条 SELECT（或 WITH … SELECT）。`tests/measure-sql.test.ts` 检查文件里没有写入、加锁、改设置或控制事务的语句，并在迁移过的测试库上用只读事务逐条跑一遍，核对列名与文件头一致、主要数字与小样本一致。
2. **会话**：下面的命令把会话设成“默认只读事务”，数据库会拒绝任何写入。
3. **时限**：每条最多跑 5 分钟，等锁最多 2 秒；超时就放弃那一条，不会拖住线上。

## 什么时候跑

- 避开发布窗口和出刊时刻，选服务器负载低的时段（北京时间凌晨）。三个文件逐个跑，不并发。
- 只需跑一次。某条超时就照实回报，不要放宽时限重跑。

## 怎么跑

文件会随整个仓库进镜像（在镜像的 `/app/scripts/measure/package2/` 下），但没有任何进程读取它们，所以不必等发布：在服务器上把合并后 main 里的三份文件放到一个临时目录（已发布过的话，也可以从镜像里取：`docker compose exec -T api cat /app/scripts/measure/package2/<文件名>.sql`），在该目录执行：

```bash
for f in events articles policy-pdf; do
  docker exec -i \
    -e PGOPTIONS='-c default_transaction_read_only=on -c statement_timeout=300s -c lock_timeout=2s' \
    amp-db-1 psql -X -q -P pager=off -U amp -d amp -f - < "$f.sql" > "measure-$f.out" 2>&1
done
```

不要加 `ON_ERROR_STOP`：一条出错不影响其余各条，错误信息会一起写进输出文件。

## 回传什么

- 把三个 `measure-*.out` 原样贴到协作看板 #348（太长就作附件）。每行第一列是测量编号（如 `M1a`、`L4b`、`N1`），不用另加说明。
- 输出里只有计数、分布、编号（稿件编号、信源编号、事件编号）和公司名，没有正文，也没有读者、账号或密钥信息。不要附带其他查询结果或服务器信息。
- `M5d` 是 50 条稿件编号，由 Claude 在后台逐条阅读标注，部署端不用处理。

## 每条测量决定什么

| 编号 | 看什么 | 决定什么 |
|---|---|---|
| M1a、M1b | 每天的归组决定数、其中调了模型的数量与费用 | 新归组规则的模型调用不能多于现在（对照基线） |
| M2a、M2b | 14 天候选池有多大、多少有向量、向量对应的是哪段文字 | 新归组的向量缓存大小；读向量前要不要先粗筛 |
| M2c | 有史以来的嵌入（向量）付费请求，按服务、模型、状态 | 现网归组是否用过向量（预期没有，与 M2b 一致）；把“开向量”交 Owner 决定之前的事实依据 |
| M3a | 模型判过的候选相似度与判定结果。没开向量时（生产至今）这个分数是**字面重合度**（相邻两字的重合比例，短的整个出现在长的里面就是 1），不是余弦值 | 现网的 0.85（需复核）、0.92（免复核）在字面重合度上实际怎么起作用；在有向量之前，说明不了余弦门槛 |
| M3b | 同一事实下报道两两的向量余弦（没有向量时为空） | 有向量之后，0.92、0.85、0.6 三个余弦门槛 |
| M4a、M4b、M4c | 内容完全相同的稿件；同一信源同标题换了地址；同一地址被多个信源采到 | 旧文换地址重采的规模；只靠完全相同的指纹够不够；48 小时重采窗口 |
| M5a–M5d | 模型给的发生日期：有多少、多少在原文里写着、多少是月末或季末；发布比发生晚几天；按信源看；50 条抽样 | 判“旧闻”的天数（起始 4 天）和迟到报道的时限（起始 72 小时）；单条日期能不能单独把稿件判旧 |
| M6a、M6b | 同一事实的各篇报道日期是否一致；后续报道晚到多久 | “日期相差太远”的 7 天规则；跟进报道的扣分 |
| M7 | 最近 30 期日报的头条：是否连续同一事件、头条的信源数与分数、按分数排是否会换头条 | “同一事件连上三天头条”“按信源数选头条”两个问题有多常见 |
| M8 | 热榜条目里，领头事实超过 72 小时的有多少 | 热榜对旧事件是下沉还是只加标注 |
| M9 | 60 天内人工纠正归组的次数 | 新旧归组一致性报告有没有足够的人工标注 |
| M10 | `articles` 表现有的索引 | 内容指纹的索引是否已在（新归组按地址和指纹查重的前提） |
| M11 | 每天触发重新发布的事件数 | 事件排序投影任务每天的工作量 |
| M12 | 事实按报道数的分布 | 每次发布重算排序锚点的成本 |
| M13 | 近 30 天同一篇稿件（内容指纹相同、正文至少 500 字节）被不同来源采到、且至少两份已被现网归进事实（现网只归编辑类、通过相关性的稿件；并入已有事实的历史稿也算）：现在分在几个事件里 | `split_across_stories` 是“该归没归”的重复稿规模的下限（换了说法的重复认不出来，所以只是下限）；是否值得把“开向量”交 Owner 决定 |
| L1a–L1c | 表的大小、正文总量、每天的分析数 | 回填要跑多久；新表是否一开始就要定期清理 |
| L2a、L2b | 模型给出公司编号的比例与分布 | 实体库的种子；模型没给主体时的规则 |
| L3a–L3c | 出现最多的 300 个事实主体、主体总数、信源登记的所属公司 | 实体库先收哪些公司；哪些登记值能直接用 |
| L4a、L4b | 公开标题和导读里“中文名（英文名）”的写法，同一英文名有几种中文写法 | “一家公司两个中文名”问题的规模和变体清单 |
| L5a–L5c | 正文开头的电头（通稿、通讯社、其他）按语言分布；与已存国家归属对照；国家标签不在归属国家里的条目 | 电头规则是否要区分通稿与通讯社、从哪天起生效、是否连带去掉国家标签 |
| L8a、L8b | 近 7/30/90 天公开条目中有英文版的数量；地理判断的理由分布 | 改写历史条目公司名的代价（英文版要重做）；是否补国名形容词和省名 |
| L9 | 各类模型回执里最早还保留回答的时间 | “同一版本重判不再付费”能回溯多久 |
| L10 | 同一版本被重复判断的次数 | 公司名为何要按版本固定 |
| N0 | 法规原件按类型统计、已有文字抽取的比例 | N1、N2 覆盖了多少 PDF |
| N1、N2 | PDF 每页可见字符数的分布；10/20/50/100 字门槛下文字、扫描、混合文档各多少 | PDF 页算“有文字”的门槛（目前定的 20 字是猜的） |

编号沿用设计里的测量顺序，L6、L7 不在本包里（见下）。

N1、N2 只统计完整解析过的 PDF。因页数、字数超限或解析失败而中途停下的 PDF 只存了一部分页甚至没有页，算进去会把它们误当成扫描件，所以跳过，只在 N0 的 `capacity_or_unparsed` 里计数。目前法规信源的抽取设置大多只允许 1 页，多页 PDF 都会落在这一列。如果 N0 显示这类 PDF 占了大头，N1、N2 就不足以定门槛：法规新写入侧（计划 2.13）合并前，还要对 `policy.original_resources` 里的 PDF 原件另跑一次只读的逐页文字统计。

## 不在本包里的测量

- 数字核对的“硬/软”不符比例（L6）和只看原文识别主体的准确率（L7）：要用这一轮新写的核对代码在生产数据上跑，等核对上线后用只读脚本另测。
- M5d 的人工阅读：Claude 拿到编号后在后台完成。
- 没有用 `EXPLAIN`：M10 直接列出索引定义，按地址或指纹查询能不能用上索引由此即可判断。M2c 和 M13 是后加的，在本机造的库上看过执行计划（30 万篇稿件、12 万个事实、50 万条回执）：M2c 走回执的服务索引，约 30 毫秒；M13 顺序读近 30 天的稿件一次（正文长度要读正文），再按内容指纹索引和成员索引逐组查，三次约 0.24–0.39 秒。

## 修改这些文件时

新增或修改测量后，在本地对临时库跑：

```bash
DATABASE_URL=postgres://…/<名字以 _test 结尾的库> npm test -- tests/measure-sql.test.ts
```

它检查只读、文件头（测什么、决定什么、输出哪些列）、列名，并用小样本核对主要数字。
