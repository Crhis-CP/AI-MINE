# 单篇核对影子（开关 `observe.articles`）

最后核对：2026-11-20。

包二的“单篇核对”先以影子方式运行：资讯的判断落库后，worker 在一个单独的队列里（`news.enrichment.observe`，一次一条）做四件事：认出稿件里的公司（公司库）；预演中文稿的公司名按“一家公司一个中文名”会怎么改；核对中文稿里的数字和日期在原文里有没有依据；读出正文开头的电头，并记下哪些国家只来自电头。结果只写 `entities.article_links` 和 `enrichment.analysis_checks` 两张表。**不调用模型，不改判断（`analyses`）和公开内容（`publications`），读者看不到任何变化。** 代码在 `packages/backend/src/pipeline/understand/observe.ts`。

哪些判断会核对：过了预筛、不是 BLOCK、属于稿件当前修订的最新那次完整判断。BLOCK、正文不到 20 字还在等的、要先去抓网页的、做完时稿件已经有了新修订的，都不核对。

稿件处理只在判断落库、发布投影之后往队列里排一个任务（先读一次开关，开关一分钟内只读一次）；排队失败只记日志，核对任务失败也只影响它自己，稿件照常处理、照常公开。

## 上线前提：数据库授权

包二的迁移新建了 `entities` 这个 schema。生产库如果按角色分开登录，发布跑完迁移后必须按 `database/roles/README.md` 重新执行一次授权（`node scripts/db-roles.ts … --apply`），否则 worker 没有这个 schema 的使用权，核对会全部失败（每日对账会显示核对没跟上或计数读取失败）。仍用单一数据库登录时不需要这一步。

## 开关

设置键 `observe.articles`（归 enrichment 模块）。**没有这个键就是开着**；值为 `"off"` 时关闭：不再排新任务，已经排着的任务取出后什么也不写。改完一分钟内生效，不用发布，也不用重启。

在生产库执行一条语句即可（例如 `docker exec -it amp-db-1 psql -X -U amp -d amp` 打开会话后执行）：

```sql
-- 关闭
INSERT INTO settings (key, value, updated_by) VALUES ('observe.articles', '"off"', 'ops')
ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value, updated_by = EXCLUDED.updated_by, updated_at = now();

-- 重新打开
DELETE FROM settings WHERE key = 'observe.articles';
```

确认：`SELECT value FROM settings WHERE key = 'observe.articles';` 查到 `"off"` 是关着，查不到是开着。关着时每日对账会写“开关关着”。

## 要撤掉这段代码时：先关开关，等队列排空

直接回退代码会留下排着的 `news.enrichment.observe` 任务：没有了处理它们的程序，任务会一直排着（排着的任务队列系统保留约两周），还会触发现有的“后台任务排队超过 2 小时”告警。按这个顺序做：

1. 用上面的语句关掉开关。
2. 等一分钟以上，再查队列里还有没有排着的任务，直到查不到为止（关着时任务取出就结束，通常几秒内排空）：

   ```sql
   SELECT state, count(*) FROM pgboss.job
   WHERE name = 'news.enrichment.observe' AND state IN ('created', 'retry', 'active') GROUP BY state;
   ```

3. 再回退代码。两张表里已写的记录留着无害（迁移只增不删）。

## 上线后做一次：导入公司库

公司库的第一批行来自代码里已有的公司清单（目前 38 家公司，连同写法、股票代码和网站共 171 条）。导入只增不改：已有的行不动，以后哪次发布给代码种子加了公司，再跑一次只补新增的。

```bash
docker compose exec -T api node scripts/entities-seed.ts           # 预演：只数，不写
docker compose exec -T api node scripts/entities-seed.ts --apply   # 导入
```

用 api 容器，因为公司库只有后台账号（private_ops）能写，worker 只能读。没导入之前核对照常运行：公司按代码里同一份清单在内存里认，但认出的公司存不下来，每日对账会写“公司库还没导入”。

## 可选：免费回填历史

给已经判断过的稿件补做核对，不花钱、不调模型。只处理每篇稿子最新的那次判断。**不是只增**：和 worker 一样，每核对一个修订，就先删掉这个修订里程序认出的公司关联再写新的（人手加的关联不动）；同一次判断的核对记录只写一次。所以重复跑安全，公司关联总是按当时的公司库。先导入公司库再回填，否则公司关联存不下来。

```bash
docker compose exec -T worker node scripts/entity-links-backfill.ts --since 2026-11-01           # 预演：跑核对，只出计数
docker compose exec -T worker node scripts/entity-links-backfill.ts --since 2026-11-01 --apply   # 写入
```

- 日期按北京时间；`--until` 不含当天，默认到现在。
- 开始时从最新的判断往回找一次这几天的编号范围，然后按编号一页一页读（`--batch`，默认 200，最多 1000），不会扫整张判断表。
- `--limit N` 本次最多处理 N 条，输出最后给出续跑用的 `--after`。
- 参数写了却没给值（例如末尾的 `--limit`）会直接报错退出，什么也不写。
- 用 worker 容器，因为核对记录表只有 worker 能写。

负载：回填是一个单独的进程，一条接一条地跑。每条核对本身在常见稿件上只要几毫秒，最长的稿件约 50 毫秒；默认每条之间停 20 毫秒（`--pause-ms` 可调大）。所以它在跑的时候最多大约占一个 CPU 核的一半到三分之二，并持续读写数据库。请在服务器空闲时（北京时间凌晨、避开出刊时刻）分批跑。

## 每天看什么

每日对账在“译文”一行后面加几行，只说计数：

| 行 | 什么时候出现 | 意思 |
|---|---|---|
| 单篇核对 | 昨天有判断时 | 昨天判断了多少条、其中核对了多少条、认出至少一家公司的多少条。回填的历史稿件不算进当天 |
| 单篇核对需要看一下 | 开关开着，但核对的不到判断的九成，或队列里有失败任务 | 核对没跟上或在失败；去后台“运行”页和 worker 日志看原因 |
| 数字核对 | 有核对时 | 程序拿不准的数字或日期多少处、在几条里。程序判为“多半写错”的那一类只记在表里，不进对账，等人工抽查证明它可靠之后再报 |
| 电头 | 有核对时 | 正文开头是企业新闻稿电头、通讯社电头、只写地点和日期的各多少条 |
| 开关关着 | 开关关着时 | 说明这一天没有核对，免得和“坏了”分不清 |
| 计数读取失败 | 这些数读不出来时 | 只少这几行，其余对账照常；原因在 worker 日志（`article check counts unreadable`） |

运行失败去哪里看：任务失败自动重试两次，仍失败就在队列里记为失败（失败的任务保留约一周）。每日对账的“需要看一下”那行会写队列里有几个失败任务；后台“运行”页的“24 小时内失败的队列任务”按队列列出次数；worker 日志里是 `article observe failed`（核对失败）或 `article observe not queued`（没排上，这种只在日志里）。

## 数据与负载

- `entities.article_links`：每篇稿子当前修订认出的公司（正文里的写法、发布方网站、信源所属公司）。同一修订再核对时整组替换，人手加的关联保留。不随保留期清理。
- `enrichment.analysis_checks`：每次判断一行（数字核对的结论与发现、公司名会怎么改、电头和会被降级的国家及其引文），保存 180 天，由每日保留期任务清理；清理失败只记日志，不影响其他清理。
- 读多少：核对只读判断步骤看到的那部分原文：标题、正文前 18,000 字加最后 2,000 字（模型每一步最多读 20,000 字），正文没有可用文字时读信源摘要；不读存下的中文译文。在 4 核 2.1 GHz 上实测，常见稿件每条几毫秒，最长的稿件（20 万到 100 万字的密集中文数字、报表）每条约 50 毫秒，第一条约 95 毫秒，中间分四段，每段之间把事件循环让给其他任务。
- 还有一项没有被这个上限管住：稿件输入是用分析自己的读取函数读的，会读进整页正文；页面里有嵌入卡片（`<figure>`）时它要把整页解析一遍，1 MB 这样的页面约 180 毫秒，这和分析这篇稿子时付出的一样。
- 队列：一次一条；有任务时连续取，空闲时每 5 秒看一次。每条读一次稿件输入；公司库放在内存里，库变动后或每 10 分钟重建一次。

## 现在不做的

不改稿、不扣稿、不改国家归属和标签；认出的公司还不进读者的筛选和搜索；公司库的合并与撤销已有函数，后台页面还没有。这些在后续批次。
