# Claude × Codex 协作约定（第二阶段）

Owner 2026-11-06：“我希望你可以在仓库中和 codex 达成协作交流，你给我提示词，我给他，之后你俩合作分工，优化我的项目”；同时要求“修复问题的时候，让 Agent 学会举一反三，把同类的问题一起修复掉”。本约定对 Claude 和 Codex 都有效；与规则文件冲突时以规则文件为准。

## 一、分工

- **Owner（Chris）**：定方向、做决定，包括评分和规则调整、对外操作、付费、信源启用等（规则文件第 7 节）。把 Claude 写的提示词转给 Codex，也可以直接在看板上指示。
- **Claude**：负责全部开发工作，包括代码、测试、文档、设计、任务卡和 PR；读 Codex 的测试和审计结果，找出根因，按类修复；写给 Codex 的任务。
- **Codex**：负责线上这一侧：
  - 合并已通过 `make-verify` 的 PR：满足第七节常设授权条件的直接合并，其余等 Owner 当次授权；
  - 部署上线，上线后核对；
  - 做线上测试和只读审计，包括服务器、数据库只读查询和日志；
  - 把结果写成报告。

  Codex 不改代码、测试、配置和数据（任务里写明的 `.env` 改动除外），不开 PR；发现的问题不修，交给 Claude。

## 二、在哪交流

- **协作看板**：[第二阶段协作看板（Issue #348）](https://github.com/Crhis-CP/AI-MINE/issues/348)是总入口，每次交接（任务和结果）都在这里留言。长报告单开一个 Issue，在看板上留链接。
- **PR**：具体代码问题（审查意见、CI 失败）在对应 PR 里讨论。
- **仓库文件**：
  - 长期有效的约定写进本文件和规则文件；
  - 部署任务书写进 `docs/research/codex-*.md`。
- **Owner 转发**：Claude 写给 Codex 的提示词，Owner 可以直接转给 Codex；同一内容也贴在看板上，Codex 以看板为准。
- **第一阶段看板**：Issue #293 留作第一阶段记录，不再用于 Claude 与 Codex 交接。

## 三、消息格式

每条留言的第一行是标签，行末写状态：待办 / 进行中 / 完成 / 阻塞。

- **`【Claude→Codex】任务名 · 日期`** 写清：
  - 目标；
  - 前提：哪些 PR 已合并、对应哪个 SHA；
  - 步骤：可直接复制的命令；
  - 每一步的通过标准；
  - 什么情况下停下；
  - 报告写什么、写在哪。
- **`【Codex→Claude】结果 · 任务名 · 日期`** 写清：
  - 每一步的结果表（命令、期望、实际、是否通过）；
  - 原始输出，放在代码块里；
  - 异常时附日志最后 200 行；
  - 观察到的现象，只写现象，不写修法；
  - 没做的步骤及原因。
- **`【Claude】已处理 · 任务名`**：Claude 读完结果后写处理情况：开了哪些 PR、哪些问题还没处理、下一步做什么。

## 四、交接规则

1. Codex 开始前先读看板上最新一条【Claude→Codex】；同一任务以最新一条为准。
2. Codex 正在操作的分支，Claude 不推送。Codex 把 main 合入分支时用普通合并，不变基、不强推。
3. 每条命令只跑一次（批量任务除外）。网络超时可以重试一次；同一个错误出现两次就停下报告。
4. 留言、报告和仓库里都不写密钥、`.env` 内容、服务器 IP、备案号。
5. 需要 Owner 决定的事（规则文件第 7 节），双方都不替他决定，在看板上写明“需 Owner 决定”，并列出选项和推荐。
6. 读者更新日志按《读者更新日志标准》（`docs/01-product/11-changelog-standard.md`）执行。

## 五、举一反三（双方都适用）

- **Claude 修复问题、优化功能、完善视觉时，按“类”处理**：
  - 先说清问题的模式，再在全仓库（读者端各页面、后台、中英文、电脑和手机）搜出同类写法，一起修掉；
  - 能收进共用的函数或组件就收进去，并加防止复发的测试；
  - PR 和任务卡写明四件事：问题的模式、怎么搜的（命令或正则）、改了哪些地方、哪些同类有意不改及原因。
  - 只改了被点名的一处、留下同类问题的，不算完成。
- **Codex 测试和审计时同样按类报告**：发现一个问题，顺手查其他页面、语言和设备有没有同样的情况，在报告里成组列出。

## 六、一次完整的循环

1. Claude 开计划 PR（任务卡）和实现 PR，在看板发【Claude→Codex】：合并、上线、核对。
2. Codex 执行，回【Codex→Claude】。
3. Codex 按 Claude 的请求或定期做线上审计，报告单开 Issue，链接留在看板。
4. Claude 读报告、按类修复，回【Claude】已处理，进入下一轮。

## 七、常设授权、测试预算与安全测试（Owner 2026-11-07）

Owner 原话：“你负责修改代码和管控 codex，所以 codex 负责部署推上线和审计出报告给你，然后你再修复反馈给他，还得让它做好安全测试这些。很多让它可以上线去做，你要管控好它，防止它总是过度测试。”台账：“DEC-78补充·Codex 常设授权、测试预算与安全测试（Owner 2026-11-07）”。

### 1. 常设授权

- Claude 的 PR 同时满足下面三条时，Codex 可以直接 squash 合并，并按部署任务书上线，不必再等 Owner 当次批准：
  - 最新提交的 `make-verify` 全部通过；
  - Codex 审查一轮，没有 P0/P1 问题；
  - 看板上有对应的【Claude→Codex】。
- 带数据库迁移的照常先做快照，再迁移。
- 下面几件事仍须 Owner 当次批准：
  - 改 `.env`（任务里写明、且 Owner 已批准的除外）；
  - 删除生产数据或备份；
  - 付费、扩容；
  - 启用新信源；
  - 改评分规则；
  - 对外公告。

### 2. 测试预算（防止过度测试）

- **审查**：只审一轮，只看本次改动和它直接调用的代码；CI 已经跑过的测试不在本机重跑。
- **复审**：只看上一轮提出的问题。
- **上线核对**：只跑任务里列出的项目，每项跑一次，全部通过就结束。
- **全站审计**：只在 Claude 发出请求时做，或每两周一次；一次审计打开的页面总数不超过 400。
- **时限**：每个任务正常在 2 小时内交报告（等 CI 的时间不算）。

### 3. 安全测试

只读、不破坏。每次大版本上线后做一次，平时每两周一次。检查项：

1. 响应头：HTTP 跳转到 HTTPS、HSTS、CSP、X-Frame-Options、Referrer-Policy。
2. 未登录访问 `/admin` 和私有接口，应返回 401/403 或跳到登录页；公开接口不返回私有字段。
3. 页面和接口不泄露密钥、`.env`、内网地址或错误堆栈；`/.env` 和 `/.git/` 返回 404。
4. `npm audit --omit=dev` 的高危和严重项。
5. 对外开放的端口只应有 80、443 和 SSH。
6. 反馈接口连续提交 5 次应被限流；只验证限流，不做压测。
7. 证书剩余天数。

禁止：压测、暴力扫描、写入数据、登录爆破、对第三方站点做任何测试。

## 九、持续审计、联动清单与防止越改越差（Owner 2026-11-08）

Owner 原话要点：上线以后 Codex 持续审计，检测 bug、检查后端，有问题向 Claude 反馈，由 Claude 判断要不要优化，两边协同，把项目越做越好；改动要“牵一发动全身”地全面考虑；规则和公告必须先给 Owner 过目。

1. **持续线上审计（Codex）**：上线后不是只做一次核验。Codex 平时持续检查以下几项：
   - 读者页面和后台；
   - 处理流程有没有卡住、失败或反复重试；
   - 日志里的异常；
   - 花费有没有异常。
   
   发现问题按“结论、关键数字、证据、建议下一步”四段写在看板 #348。要不要改、怎么改，由 Claude 判断并写卡，Codex 不自行修改代码。
2. **联动清单（Claude）**：每张实现卡写一节“联动清单”，逐项列出改动会牵动的地方，没勾完的不提交。要查的地方：
   - 读者页（中文和英文）；
   - 后台；
   - 公开接口、RSS、MCP；
   - 用量记账和费用估算；
   - 告警；
   - 规格文档、更新说明和测试。
   
   比如换模型，后台的模型设置、记账类别、费用估算、告警阈值和文档要同时改。
3. **四道闸**（照 AIHOT 的 ADR-0007：每项 AI 能力 = 规则 + 评测集 + 评测脚本）：
   - **改动必附对比**：新旧两版在同一批样本上跑，列出多收、漏收和多花的钱；
   - **评测样本来自 Owner 的标注**：用刷卡校准台里的标注，不由 AI 自己判定；
   - **规则带版本号**：只有 Owner 确认过的版本才能用在正式站；
   - **上线后每周看指标**：看漏选、多选和花费，变差就退回上一版。
4. **Owner 先过目再写的事**：
   - 更新日志和大版本动画；
   - 精选、筛选、热点规则和门槛。
   
   写之前先停下，给 Owner 看方案，Owner 同意后再写代码。
5. **阶段收尾做全面协同审计**：3.0、3.1、4.0 每个阶段收尾时，Claude 审代码与文档，Codex 审线上，对照计划逐项核对，确认没有遗漏，也没有“局部改了、整体没跟上”的情况。
6. **防止过度防御、过度思考**：
   - 每次交接写清目标、准确版本号、通过标准和停止条件；
   - Codex 只复核本次改动的部分，不扩大成全面审查，已经核对过的内容不重复核对；
   - 已知偶发超时只重跑一次，同一个错误连续出现两次就交回；
   - 拿不准的地方由 Claude 当场裁定，只有花钱、改 `.env`、删数据、改规则、对外发布这五类事才去问 Owner。
7. **执行计划**：`docs/research/plan-3.0-20261108.md`，有 18 步，分 3.0、3.1、4.0 三个阶段。中途有新想法，先加进计划，再动手。
8. **分工调整（Owner 2026-11-08）**：Claude 做架构师和监管者，部分后端实现交给 Codex 写。本条覆盖 DEC-78 补充里“删除、参数化、评分更新、优化和 UI 改版都由 Claude 完成”中关于后端实现的部分，其余不变。
   - **Claude 负责**：
     - 整体架构；
     - 规则和门槛：编辑政策、评分、精选、筛选、热点；
     - 读者端和后台的前端设计与实现；
     - 写任务卡和接口设计；
     - 审查 Codex 写的代码，及时纠正写错的地方和过度设计。
   - **Codex 负责**：
     - Claude 指派的后端实现卡，例如模型供应商接入与故障切换、评测和回放运行器、批量脚本、信源配置；
     - 上线、线上核对和持续审计，与原来一样。
   - **每张派给 Codex 的卡，Claude 都要写明**：
     - 要做什么、不做什么；
     - 接口或函数签名；
     - 改动文件范围；
     - **代码量预算**，例如“实现约 150 行，测试只覆盖卡里列出的场景，测试代码不超过实现的 1.5 倍”；
     - 验收标准。
   - **Claude 审查时直接打回的情况**：
     - 超出预算；
     - 为卡里没写的情况额外加防御代码；
     - 卡里没要求就新建抽象层或配置项；
     - 测试远多于实现，或者在测同一件事。
     
     原则是“为了做一个鸡蛋，不重建厨房”：在合理范围内考虑周全，不为想象中的情况写代码。
   - **分支**：Codex 写代码用自己的分支（`codex/...`），Claude 审查通过后再合并；Claude 的分支 `claude/nice-newton-mew572` 仍只由 Claude 推送。
