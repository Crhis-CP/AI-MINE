# 多 Agent 协作的架构整理方案（2026-11-06）

Owner 2026-11-06：代码不冗余、架构清楚高效、运行稳定，并且能让多个顶级 AI 编程 Agent（不同厂商的模型）同时在仓库里工作、互不踩脚。本文是这次只读审计的结论和分步计划；第一步已在 TASK-0560 完成，其余按下表推进，标“需 Owner 决定”的到时单独问。

## 一、审计结论（数字来自 2026-11-06 对 `edc34c8` 的扫描）

- **代码本身不冗余**：生产代码重复率 0.49%（jscpd，60 个词元以上的重复块，44 处，共 583 行）；真正值得处理的只有几块（后台对账面板的旧副本、两个 SQL 检查脚本的公共部分、5 个网页测试里复制的启动代码、引擎与法规模块之间的两段复制）。死代码很少（knip：3 个文件、11 个导出）。不需要发起“去重运动”。
- **多 Agent 冲突主要来自“人工维护的登记文件”和“提交进仓库的生成文件”**，而不是业务代码：
  - 第二阶段 71 个改代码的提交里，两两改到同一文件的 1,094 对中，**680 对（62%）只撞在本可由脚本生成的文件上**；
  - 被改得最多的是任务卡索引 `tasks/INDEX.md`（第二阶段 107 个提交里 47 个），其次是发布说明 `industry/release-note.json`（23 个）、合并用的总卡（28 个）、`reference/contracts/manifest.json`、数据归属登记、迁移清单与写死数目的测试。
- **泳道（`lanes.yaml`）与代码已对不上**：152 条路径规则里 99 条匹配不到文件；501 张任务卡里 422 张用“架构”泳道（可改任何文件），TASK-0347 之后没有卡用其他泳道。整合卡 TASK-0528 的 `allowed_paths` 是一行 987 个路径，等于合并的全部改动，路径守卫实际没有起到约束作用，却多出两个“计划 PR”。
- **模块边界有回流**：`modules/policy` 用了后端 87 个入口里的 28 个；后端又通过 16 个转出文件反过来引用模块；后端内部有 33 对目录互相引用。
- **一致性问题**：国家别名分三处维护，已经出现分歧（“DRC”在检索里认作刚果（金），在归组的国家冲突判断里不认）。

## 二、这次已经做的（TASK-0560，低风险、收益最大）

1. **任务卡索引改为本地生成、不提交**：`node scripts/verify/tasks.ts --write-index` 仍可生成 `tasks/INDEX.md` 查看，但它进了 `.gitignore`，完整验证只检查任务卡本身。冲突最多的文件从此不再参与合并。规则文件第 6.3、16 节同步。
2. **国家别名一张表**：`@amp/industry/jurisdictions` 的 `COUNTRY_ALIASES` 同时供读者检索/筛选和归组的国家冲突判断使用，修正“同一国家两种叫法被当成两个国家”的问题；地理判断那一步的别名集合属于它已存结果的配方，单独维护（改它等于改配方）。
3. **删掉死代码**：后台对账面板里没人用、且已和运行页分叉的 `UsageReconciliation`；只剩一行转出、没有引用的 `publication/metal-prices/change.ts`。

## 四、不要改的（已经做得好的）

- 模块接入方式：`module.ts` → `site/modules` → `routes.ts` / `ServerModule`；
- Zod 契约加 OpenAPI 漂移检查、网页不直接连数据库与模型的检查；
- 按模块、按时间戳命名的迁移目录与已合并迁移的哈希冻结；
- 共享同一次加载的有界缓存、按发布区分的 CDN 缓存头；
- 归属与数据库角色检查本身（只改输入的来源，不放松规则）；
- 分类键集中定义、翻译类型检查。

## 五、给多个 Agent 同时工作的约定（在上述改造完成前就适用）

- 每个 Agent 在自己的 worktree / 分支里工作，一张任务卡对应一个目录范围；不同 Agent 的卡不重叠目录。
- 只改自己卡内的文件；需要共享区（公共类型、根配置、锁文件、组合根）的改动交给集成人。
- 不手改生成文件；需要的生成物在检查时生成。
- 每张卡自带验证命令，合并前在最终提交上跑完整验证；冲突只允许出现在业务代码里，并由改动的一方在自己的分支解决。
