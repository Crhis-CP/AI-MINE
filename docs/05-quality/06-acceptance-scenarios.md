> **结论**：本文件定义新项目的验收场景，不报告任何场景已经通过（交接时全部为 `not_implemented`）。场景来自 B 包（B:quality/01-acceptance-and-tests.md）的 T-001～T-096，**编号原样保留**；v2.0 在其后顺延新增 T-097～T-156，并按合并裁决改写了与裁决冲突的场景（见 0.5）；v2.1 再顺延新增 T-157～T-160，并按 Owner 2026-10-01 答复（含追加答复）改写或废弃若干场景（见 0.6）。每个场景都带**层**（L1～L6）、**级**（I/N/P）、**INV 与规则**和**通过判据**；一个场景要么有可数的通过判据，要么在判据栏写明 `not_evaluated` 的原因，不留空。

### 0.3 列的含义

| 列 | 含义 |
|---|---|
| ID | 场景编号，稳定，不复用 |
| Given / When / Then | B 的行为约束写法；Then 是可测断言 |
| 通过判据 | 数值或清单。写“同本节默认”表示以本节开头的默认判据为准；写 `not_evaluated` 表示取值依据尚不存在（如容量基准、留出集），在依据建立前不得宣称通过 |
| 层·级 | 层：L1 单元、L2 模块集成、L3 契约与产物扫描、L4 端到端、L5 AI 评测、L6 环境验收（定义见 `03-testing-standards.md` §1）；“评审”表示需要 Owner 本人抽检（DEC-15）。级：I 继承行为（Owner 已确认或旧站验证过）、N 新设计要求、P 建议标尺；一行混合多个级别时在句首用【I】【N】【P】分别标出 |
| INV·规则 | 该场景守护的不变行为，以及直接相关的规则、验收或裁决编号 |

### 0.4 与 INV、AC 的关系

- **INV → T**：`01-invariants.md` 每条 INV 的“覆盖场景”列列出本文件的场景；INV 的**主守护层**决定它在哪里通过（L1–L4 每个 PR；L5 随 AI 评测门；L6 随环境验收与观察）。
- **AC → T**：`04-acceptance-criteria.md` 每条验收引用本文件的场景作判定方法；场景本身不是里程碑，**场景全部通过也不等于里程碑通过**（还需八列签收表的其他证据）。
- **F → T**：`07-traceability.json` 每个功能规格卡（F-001～F-067）至少挂一个 T 或明确的待补用例；每个功能全集主编号（已废弃、不排期候选除外）经规格卡至少有一个场景或验收条目；每个 T 至少挂一个 F、一个 INV 或标为系统级。
- 语义准确类场景（T-023、T-029～T-032、T-111～T-117 等）留在 L5，不做 INV。

## 1. 证据级别、结果状态与证据记录

**三个级别**（行级标注，不再按章节统一标）：

- **I，继承行为**：用户已经明确，或旧项目经过明确确认且与本轮目标不冲突的业务行为与数值，例如完整中文、自动供稿、人工撤回保护、费用未知不重发；Owner 已确认的数值门槛（预热后常用公开接口 p95 ≤300ms、首屏桌面 ≤2s 与手机 ≤3s、聚簇成对精确率 ≥95% 与召回率 ≥85% 与关键跨法域误合并 0、首批六发布方与 72 小时 10 条 / 3 发布方 / 两批自动公开；预算口径已由 Owner 2026-10-01 改为不设金额上限，熔断阈值是可调的设计默认值，属 N 级）。**I 级的数值改动须 Owner 书面确认**，并走新的 reviewed ADR。
- **N，新设计要求**：为本轮前后端分离、稳定契约、模块隔离、多 Agent 开发提出的工程约束。
- **P，建议标尺**：尚无真实数据支持的新质量、性能、恢复目标。可用于规划和基准构建，不能写成用户已经确认或当前已达标的数值，也不能在未经留出集检查的情况下作为全面切换的精选门槛（影子运行期可先用 AIHOT 原门槛）；没有取值依据时标 `not_evaluated`。

继承语义，不继承旧项目的技术栈、路径白名单、数百条治理检查、强制 GitHub Actions、55/75 分以及日常逐条二审。测试范围随真实改动选择：纯文案不要求重跑整站；接口、迁移、流程和模型规则变化必须跑相应契约、回归及代表性端到端。没有修改、失败或未解疑点，不为追求“零建议”无限循环审计。

**单条验收结果**使用 `not_implemented / ready_to_test / passed / failed / blocked_external / not_applicable_with_reason`，另有 **conditional（有条件通过）**：必须列出条件与期限，期限到期未满足即转 `failed`。这是与“功能交付状态”（`specified → implemented → locally_verified → integrated → live_verified → quality_accepted`）相互独立的另一条轴；两者的对应与使用见 `04-acceptance-criteria.md` §1.2。

**证据记录**：`passed` 至少附——代码提交（完整 SHA）、契约版本、配置/规则/模型版本、环境和数据集哈希、时间、命令或步骤、结果、责任人（B 的字段）；需要人眼验收的场景再附验收人（Owner 或质量 Agent）、设备（桌面浏览器型号、手机型号）、步骤与结果、未通过项与原因、结论（A 的验收记录字段）。两组字段取并集，记录存入仓库 `docs/acceptance/`（模板 `06-agents/templates/acceptance-record.md`）。模拟模型、合成样例、历史报告必须显式标注，不能代替真实模型、法律质量、上线或持续运行证据。

## 2. 通用测试准备

1. **确定性 fixture 分三类**：①自编（`SELF_AUTHORED`）：保留真实页面的结构与陷阱——分页、置顶旧文、验证页、仅日期、PDF 链接、错误时间、否定、脚注、重复标题、同名不同实体、恶意指令和格式破损——内容自写，链接用 `example.invalid`；②许可允许保存的短事实；③许可范围内的真实材料引用：只存修订 ID、字节哈希、许可依据与回执，正文放私有制品库，**不进 Git**（抓取成功不等于允许保存，许可逐来源逐用途）。fixture 只验行为，不是法律真值金标。
2. **真实材料回放**：取得许可的固定原件及回执、完整字节哈希、页/条款/附件定位；只在有许可的来源上做；禁止测试默认访问生产。保留失败原件的哈希和预期缺口，不能只收“好处理”的样例。
3. **真实基础设施测试**：集成测试通过 `DATABASE_URL` 连接一次性 `*_test`/`*_ci` 数据库（沿用 AIHOT `tests/setup.ts` 的守卫），数据库由执行器提供（本机服务、服务容器或 testcontainers 均可），每个测试文件从已迁移的模板库克隆；可在预留、发出、回执、提交等精确点杀进程、制造重复投递、延迟和网络失败。
4. **语义评测**：真实人工标注者、原件依据、争议裁决和冻结留出集；代理模型生成标签只能算候选，不得改称人审金标。评测由显式任务触发，只用最小必要样本、不设金额上限，规则见 `03-testing-standards.md` §5 与 T-141。
5. **前端测试**：只通过正式 HTTP 契约连接候选后端；desktop/mobile、深浅色、键盘和慢网。SSR/预渲染也不得直连业务数据库绕过 API。
6. **验证不花模型钱**：验证入口（`make verify`）只用假模型、录制响应与黄金集固定夹具，不访问真实模型，执行器不持有模型密钥。
