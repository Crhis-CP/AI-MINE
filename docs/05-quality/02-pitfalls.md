## 阅读约定

- 每条坑点固定六项：**现象 → 根因 → 预防规则（可测试的陈述）→ 自动检查（建议的测试层级 L1–L6）→ 关联（INV / ADR / BR / ENT）→ 证据**；另有一行 **分级 · 落点 · 核验**（v2.0 新增）。
- **分级（grade）**：`incident` = 有日期的线上或交付事故、Owner 明确纠正；`defect` = 代码或设计缺陷、缺口，未必出过事（法规分支经真实原件实验发现、但未上线的问题也按此级）；`risk` = 由证据推导、尚未发生，或只有聊天来源 / 仅 v1.0 转述而没有补到仓库锚点；`process` = 流程与治理教训。权重：先防 incident，再防 defect，risk 与 process 按所在泳道排期。
- **落点**：检查最终在哪里跑。`verify` = `make verify` 子目标（合并前，ADR-0014、ADR-0017），其中自定义的静态规则与 lint 统一由 M0 任务 **T-0011“PIT 检查库”**交付（`06-agents/02-roadmap-and-wbs.md`；`06-agents/01-parallel-development-rules.md` 8.2 的 `pit-checks` 阶段；`07-bootstrap/01-new-repo-bootstrap.md` 第 4 节）；`release-check` = 发布前 `make release-check`；`L6` = 运行时监控与环境验收；`手工` = 发布前手工验收（写明验收人）；`不自动化` = 写明原因。
- **核验**：`路径:行号@main` / `@policy`、PR / Issue 编号。写“本轮已读”的是 2026-09-30 前后在线读取过原文（只读，不落盘）；“对照已核”是核对过关键数字或行号；只写证据行 PR 编号并标“未逐条复核”的，新团队引用前应自行核对。
- **【待落实】**：条目的手段在本包规格里没有落点时，在条目内标【待落实】并列入第 7 节，转交相应文件；落实之前，Agent 不得自行发明替代品，应向架构 Agent 提问。本版写作时逐项核对，已无遗留项（见第 7 节）。
- 证据写法：`#n` 为旧仓库 PR 编号，`Issue#n` 为旧仓库 Issue；`旧ADR-00nn` 为旧项目 ADR，`ADR-00nn` 为本交接包 ADR；`审计Fnn` 为旧仓库 `docs/reviews/product-production-audit-20260920.md@main` 的条目（F01–F20）；`V3审计` 为 `docs/reviews/v3-audit-20260920.json@main`（该文件自注已被前者取代，其 `still_present` 只表示 2026-09-20 首轮判断，未逐项复验）；`POL-T` / `POL-R` / `POL-D` 为法规分支编号；`A:文件`、`B:文件` 为两份原始交接包；`C:`、`D:`、`B1:`、`B2:`、`A2:` 前缀的编号是包外蒸馏报告的原编号，不在本包内、无法解析：v2.0 已从证据行移除（能对应到旧仓库 PR / Issue / ADR / 路径的，已改写成这些指针；对应不到的写“仅 v1.0 转述，未核对”，并按 `risk` 或“未逐条复核”处理），旧编号只在 2.16 保留到 PIT 的对照（`appendix/A-legacy-evidence-index.md` 第 11 节）。

## 1. 一页结论：旧项目为什么变成“屎山”

**一句话**：不是技术栈选错，而是三件事叠加——**产品定义三次翻转**、**治理与交付机器比产品跑得快**、**用补丁而不是结构去解决结构性问题**。到 2026-09-21，旧仓库有 Python 服务代码约 8.95 万行、Python 测试约 10.2 万行、基础设施代码约 2.3 万行、17 个工作流、28 组迁移；真正在线上运行的只有一条约 3.3 万行的流水线，另有约 2.7 万行离线服务从未接入生产。主干 119 个已合并 PR 中，标题带 fix 的有 42 个。

### 1.1 技术层根因

1. **用“整份文档”实现一致性**。全部公开内容（连同全部报告历史）每 5 分钟整池重建成一个 JSON 快照，读取时整份校验；快照逼近 8MiB 后被迫放宽到 12MiB，冷读 12 秒超过网页 10 秒超时。出了问题只调上限和配额（PIT-037、PIT-042、PIT-043）。
2. **身份和状态绑在会变的东西上**。信源 ID 由网址哈希、事件 ID 由模型给的分类与阶段哈希、修订 ID 含许可指纹；一个“待核查”状态同时装着失败、限流、未知费用和人工审核。每调整一次语义，就要写补丁函数和修复批次（PIT-021、PIT-031、PIT-002、PIT-009）。
3. **第二套、第三套同类机制长期并存**。离线的模型网关、事件、编辑、报告服务和规则包从未接入生产；合并后未接线的运营台；两套信源台账；两套正文清洗；另起容器的第三方 Agent 试验（PIT-035、PIT-013、PIT-045）。
4. **业务规则写在错误的地方**。SQL 视图里的正则、迁移里的金额与网址、19 个逐源定制读取模块、事后追加的关键词黑名单；配置与运行对不上（写着并发 2 实际串行；配置 38 项而核实启用 21 项，“31 项”是第一代注册表，不能和 38 项混算）（PIT-047、PIT-048、PIT-007、PIT-034、PIT-036）。
5. **交付链比产品还重**。云临时凭证、云主机命令通道、签名制品、30 多个部署与探针脚本；交付链自身的故障（制品配额、令牌不触发工作流、下载中断、网络地址池耗尽、系统盘 33GB）占去大量迭代；2026-09-26 检查因 Actions 预算限制在步骤启动前失败，绑定 Actions 的必过检查无从发布，Owner 随即决定“GitHub Actions 如果不是必须，以后不用”（旧ADR-0038，PIT-053～PIT-056、GOV-21）。

### 1.2 流程层根因

1. **靠文字和仪式保证的东西都腐烂了，靠自动化测试守住的基本守住了**。旧 ADR 索引止于 0030，多份被取代的 ADR 仍标“已接受”；运营台合并后并未接线，文档却写成可用；部署保护把全局暂停遗留 5 天无人察觉。反过来，真实 PostgreSQL 回归、预算预留、下架防复活在多次重构中都保持住了（PIT-074、PIT-052、GOV-01、GOV-05）。
2. **治理成本高、防护低**。总控逐项审查、两阶段知识收口门、约 91KB 的任务边界文档、约 57KB 的测试策略、断言文档措辞的测试（一次改文字就有 36～51 个断言失败）、每次都“阻止发布”的 AI 审查机器人（Owner 已于 2026-08-17 撤销该门禁）——都没有挡住快照膨胀、信源停滞和 5 天停更（PIT-069、PIT-077）。
3. **巨型 PR 与多工具并行没有边界**。单个 PR +108,061 行、388 个文件；另一个 PR 把另一工具的已提交与未提交修复整包并入；现场 43 个工作树、3 处未提交成果（PIT-075、PIT-076）。
4. **“完成”的口径不统一**。本地通过、CI 通过、合成回放被当成上线或质量证据；24 小时观察从未通过；PR 测试计划里的“生产回读”大量未勾就进入下一轮（PIT-073、PIT-010）。
5. **同一问题反复修**。中文阅读链路 9 月 8 日至 16 日连续 8 个恢复 / 修复类 PR，交付链 10 个（#168 已计入前者），都没有同步补上“下次自动发现”的检查（PIT-079）。

### 1.3 产品定义层根因

1. **产品定义三次翻转**。7 月按“政策情报、只有元数据、不用 AI、桌面优先”建设；9 月 5 日一夜切换为“自动情报、模型中文整理、全文阅读、AIHOT 式阅读站”；9 月 13 日改为“先恢复连续中文阅读，精选与评分延后”；9 月 26 日 Owner 批准法规升级（草稿 PR #180 扩到 33 国及 3 个国际组织，旧ADR-0037），法规线自此与资讯线并行、隔离运行（ADR-0016）。约 2.5 万行代码和一批 ADR 在两周内事实作废（PIT-074）。
2. **先建治理与安全，后定义“谁用、用来做什么”**。三套高保真设计比稿停等 17 天后被“复刻 AIHOT 交互”取代；多管理员动态口令与四角色权限一天合并 5 个 PR，10 天后改为只用密码（PIT-060、GOV-15）。
3. **读者可见功能反复加撤**。精选、热点、评分、主题入口加了又撤，占位页长期存在；精选规则先后经历“模型一票否决 → 纯分数 → 停用归零 → 历史残留”（PIT-063、PIT-030、PIT-041）。**（v2.1：Owner 2026-10-01 已定精选、热点沿用 AIHOT 并矿业化，随全面切换上线，入口不再占位，只有数据不足时才显示诚实空态；预防手段见 PIT-030、041、063、106。）**
4. **数量口径不清**。321 条原表记录、320 个目标、38 项配置、21 个启用、0 个核实持续供稿被混在一起汇报；“至少 6 家独立发布方”被当成目标而不是下限（PIT-010、PIT-007）。
5. **范围决定与供给度量没有分开**。原表还有 290 个目标未接通时，法规升级草案已扩到 114 个研究来源，其中只有 3 个有取得依据，0 次真实模型调用、0 次公开。扩范围本身是 Owner 2026-09-26 的决定，不是失误；问题是研究、取得、内容、运行四类完成数被混在一起汇报，全范围完成数至今为 0（PIT-078）。

| 全部功能完成后全面切换（DEC-19） | PIT-058（切换前的存档备份）、PIT-104 | 没有“对等即切换”；新站上线当天旧站停止服务，不保留只读、不切回（2026-10-03）；旧站在切换前按自己的上限运行 |
| 信源许可全部按 Owner 声明建档（DEC-33） | PIT-005、015 | 九项一律“允许”（`owner_declared`、不设自动到期），逐源收紧；缺权限版本记录才失败关闭；没有“未知按禁止”与“批量确认”；robots 明确禁止的路径默认不抓，负责人可凭许可逐源覆盖并留审计 |

## 2. 坑点清单

> “预防规则”是可以直接写成断言的陈述；“自动检查”给出建议的测试层级（L1 单元、L2 模块集成、L3 契约、L4 端到端、L5 AI 评测、L6 环境验收，定义见 `03-testing-standards.md`），用例名带 PIT 编号。

### 2.1 信源与采集

#### PIT-001 试抓预览在 API 进程里联网
- **现象**：运营台点“测试与预览”时，请求在被刻意断网的 API 容器里直接抓站，全部返回域名解析失败（2026-09-21 线上实测）；旧的成功预览记录掩盖了按钮其实不可用。
- **根因**：后台请求同步调用联网采集器，违背“只有采集进程联网”的隔离；测试只在有网络的环境里跑过。
- **预防规则**：api 进程的任何路由都不发起出网请求；试抓只写一条绑定配置版本的任务，由 worker 执行并回写；同一配置版本的在途任务复用；配置被改或信源退役后旧结果作废；中断的试抓不显示旧的成功结果。
- **自动检查**：L2 给 api 注入“出网即失败”的网络桩，调用试抓接口只产生任务、出网次数为 0；worker 完成后结果可读；配置版本变化后结果被丢弃。
- **关联**：目标架构第 3 节（运行拓扑：只有 worker 与 fetcher 出网）；ADR-0005、ADR-0019；ENT-05；OP-04（最小私有页面里的试抓预览）；BR-SRC-21、BR-ACQ-01、BR-ACQ-13；AC-SEC-11。
- **证据**：#178；`docs/reviews/admin-click-verification-20260921.md:5-7@main`。
- **分级 · 落点 · 核验**：`incident` · `verify`（L2：api 注入“出网即失败”的网络桩） · 对照已核：`docs/reviews/admin-click-verification-20260921.md:5-7@main`；#178

#### PIT-002 保存任何配置都会暂停信源、清空检查点
- **现象**：保存已有信源的任意字段，都会让修订号 +1、状态回草稿、暂停、清空采集进度，并要求 24 小时内重新预览才能启用；为了避免“升级许可范围就丢翻页进度”，又专门写了保留进度的范围升级函数和草稿修复函数。
- **根因**：没有区分“影响采集身份的变更”和“文案、许可说明类变更”，一律按最严格处理，再用专用函数打补丁。
- **预防规则**：只有入口地址、采集方式、选择器与分页规则、允许路径这类“采集身份字段”变化才产生新配置版本并要求重新试抓；名称、说明、许可说明、检查频率的修改不暂停信源、不清空检查点、不重新计费。
- **自动检查**：L1 参数化用例逐字段断言“是否需要试抓 / 是否保留检查点”；字段分类由配置 schema 元数据生成，新增字段未归类时 `verify` 失败。
- **关联**：ENT-56（采集配置：管理态、健康态、预览、游标、配置版本）、ENT-04；领域模型原则 3；BR-SRC-22、BR-SRC-23。
- **证据**：旧迁移 0018、0023 的专用函数；#154。
- **分级 · 落点 · 核验**：`incident` · `verify`（L1 参数化 + 配置 schema 元数据） · 未逐条复核：#154；旧迁移 0018、0023 的专用函数

#### PIT-003 自动流程覆盖人工对信源的操作（ABA）
- **现象**：自动接入与许可范围升级可能在负责人编辑、暂停、恢复、归档的同时启用信源；旧项目只好把“最近一条审计记录的编号”当作控制令牌在行锁内比对，审计表因此承担了并发控制，且没有防篡改保护。
- **根因**：数据模型没有版本列和“人工触碰”标记，并发控制借用了审计表。
- **预防规则**：所有写操作带期望版本号（版本列比较交换）；人工暂停、归档、编辑之后，自动流程不得改变该信源的启用状态；审计表只追加、不参与并发判断，任何更新或删除被数据库拒绝。
- **自动检查**：L2 真实 PostgreSQL 并发用例覆盖两种加锁顺序和“暂停→恢复”的 ABA；自动接入遇到人工暂停时保持暂停；对审计表执行更新、删除断言失败。
- **关联**：INV-04、INV-05、INV-35；ADR-0011；ENT-46；BR-SRC-24、BR-ACQ-18、BR-OPS-05；PIT-095（租约围栏与发送前复核）；B:H-035（验收 T-011、T-064；T-100）。
- **证据**：#146（8 个真实 PG 并发用例，回归先失败后通过）；#153（保留原暂停状态、不覆盖并发的人工修改）。
- **分级 · 落点 · 核验**：`incident` · `verify`（L2 真实 PostgreSQL 并发用例） · 对照已核：PR#146 描述（8 个真实 PG 并发用例、审计记录编号当并发令牌）；#153

#### PIT-004 严格网络客户端没有“受控例外”，真实信源大面积接不上
- **现象**：赞比亚矿业部 RSS 因证书链不完整被拒（浏览器能打开也不算）；`application/xml; charset=UTF-8` 被当成不允许的类型；法规接口因请求头缺 XML 返回 406（加拿大 Justice，`docs/policy-upgrade/xml-negotiation-audit.md:3-6@policy`）；PDF 不在类型白名单。一度“没有第二个信源能通过冻结的传输与解析契约”，接入停滞。另有两件事**不是要绕过的故障**：跨主机重定向被拒，是 Issue#129 / #130 刻意加的安全加固（一个信源新增入口，不得扩大其他信源的重定向目标）；湖南来源在服务器上 TLS 握手 `BAD_ECPOINT` 失败，旧仓库明确“没有关闭 TLS 验证、变更许可或自动启用这个草稿来源”。
- **根因**：安全客户端的例外只能改代码，信源层面没有经审定的、数据化的例外配置；另一头，重定向目标曾按“所有已审定入口”并成一个白名单，新增入口会扩大所有既有入口的重定向范围（Issue#129）。
- **预防规则**：①可由**信源级配置例外**解决的症状只有四类：证书链补全、额外内容类型（含 `application/xml; charset`）、请求 Accept、PDF 类型。它们是信源配置版本的字段，经负责人审定并试抓通过后生效，只对声明它的信源生效。②重定向默认只允许同一主机（BR-ACQ-16）；确需例外时，必须是“信源配置版本字段 + 精确目标主机 + 审定人 + 试抓证据”，不得因另一个信源使用了该主机而自动生效，白名单上限以 BR-ACQ-16 为准；入口默认只用 https，http 入口只能由负责人为单源开例外并留审计（DEC-56）。③**任何例外都不能关闭**：SSRF 防护、主机名与 TLS 证书校验、私网与元数据地址拦截。④TLS 握手失败（如 `BAD_ECPOINT`）、WAF 空响应（如 202 空页）、限速、授权拒绝、无变化是不同状态，如实记为“不可达 / 受限 / 无变化”；不降级 TLS、不切换浏览器绕过、不当作成功或“今天没有新稿”，重试有界（BR-ACQ-08、BR-ACQ-14、BR-ACQ-28）。⑤失败原因映射为中文业务原因。
- **自动检查**：L2 录制失败样本库（证书链不全、XML 类型变体、缺 Accept 得 406、PDF 类型）作为回归；例外只作用于声明它的信源；**两个信源的主机互相重定向必须失败**（沿用旧 `tests/ingestion/test_network.py` 的思路）；SSRF 用例（私网、元数据地址、DNS 重绑定）与“TLS 校验不可关闭”在任何配置下都通过；握手失败、WAF 空响应夹具断言状态为“不可达 / 受限”而非成功。
- **关联**：INV-16、INV-33；ADR-0009、ADR-0019；ENT-04；BR-ACQ-07、BR-ACQ-08、BR-ACQ-14、BR-ACQ-16、BR-ACQ-28；AC-SEC-11；B:H-009、H-020（规范化指纹见 PIT-086；H-020 验收 T-006、T-019）；验收 T-014、T-015。
- **证据**：Issue#129 / #130（`CHANGELOG.md:29-39@main`）；`docs/reviews/source-preview-followup-20260921.md:19@main`；#79；#123；#124；#126；#180；旧ADR-0014。
- **分级 · 落点 · 核验**：`incident` · `verify`（L2 录制样本、SSRF 与 TLS 用例） · 本轮已读：`CHANGELOG.md:29-39@main`、`docs/reviews/source-preview-followup-20260921.md:19@main`；对照已核：#79、#123；WAF 202 空响应只有聊天来源（B:H-009），按 `risk` 处理，不当作已发生事故

#### PIT-005 robots 规则从未在运行时执行
- **现象**：旧项目的生产采集进程没有运行时 robots 抓取与解析，robots 只出现在注册表的人工审定项和研究期探测结论里（探测中 11 个不可用、1 个拒绝）。
- **根因**：robots 被当成接入时的一次性人工核对，而不是每次抓取前的门。
- **预防规则**：抓取前按信源检查 robots（缓存有效期可配置，默认 24 小时）；不允许时不发出目标请求，记录“来源拒绝自动访问”；robots 明确禁止的路径默认不抓；负责人可凭许可（Owner 声明许可，或来源方书面授权、明确允许自动访问的官方接口条款）逐源覆盖并留审计，记入信源权限版本（与 BR-ACQ-15、BR-SRC-36 一致）。
- **自动检查**：L1 解析夹具（允许、禁止、404、5xx、超大文件）；L2 断言“禁止”时目标地址请求数为 0，覆盖依据写入权限版本；验收：T-142（robots 与礼貌抓取，三条路径禁止路径请求数 0）。
- **关联**：ADR-0009（`fetch` 权限）；INV-32；BR-SRC-16、BR-ACQ-15（预览、研究、生产三条路径都遵守）。
- **证据**：`services/ingestion/policy.py:51-52@main`（只检查注册表里的 robots 状态，没有运行时 robots 抓取与解析代码）；研究期探测结论（11 个不可用、1 个拒绝）仅 v1.0 转述，未核对。
- **分级 · 落点 · 核验**：`defect` · `verify`（L1 解析夹具 + L2 请求数断言） · 对照已核：`services/ingestion/policy.py:51-52@main`（只检查注册表里的 robots 状态，services 内没有 robots 抓取与解析代码）

#### PIT-006 调度不自愈：逾期信源不采、子步骤失败整轮跳过、阶段互相饿死
- **现象**：（a）新闻线线上问题：失败后“下次运行时间”被一路推后，逾期信源长期不采，24 小时观察一直停在“需要关注”；启动时某个引导步骤失败，整轮跳过所有到期信源（#159、#160、#161）。（b）法规分支的模拟回归（未上线）：90 秒片段里先做两次 30 秒采集，剩下 30 秒，而模型调用要预留 70 秒，结果四轮模型调用数为 0（`docs/policy-upgrade/service-scheduling.md:9-12@policy`）。
- **根因**：采集、正文、模型、发布挤在一个串行循环里，没有按阶段独立排队和公平调度，也没有“最久未推进”的度量。
- **预防规则**：任一已启用信源距上次尝试不超过“2×检查间隔 + 宽限”；单个步骤或单个信源的异常不跳过其他信源与阶段；各阶段独立队列与并发（lane × stage），度量“最久未推进时长”并告警；采集不在剩余时间不足的窗口里启动长请求（旧分支做法：不足 35 秒不启动 30 秒请求，数值为初值）；**法规线按来源与国家轮转**：同一来源同一时刻最多一个取得任务，失败退避让出位置，一国内容多不能抵消另一国长期无检查，逐国“最后成功检查”可观测并告警（BR-POL-18）。
- **自动检查**：L2 注入固定时钟推进时间，断言逾期信源被安排；注入启动步骤异常，其他信源照常采集；各阶段积压告警用例；模拟“国家 A 大量内容 + 国家 B 长期无检查”，断言 B 在固定时间内被检查（POL-T57），并保留“慢抓取不饿死模型阶段”回归（B:H-031，验收 T-075、T-076、T-137）。
- **关联**：INV-16、INV-29；ADR-0005、ADR-0016；BR-OPS-01、BR-OPS-03、BR-OPS-09；BR-ACQ-04、BR-ACQ-05、BR-ACQ-07、BR-ACQ-26；BR-POL-18；T-137（双业务线公平与隔离基准）。
- **证据**：#159、#160、#161；`docs/policy-upgrade/service-scheduling.md:9-18@policy`（迁移 0038 的三阶段轮转）。
- **分级 · 落点 · 核验**：`incident` · `verify`（L2 固定时钟）+ `L6`（最久未推进告警） · 本轮已读：`docs/policy-upgrade/service-scheduling.md:1-20@policy`（法规线为模拟复现，非线上事故）；未逐条复核：#159、#160、#161

#### PIT-007 接入靠逐源定制代码和写死的上限，原表目标长期停滞
- **现象**：为 19 个来源写了专用读取模块；接入要经过受保护工作流和暂停 worker 的一次性资格容器；原表 320 个目标到 9 月 15 日仍有 290 个没有任何采集配置；已审定接入上限写死为 20，要改代码提到 40 才能继续；注册表校验器强制 30–50 个启用，而运行时期望恰好 31 个。
- **根因**：把“新增一个信源”做成工程任务，缺少通用适配器（中国政府网站集约化平台、网页列表）和数据化的接入入口；数量上限写进 schema 与代码。
- **预防规则**：通用适配器能覆盖的信源，从填写“国家 + 名称 + 网址”到启用，经最小私有页面（OP-05 添加信源 → OP-04 试抓预览 → 启用）、一次受审计导入（带期望版本号）或一个 PR 完成，不需要代码变更、部署或暂停 worker；新增专用适配器必须在任务卡写明通用方案为何不行（BR-ACQ-21）；数量上限只作为资源保护写在配置中，超限降级并告警，不整批拒绝。
- **自动检查**：L4 最小私有页面新增信源→试抓→启用→下一轮被调度，全程无部署；`verify` 统计专用适配器数量变化并要求任务卡说明（T-0011）；lint 禁止在 schema 与校验器里写数量常量。
- **关联**：目标架构第 8 节（配置即数据，能力即代码）；ADR-0018；ENT-06、ENT-07、ENT-56；第 11 节第 4 条；BR-SRC-17、BR-SRC-30、BR-ACQ-20、BR-ACQ-21；OP-05。
- **证据**：#163；#166；旧ADR-0029（“耦合的旧上限”）；`config/live/source-integration-progress.json:22-39@main`。
- **分级 · 落点 · 核验**：`incident` · `verify`（L4 + 专用适配器计数，后者依赖 T-0011） · 对照已核：`config/live/source-integration-progress.json:22-39@main`（290 个原表目标未配置）；未逐条复核：#163、#166

#### PIT-008 分页与检查点陷阱
- **现象**：某新闻站 `/page/2/` 实际重复第 1 页；置顶旧稿提前结束了窗口扫描；没有日期的卡片无法按日期停止；列表里一张跨栏目的同站卡片让整页解析失败，挡住其余合法条目；澳大利亚法规预览只看前 3 条原始结果就判“无结果”。
- **根因**：分页与终止规则按“理想网站”编写，没有针对真实异常建立夹具。

### 2.2 正文、解析与编码

#### PIT-011 压缩与字符集处理缺失
- **现象**：两个中国官方栏目返回的 gzip 字节原样进入 HTML 解析器，页面“能打开”却取不到任何有效材料；生产链路把所有 HTML 当 UTF-8 解析，没有 GBK/GB18030 处理；法规原文后来不得不专门拒绝 NUL 与替代字符，防止解析器静默改写正文。
- **根因**：解压与字符集判定散落在各适配器，没有统一实现和夹具。
- **预防规则**：统一的抓取客户端负责解压（gzip/deflate/br，有解压后大小上限与完整性校验）和字符集判定（响应头 → BOM → 页面声明 → 探测）；解码失败报 `decode_failed`，不把乱码入库；**字符完整性分线**：资讯线解码后替代字符比例超过阈值的材料不得晋升为正文；法规材料严格解码，任何 NUL 或 U+FFFD 都阻止晋升并标“字符完整性未核验”（BR-ACQ-17、BR-POL-19）。
- **自动检查**：L1/L2 夹具：gzip、错误声明编码、GBK、GB18030、Big5、含 NUL 的页面，断言解析结果与期望文本逐字一致；法规夹具：U+FFFD 出现在表格数字里时拒绝晋升（B:T-018）。
- **关联**：`03-testing-standards.md` 第 3 节“录制的信源响应”；BR-ACQ-16、BR-ACQ-17、BR-MAT-07、BR-POL-19；B:H-013（验收 T-018）。
- **证据**：#143；#180；`docs/policy-upgrade/status.md:275@policy`（NUL 被解析器静默替换为替代字符后仍标完整）；“生产链路没有 GBK / GB18030 处理”仅 v1.0 转述，未核对。
- **分级 · 落点 · 核验**：`incident` · `verify`（L1/L2 夹具） · 对照已核：`services/ingestion/network.py:305-321@main`（gzip 字节原样进入 HTML 解析器）；未逐条复核：#143、`status.md:275@policy`

- **现象**：缺少发布时间时，来源更新时间、本站公开时间被拿来顶替，列表只好加“更新”“本站公开”徽标说明来源；成文日期、签署日期、网页发布时间容易混用；联邦公报的“公开阅览登记时间”并不是正式发布时间。
- **根因**：时间只有一个“发布时间”主字段，其他时间是可选补充。
- **预防规则**：来源发布、来源更新、正式刊发、登记 / 公开阅览、成文 / 签署、生效、系统发现、本站首次公开分字段保存，每个字段带依据（TimeAssertion，ENT-60）；任何时间都不顶替另一种时间；签署日晚于发布日时标为冲突；CMS 标题、页脚版权、人物署名、正文落款不得当作来源或日期（B:H-011）；法规线的法律日期与法律状态分维记录，见 PIT-087。
- **自动检查**：L1 夹具：只有更新时间、成文日与发布日不同、只有登记时间的文书，断言显示标签与字段一致。
- **关联**：BR-TIME-04、BR-TIME-05、BR-TIME-13；ADR-0010；ENT-10 时间组、ENT-60；BR-MAT-14、BR-MAT-16、BR-MAT-17；PIT-087；B:H-011（验收 T-016、T-026）。
- **证据**：旧ADR-0020；#166。
- **分级 · 落点 · 核验**：`incident` · `verify`（L1 夹具） · 未逐条复核：#166；旧ADR-0020 复盘；B:H-011 依据的旧测试（R03）未逐条核

#### PIT-018 来源时区未知、夏令时与缩写歧义
- **现象**：没有时区的分钟级时间容易被当作北京时间；草稿配置漏填时区，只好写迁移补 `Asia/Shanghai`；某订阅源的时区偏移与网页冲突；夏令时缺口与重叠时间需要专门处理；缩写 “CST” 有多种含义。
- **根因**：时区被当成可选配置，缺少“可验证才填，否则降精度”的规则。
- **预防规则**：信源时区只接受可验证的 IANA 名称；时区未知时分钟级时间降为 `date`；夏令时中不存在或有歧义的本地时间拒绝而不猜测；晚于当前时间 5 分钟以上的发布时间拒收；时区问题在试抓阶段报告。
- **自动检查**：L1 属性测试覆盖夏令时切换边界、缩写输入、偏移冲突；L2 试抓未配置时区的信源时给出明确原因。
- **关联**：BR-TIME-02、BR-TIME-12；ADR-0010；BR-MAT-14。
- **证据**：#18；旧ADR-0013；旧迁移 0023 补时区；#141。
- **分级 · 落点 · 核验**：`incident` · `verify`（L1 属性测试 + L2） · 未逐条复核：#18、#141；旧迁移 0023（补 `Asia/Shanghai`）

#### PIT-019 迟到材料改写已发行的报告
- **现象**：报告按来源日期归期，截止后才采到的旧日期材料会让旧一期日报生成新修订，与原规则“迟到内容进入下一期并标注”相反（这是旧ADR-0011 的写法，资讯线现已按 AIHOT 的归期、不再标注“补录”，见 BR-TIME-09、DEC-65），读者看到的历史刊期悄悄变化。
- **根因**：归期规则没有写成独立、可测的函数，报告随每次整池发布重算。
- **预防规则**：报告期间归属是纯函数（沿用 AIHOT，DEC-65：只在精选候选中判定，候选的归期时刻是它的精选公开时刻 `visible_after`，落在窗口 [起, 止) 内的进入该期——日报窗口为前一日 08:00 至当日 08:00，周报为上一个 ISO 周，月报为上一个自然月；不是旧文，BR-RPT-02、BR-TIME-09）；资料进入站点后跨过刊期边界才确定精选公开时间的，归入下一期候选池，不设“补录”；已发行刊期只因更正或下架产生新修订并写明原因，编制之后才入选精选的也不改写已发行的刊期。
- **自动检查**：L1 表驱动用例（出刊时刻前后一分钟〔07:59 与 08:00〕、跨界、跨周、跨月、取稿时仍在提交的发布事务）；L2 断言新材料到达后已发行刊期的修订号不变。
- **关联**：INV-21；BR-RPT-02、BR-TIME-09；ADR-0004 第 5 点；BR-ACQ-12、BR-MAT-15；B:H-023（翻译、转载与回填不得刷新旧闻，更正不得洗掉原发布时间；验收 T-016、T-036、T-037）。
- **证据**：旧ADR-0011；归期规则的其余转述仅 v1.0 转述，未核对。
- **分级 · 落点 · 核验**：`defect` · `verify`（L1 表驱动 + L2） · 未逐条复核：旧ADR-0011

#### PIT-020 首次公开时间事后回填
- **现象**：首次公开时间表晚于公开功能上线，只能用历史快照最早的创建时间回填；早于该迁移且快照已清理的条目只有近似值。

### 2.4 实体、聚簇与去重

#### PIT-021 身份从可变属性或模型输出派生
- **现象**：信源 ID 由“采集方式 + 网址”哈希得出，改网址就换身份；事件与故事 ID 由“法域 + 模型给出的分类 + 文号或网址 + 阶段”哈希得出，模型改判分类或阶段就生成新事件；材料修订 ID 含许可指纹，许可升级制造出“新修订”，又要用作废修订清单、人工修订绑定旧修订等补丁收拾。
- **根因**：用哈希派生 ID 图省事，把“身份”和“当前属性 / 判断”绑在一起。
- **预防规则**：两层：①所有对外、库内主键都是**创建时生成的不可变代理 ID**（可按时间排序的随机编码），网址、分类、阶段、许可变化都不改变 ID，一经公开永不改变（INV-18）；聚类变化用合并 / 拆分记录与别名重定向表达；修订只由内容变化产生。②需要去重的对象另设**天然身份键**作为唯一约束与匹配依据，但不作主键：信源 = 发布方 + 入口族；**法规文书 = 法域 + 发布机构稳定 ID + 文书类型 + 原文文号**（无文号时退化为来源身份 + 官方 URL 并标“弱身份”；中文标题不进入身份；不同地方同文号不合并，BR-POL-02）；事件不设天然键，`identity_key` 只是可重算、可有多个的非唯一候选召回键，变化不改变事件 ID，只靠合并 / 拆分记录（BR-EVT-01）。天然键成员变化（文号勘误、机构更名）走“旧身份退出当前视图 → 原件核对 → 新身份 → 可拆回”，不改代理 ID。
- **自动检查**：L1 属性测试：修改分类、阶段、网址、许可后 ID 不变；L2 事件合并后，被并入事件的原公开 ID 跳转到合并后的事件（新站自身的别名，与旧站地址无关；公开 ID 不复用）；许可变化前后修订数不变；**同文号不同法域不合并**；文号更正后代理 ID 不变；同一文书的两个语言表达归同一文书（B:T-022、T-027）。
- **关联**：INV-18；ADR-0003；领域模型原则 2、3；ENT-11、ENT-16、ENT-21、ENT-78；BR-EVT-01、BR-POL-02；`03-data/02-public-api-contract.md` 的“身份与 ID”条；B:H-018、H-019、H-022。
- **证据**：审计F14；`docs/policy-upgrade/material-processing.md:9-12@policy`（文书 ID 的组成）；`docs/policy-upgrade/official-identities.md:3-14@policy`（身份变化先退出、可拆回）。
- **分级 · 落点 · 核验**：`incident` · `verify`（L1 属性测试 + L2；“ID 只在共享内核生成”的 lint 依赖 T-0011） · 本轮已读：`material-processing.md:7-15`、`official-identities.md:1-22`（@policy）；未逐条复核：审计F14、旧迁移 0015 等补丁

#### PIT-022 规则式识别误判，再用 SQL 视图打补丁
- **现象**：“US$”金额被标成美国，“Indian land”被标成印度，只能在读者视图里用正则排除；俄语词根子串触发矿种误判；“Gold Fields”“Barrick Gold”等公司名被识别为矿种；加密货币与数据“挖矿”混入矿业。
- **根因**：国家与矿种识别用子串词表，缺少词边界、上下文与硬负例；修正写进数据库视图而不是可测试的应用代码。
- **预防规则**：识别规则是应用层纯函数，按 Unicode 词边界或别名表最长匹配，并先排除硬负例（货币符号、公司名、加密 / 数据挖矿）；**字符串包含不等于国家、矿种或法域提及**（如“印度尼西亚”“加勒比海”含另一国名子串，BR-ENT-04）；文章国家不按发布方所在国或域名推断；每个误判先进夹具再修。
- **自动检查**：L1 硬负例夹具库（持续增长，用例名带 PIT-022）：US$、Indian land、公司名、加密挖矿、“印度尼西亚”“加勒比海”“几内亚系列”（POL-T49）；`verify` 禁止在视图与迁移中出现识别用正则（T-0011）。
- **关联**：INV-31；BR-ENT-02、BR-ENT-03、BR-ENT-04；B:H-021（验收 T-025、T-026、T-035）。
- **证据**：`db/migrations/0015_reader_country_exclusions.up.sql:11-20@main`（读者视图里用正则排除 US$ 与 Indian land）；#147（旧迁移 0015）；#22；#148。
- **分级 · 落点 · 核验**：`incident` · `verify`（L1 夹具库） · 对照已核：`db/migrations/0015_reader_country_exclusions.up.sql:11-20@main`；未逐条复核：#147、#22、#148

#### PIT-023 跨语言、跨法域召回几乎为零
- **现象**：同一事件的中英文报道基本关联不上；候选必须同法域、同分类，法域为“未知 / 全球”的材料一律不关联；只靠英文项目名前后的字面锚点匹配。
- **根因**：召回只有字面规则，没有多语言实体别名与语义向量，也没有分语言的评测。
- **预防规则**：召回使用文号、多语言实体别名和有界的确定性候选；法域未知不等于不可关联；召回质量按语言对分别度量 Recall@K 并设门槛。**首版不把向量相似度作为依赖**：新增 embedding 按新付费依赖处理，须基准证明必要并经 Owner 同意（DEC-29），此前事件召回用确定性候选 + DeepSeek 判定。
- **自动检查**：L5 事件关联黄金集按语言对分层的留出评测；L2 同一事件的中英文夹具能进入彼此候选集。
- **关联**：BR-EVT-02、BR-EVT-09；ADR-0007；DEC-29。
- **证据**：审计F04。
- **分级 · 落点 · 核验**：`defect` · `verify`（L2）+ `release-check`（L5 留出集按语言对分层） · 未逐条复核：审计F04

#### PIT-024 否定 / 延后的关联结论永不重算
- **现象**：“无需关联”“延后”的结论持久化后不再复查，之后出现的同事件报道因此漏关联。
- **根因**：否定结论没有绑定当时的候选集，缺少失效条件。
- **预防规则**：否定或延后结论记录候选集哈希与判断时间；候选集变化或到期后重新判断；重判复用付费缓存，不重复计费。
- **自动检查**：L2 先得到否定结论，再加入新候选，断言重新判断且付费调用只发生在新组合上。
- **关联**：BR-EVT-03；INV-14。
- **证据**：审计F07；#173。
- **分级 · 落点 · 核验**：`defect` · `verify`（L2） · 未逐条复核：审计F07；#173

#### PIT-025 候选截断与相反阶段误并
- **现象**：候选按时间截断时，较旧的强匹配被 35 条较新的弱匹配挤掉；未完成处理的稿件挤占召回名额；“拟议”与“批准”、“停产”与“复产”这类相反阶段有被判为同一事件的风险（均曾复现后修复）。
- **根因**：候选排序按时间而不是证据强度；缺少“相反阶段不能是同一事件”的硬规则。
- **预防规则**：截断前按身份证据强度（文号、实体、锚点）排序；未完成处理的材料不进入候选；相反阶段只能判为同一发展线的后续或同一政策线的不同阶段，不能合并为一个事件。
- **自动检查**：L1 反例（旧强匹配 + 35 条新弱匹配；相反阶段对）；L5 误合并率单独报告并设上限。
- **关联**：INV-23；BR-EVT-04、BR-EVT-05；ENT-16、ENT-19、ENT-22（政策进展线，ENT-18 的 `policy_thread` 视图）；B:H-022（验收 T-033、T-034）。
- **证据**：#173；审计文档“追加验证与候选修正”。
- **分级 · 落点 · 核验**：`incident` · `verify`（L1 反例）+ `release-check`（L5 误合并率上限） · 本轮已读：PR#173 描述（相反事件阶段、未完成稿挤占召回均有失败复现与修复证据）

#### PIT-026 代表稿口径不一

#### PIT-027 未核实译名：词表过小、规则过硬
- **现象**：已核实的公司译名表只有 2 家；受控试验中 2 份已付费的完整结果因含“未核实译名”被整稿拒绝，费用白花。

### 2.5 AI、模型与成本

#### PIT-028 费用账本不完整：先调用后记账，未知预留不核销
- **现象**：早期模型调用没有回执，到迁移 0024 才补“回执先落库”；结果未知的调用预留不释放也没有账龄，2026-09-20 账本已花约 4.04 元、预留约 26.92 元，未知预留占掉月额度约 27%，是真实花费的 6.7 倍；清理只能靠一次性手工批次（每批最多 10 篇、1 元，需明确批准）。
- **根因**：回执、结算、核销没有从第一天设计成完整生命周期。
- **预防规则**：先写回执再调用，先持久化完整响应与用量再使用；未知预留有账龄、核销状态与核销依据（供应商账单或确切用量）；未知占用累计 ≥10 元或账龄 >24 小时告警（07-deployment §6.4，BR-COST-03）；**核销是 OP-13“用量与熔断”页上逐笔、必填依据、写审计的操作**，只改该笔回执、不改月度用量，核对完成前该调用永不重发（BR-COST-03、BR-COST-04、BR-COST-16，DEC-55）；未知占用在用量账本里单列、不并入已确认，并计入异常熔断的单日总费用判断（BR-COST-18、BR-COST-20）。
- **自动检查**：L2 假模型注入“调用后、结算前进程退出”，重启后补结算且不重发；账龄与累计告警用例；**异常熔断触发（含达阈值 70% 的预警）时新的付费调用暂停、公开照常，不存在月度硬停**（T-099）；选择“未计费”而不填依据被拒，且月度用量没有被直接修改的入口。

#### PIT-031 自动失败与人工待办混在一个“待核查”状态里

#### PIT-032 模型输出未做语言与结构校验
- **现象**：模型把请求 JSON 信封和英文原文当“译文”返回，被拼进“全文翻译”；一次受控任务因 2048 token 输出上限截断失败。
- **根因**：分段输出只校验 JSON 结构，不校验语言与内容；输出上限凭经验写死。
- **预防规则**：每段译文入库前校验（去除 URL 后统计）：含汉字；不含请求封套特征（语言、段序号、总段数、source 等字段名模式出现 ≥3 个）；拉丁字母数不超过 max(240, 3×汉字数)；单段字符数不异常（旧值 20000）；不含 NUL；不含替代字符 U+FFFD【新增】——任一不满足即坏段。阈值是旧实现值，可随评测调整（DR-35）。坏段只重译该段并保留合格部分；读者端对存量译文在读取时复检，不合格按“正文正在补齐”显示；输出上限按能力配置并检测截断；只有确切用量证明截断时才派生一次替代任务（翻译则二等分），且与格式无效重试不叠加（BR-ENR-09、BR-COST-04）。
- **自动检查**：L2 假模型返回信封、英文原文、截断响应、含替代字符的译文，断言被拒、只重译坏段、截断重试最多一次；读取路径对存量坏译文复检（B:T-017、T-018）。

#### PIT-033 缓存复用与模型准入按错的依据判断
- **现象**：已结算的子调用结果因“祖先调用”的模型白名单不匹配被拒绝复用；供应商响应指纹轮换或缺失时，指纹前置检查挡住了已批准的模型路由；旧严格门的拒绝结论被错误地“零调用改判为通过”。
- **根因**：缓存键与准入依据的是间接信息（祖先调用、指纹），不是该次请求实际使用的模型与价格。
- **预防规则**：缓存键 = 能力 + 输入哈希 + 提示词 / 规则版本 + **实际请求模型**；**价格表版本不参与复用**，只记录在回执与账本里用于结算与审计（BR-COST-05）；复用校验以该次请求的实际模型为准；供应商可变字段只做诊断不做硬门；否定结论的复用需版本化，不能静默翻转；缺价格或付费调用被熔断暂停时，只读复用照常，只有发新请求才检查价格与熔断状态（价格过期见 PIT-104）。
- **自动检查**：L2 子调用复用、指纹缺失、路由切换三类用例；旧否定结论在新规则下必须重新判断；价格表更新后已付结果仍可复用，熔断暂停时缓存读取不被阻止（B:T-068）。
- **关联**：INV-14；BR-COST-05、BR-COST-13；B:H-033（验收 T-021、T-068、T-073；旧测试 `tests/live_pipeline/test_translation_model.py:432@main`）。

#### PIT-037 整站 JSON 快照
- **现象**：每 5 分钟把全部公开内容（含全部报告历史）整池重建成一份 JSON 快照，读取时整份校验；一组测量（590 条材料、283 份报告修订）的快照完整校验约 5.2 秒；另一组同一生产快照的测量（595 篇材料、290 份报告修订）在 0.5 核下冷读 12.0 秒、1 核下 6.4 秒，网页超时 10 秒，公网首个版本请求 10.4 秒后返回 503；快照约 7.7MB 逼近 8MiB 上限，被迫放宽到 12MiB 并把 API 调到 1 核。

#### PIT-046 回滚迁移会毁数据
- **现象**：第一代回滚严格（显式事务、禁止级联）；第三代主迁移的回滚是删除整个 schema 并级联，一次删光全部线上数据与角色；有的迁移没有回滚文件，有的回滚永远报错，多个回滚直接删除反馈、首次公开时间、产品更新、加密模型密钥等业务表。

#### PIT-050 SQL 没在真实 PostgreSQL 执行过

- **根因**：运维脚本与观察器中的 SQL 没有被集成测试覆盖。

- **自动检查**：L2 真实 PostgreSQL 集成（以执行器提供的一次性测试库为主路径，容器化只是可选实现，见 ADR-0017 与 `03-testing-standards.md` 第 1 节）；`verify` 汇总“已执行语句指纹”，与仓库 SQL 清单比对（T-0011）；验收与承接：T-081（AC-M0-04：空库全量迁移，仅在 `_test`/`_ci` 库上运行）；已执行语句指纹比对由 `pit-checks`（T-0011）承接。
- **关联**：ADR-0015；`03-testing-standards.md` L2。
- **证据**：#137；#24；旧ADR-0008（反例）。
- **分级 · 落点 · 核验**：`incident` · `verify`（L2） · 未逐条复核：#137、#24

#### PIT-051 ID 与幂等键规则各自为政
- **现象**：同一前缀 `src_` 在第一代表示“一篇来源文章”、在第三代表示“一个信源”；信源 ID 有 24 位与 26 位两种；请求 ID 契约写 26 位、实际 32 位；内容版本号有三种格式；任务键、模型调用键（跨月仍视为同一请求）、产品更新键、快照内容寻址、预览去重、补齐批次各有一套幂等规则。

- **预防规则**：每类对象一个前缀、一种长度、一个生成器（放在共享内核）；幂等键统一由“任务 + 输入修订 + 能力 + 模型 + 提示词版本 + 配置版本”组成。
- **自动检查**：L3 ID 格式契约测试；lint 禁止在共享内核之外生成 ID 或幂等键。
- **关联**：INV-18；领域模型第 1 节、原则 8；ENT-78；`05-engineering-conventions.md` 第 6 节。
- **证据**：仅 v1.0 转述，未核对。
- **分级 · 落点 · 核验**：`risk` · `verify`（L3 格式契约 + lint 依赖 T-0011） · 仅 v1.0 转述，未核对

#### PIT-052 全局暂停被遗留 5 天无人察觉
- **现象**：部署保护把数据库全局暂停置为开启后没有恢复，worker 于 2026-09-15 16:39:54 UTC 以退出码 0 退出，直到 9 月 20 日现场排查才发现并恢复；期间公开站没有新内容，Web / API 与容器健康都显示“正常”，而 worker 已不在运行、业务记录不推进（审计F01；V3审计 F02“启动健康不等于业务推进”）。
- **根因**：暂停没有原因、持有者、到期时间与告警；健康信号看进程存活与容器状态，不看业务新鲜度；“部署暂停”与“Owner 暂停”共用一个开关，无法区分，也做不到“暂停新闻、法规继续”（`docs/policy-upgrade/operations-exit.md:30-31@policy`）。
- **预防规则**：①**暂停是带持有者的记录**：业务线（news / policy / all）、持有者（owner / deploy / system；原 `budget` 持有者随月度额度取消，异常熔断是独立的熔断状态 ENT-82，与暂停互不覆盖）、原因、操作人、到期时间、版本号（ENT-54，07-deployment §3.5）；暂停全部业务线的全部自动处理最长 24 小时，到期未恢复即告警，不自动恢复。②**部署保护只创建与释放 `holder=deploy` 的暂停**，释放时对版本号做比较并交换，版本已变则不恢复、保留事实并告警；回滚并验收成功后释放，回滚验收失败则保持暂停（带到期与告警）并进入维护态（PIT-091）。③**新鲜度分三层**（阈值以 07-deployment §6.3–6.4 为准）：硬告警——各业务线调度器最近一次成功周期、各阶段最久未推进任务的年龄、暂停超时、worker 进程在但一段时间内没有任何任务完成，与“有没有新稿”无关；供给报告——“检查成功但无新稿”记为稳定但无新稿，不得报为供给通过，也不设新闻到达期限（旧观察器口径）；软告警——只用于资讯线的“最近一次公开距今过久”，法规线改用“计划检查成功 + 真实无更新”，不因没有新法规判宕机。④**独立于应用的外部拨测**读回公开新鲜度探针（07-deployment §6.3(b)）；页面正常、容器健康、worker 心跳都不能单独证明内容在更新。⑤公开页显示“公开内容更新于 …”（`03-reader-pages.md` 通则 24、INV-30）。
- **自动检查**：L2 固定时钟下暂停到期告警；部署失败注入后 deploy 暂停版本已变则不恢复且告警；停掉 worker → 分钟级硬告警；模拟周末零新闻 → 不触发硬告警；L6 外部拨测的新鲜度告警在生产持续运行；验收：T-102（暂停到期告警、业务线停更告警与最近更新时间）、T-146（运行告警送达：去重、恢复、第二渠道与外部拨测）。
- **关联**：INV-30；BR-SITE-02、BR-OPS-01、BR-OPS-09、BR-ACQ-26；ENT-51、ENT-54；`04-architecture/07-deployment-and-ops.md` 3.5、6.3、6.4；`01-product/03-reader-pages.md` 通则 24；AC-OPS-07；T-102、T-146；PIT-091。
- **证据**：审计F01（`docs/reviews/product-production-audit-20260920.md:16-20@main`）；#173；`infra/tencent-cloud/scripts/observe_live_host.py:8-16@main`；`docs/runbooks/automatic-live-intelligence.md:433-451@main`。
- **分级 · 落点 · 核验**：`incident` · `L6`（硬告警 + 外部拨测）+ `verify`（L2 固定时钟） · 本轮已读：`product-production-audit-20260920.md:14-22@main`、`observe_live_host.py:8-16@main`、`automatic-live-intelligence.md:433-451@main`；“心跳与容器健康正常”已改为“Web / API 健康而 worker 已退出”

#### PIT-053 发布残留资源累积：磁盘、镜像、网络
- **现象**：系统盘一度用到 33GB/40GB，清理 94 个旧停止容器、82 个旧镜像标签、19 个旧发布目录后降到 16.7GB；反复部署留下的 Compose 网络耗尽了 Docker 默认地址池，下一个版本无法启动。
- **根因**：只在空间不足时才回收，发布流程不负责清理自己的残留。
- **预防规则**：每次成功发布后自动回收（仅限 07-deployment §3.4 列出的受管对象：已停止且身份匹配的旧容器、无引用的旧镜像标签、已验证的旧发布目录、泄漏的 Compose 网络），只保留当前与上一版本；系统盘已用字节 < 20,000,000,000 是 **Owner 对旧 40GB 主机的要求**，新环境按容量档另定并由 Owner 确认（同一比例即 50%），超阈值告警；部署前检查余量（可用磁盘 ≥4GiB、内存 ≥1GiB）；禁止全局 prune、强制删镜像、删卷、为达标删除业务数据。
- **自动检查**：部署脚本集成测试：连续发布 N 次后残留容器、镜像、网络、目录数量恒定；磁盘告警用例；承接：`make release-check` 的部署脚本集成测试与 L6 磁盘告警（AC-OPS-05、AC-M1-14），不另设 T 场景。
- **关联**：ADR-0012 第 5 点；`04-architecture/07-deployment-and-ops.md` 3.4、第 7 节；AC-OPS-05。
- **证据**：#171；#151；旧仓库 `docs/reviews/storage-retention-20260920.md`。
- **分级 · 落点 · 核验**：`incident` · `release-check`（部署脚本集成测试）+ `L6`（磁盘告警） · 对照已核：`docs/reviews/storage-retention-20260920.md:4-15@main`（33GB → 16.7GB；94 个容器、82 个镜像标签、19 个发布目录）；#171

#### PIT-054 发布失败或中断后生产处理停摆，部署误报成功
- **现象**：部署只确认 worker 进程号存在就记为成功，存在初始化失败后退出的误报窗口；Web 镜像漏掉一份构建输入导致制品失败；失败发布让采集进程停在停止状态；部署保护的“持有”状态与磁盘门禁让 worker 停着等人救。
- **根因**：发布状态机没有覆盖失败路径上“恢复处理”这一步，成功判定太弱。
- **预防规则**：发布成功 = 健康检查通过 + 公开读取冒烟通过 + worker 完成至少一轮处理 + 从主机之外读回发布标识头（07-deployment §3.2）；任何失败路径都回滚到上一版本；**回滚目标同样适用成功判定**，回滚验收失败不得报成功（PIT-091）；镜像从干净上下文构建并检查必需文件。
- **自动检查**：部署状态机测试：在每一步注入失败，断言回滚后 worker 运行、暂停状态与部署前一致；构建后检查镜像内容。
- **关联**：INV-29；ADR-0012 第 3 点、ADR-0017；BR-OPS-07；AC-OPS-06；T-149；PIT-091。
- **证据**：#133；#156；#168；#169。
- **分级 · 落点 · 核验**：`incident` · `release-check`（部署状态机测试，每一步注入失败） · 本轮已读：`docs/runbooks/production-deployment.md:127-130,306-317,383-392@main`；未逐条复核：#133、#156、#168、#169

#### PIT-055 软件交付依赖单一 CI 平台特性与定制通道
- **现象**：时间线（旧仓库）：2026-09-16 GitHub 制品存储配额用尽，签名包上传失败（#169）；用应用令牌合并不触发 push 工作流，主干提交没有 CI 与制品（#170）；9 月 20 日的交付通道（#173）用“可配置的临时隔离 runner”，真实 Required 检查与 GitHub OIDC 签名继续保留，签名包可存入私有 Release 附件——**此时仍在用 Actions**；9 月 26 日检查因 Actions 预算限制在步骤启动前失败，Owner 随即明确“GitHub Actions 如果不是必须，以后不用”，当日 19:05 UTC 停用 Actions；主分支保护里绑定 Actions 的必过检查仍在，任何未经验证的合并继续被阻止（旧ADR-0038，`docs/policy-upgrade/status.md:92-109@policy`）。另：OIDC 换取云临时凭证用了 7 个 PR 才打通；云主机命令通道有 64KB 限制，签名包下载接近完成时失败只能重下。迁移风险：**服务器当前只信任历史 Actions 签发身份**，新密钥或自签文件不会自动成为可信发行方。另外，旧仓库在每次主干提交时都构建完整大制品（V3审计 F13，2026-09-20 首轮判断仍存在）。
- **根因**：把平台特性（配额、令牌行为、命令通道）放进了生产发布的关键路径，交付链自身成了最大故障源。
- **预防规则**：验证入口是单一的 `make verify`，可在任意独立执行器上按完整 Git SHA 运行并产出机器可读回执（ADR-0017 第 1～3 条）；合并前必须有与该 PR 最终 SHA 绑定的完整回执，不手工填成功、不删除必过检查来掩盖未执行的验证；镜像按 SHA 构建，附 manifest、SBOM 与项目自有密钥的离线签名，信任根由 Owner 一次性授权并显式迁移，不能先关闭验签来上线（ADR-0017 第 5、6 条）；验证通过不等于已上线，以外部读回的发布标识头为准；生产新闻流水线、采集与公开不依赖 CI、制品仓库或代码托管平台（INV-29）；不设云端定时 CI，容量与漂移检查在发布前与运行时监控里做；验证只在发布前按目标 SHA 运行，不在每次提交时构建完整大制品。**必过检查的发布者与 CI 平台不可绑死**：旧仓库的必过检查（`Required / quality-gate`）把发布者固定为 GitHub Actions 应用，预算阻止作业启动、Actions 停用后，该检查无从发布，管理员又同受约束，所有合并都被挡住，本机还缺 Docker 跑不完 `make verify`（`docs/policy-upgrade/actions-transition.md:20-34@policy`）；新仓库先不设“必须通过检查”的平台强制，由集成人按最终 SHA 绑定的回执核对，待最小 GitHub App 实际发布过一次真实检查之后再开启（两阶段，`06-agents/01-parallel-development-rules.md` 8.5）；结构测试只断言“存在并执行统一入口”，不断言某个 workflow 文件存在。
- **自动检查**：`verify`：发布前必须有与目标 SHA 绑定的完整 verify 回执（含 SHA、tree、锁文件哈希、OS / 架构 / 工具版本）；`release-check`：镜像摘要与 manifest 核对、离线签名校验，篡改与未知信任键被拒；部署脚本行数预算（超出需说明）。
- **关联**：INV-29；ADR-0012（第 2 条已由 ADR-0017 取代）、ADR-0014、ADR-0017；`06-agents/01-parallel-development-rules.md` 8.1～8.5；GOV-21；B:H-007（验收 T-085）。
- **证据**：#169；#170；#173；#180；#51–#57；#150；#179；`docs/policy-upgrade/status.md:88-112@policy`；`docs/architecture/decisions/0038-provider-independent-delivery.md:9-58@policy`；`docs/reviews/v3-audit-20260920.json:148-157@main`（V3审计 F13）；`docs/policy-upgrade/actions-transition.md:20-34@policy`。
- **分级 · 落点 · 核验**：`incident` · `verify` + `release-check` · 本轮已读：`status.md:86-113@policy`、`0038-provider-independent-delivery.md:1-58@policy`、`actions-transition.md:1-60@policy`、V3审计 F13 条、PR#169 / #170 / #173 元数据与 #173 描述；原“停用 Actions 后改用临时 runner”的先后已更正

#### PIT-056 自写部署脚本与宿主探针成为故障源
- **现象**：runc 版本解析拒绝了 Ubuntu 的包版本号；同一套接字上的已连接条目被误判为监听；Docker internal 网络不发布端口，回环发布无效；只读挂载下 Caddyfile 权限让非 root 进程读不到；缺少网络工具时探针直接报未知；镜像加载后 ID 跨引擎不一致；前置检查有描述符竞态；部署器丢弃底层错误只报“docker 命令失败”，只好另写诊断工作流；升级器整份替换 Caddyfile，把私有 MCP 路由一并抹掉。

#### PIT-057 容量靠猜：冷读超时，线上临时改配额造成漂移
- **现象**：API 只给 0.5 核，冷读超过网页超时，只好在线上临时改成 1 核（运行配置与发布版本不一致，要等下次发布才消除）。旧机数据点（不是新项目的规则）：worker 在 640MiB 内存下必须一次只抓一个信源，否则会在中途退出；一次观察中旧 4 核 4GB 主机上的 API 容器用到 234.9/256MiB。
- **根因**：资源限额按估计配置，没有基准测量；线上手工调整不受版本管理。
- **预防规则**：容器资源限额写在版本化的编排文件中，线上与期望配置的差异被自动发现（配置漂移告警，07-deployment §6.4）；并发度与内存按实测基准取值，不照搬旧机常数；内存口径用 MemAvailable 与容器 cgroup 工作集，不以 MemFree、页缓存或“used”判断耗尽（07-deployment §7.2）；每次扩源批次后记录资源占用与单位成本；容量基准在发布前（`make release-check`）与运行时 L6 监控，不依赖 nightly CI。
- **自动检查**：配置漂移检测（运行配置对比当前版本期望）；发布前容量基准回归。
- **关联**：`04-architecture/07-deployment-and-ops.md` 第 7 节（7.5 旧机数据点）；第 11 节第 9 条；AC-OPS-04；B:H-041（验收 T-093、T-094、T-096）。
- **证据**：#175；#161；旧ADR-0035；审计F18；旧仓库 `docs/reviews/admin-click-verification-20260921.md`“内存对照”。
- **分级 · 落点 · 核验**：`incident` · `release-check`（容量基准）+ `L6`（漂移告警） · 对照已核：`docs/reviews/admin-click-verification-20260921.md:21@main`（234.9/256MiB）；未逐条复核：#175、#161

#### PIT-058 备份与恢复从未演练
- **现象**：备份与恢复脚本早已写好（加密转储到私有对象存储，保留 7 日 + 4 周），但生产备份与隔离恢复始终没有完成记录，一直是待办；旧仓库运行手册还记载备份桶未创建（`enable_cos_backup=false`）、命令行工具未安装、恢复证据 pending——切换前旧库没有经验证的异地备份。
- **根因**：备份被当作一次性脚本任务，而不是有记录、有告警的日常运行。
- **预防规则**：每日自动备份并记录结果：客户端加密（私钥由 Owner 离线保管，不在主机与对象存储），默认保留 7 日 + 4 周（可配置，不是 Owner 要求）；首次生产部署前完成一次空机隔离恢复演练，切换前再做一次，此后每月一次，恢复到随机命名的隔离库并跑冒烟，核对账本、下架集合与人工修订，记录实际 RTO；结果经告警推送并可由只读运维 MCP 查询（不设系统页）；备份或演练失败、超期（>35 天未成功）告警；恢复后先套用最新抑制集，不复活已下架内容、不重复收费、未知预留保留（07-deployment §5、B:H-042）。M1 验收目标 RPO ≤24 小时、RTO ≤2 小时（Owner 可调）。**全面切换前的硬前置**：对旧生产库做一次加密全量备份并在隔离库恢复校验，**用于存档，兼作切换窗口内中止切换的兜底，不导入新站，切换完成后不再用于恢复旧站服务**（AC-OPS-03）；桶是否已存在由 Owner 确认，不默认“已有”。
- **自动检查**：恢复演练任务的 L2 测试（含“下架 → 备份 → 恢复 → 各出口不可见”）；L6 告警：距上次成功备份 >36 小时、演练超期；验收：T-084（隔离恢复演练：RPO ≤24 小时、RTO ≤2 小时）。
- **关联**：`04-architecture/07-deployment-and-ops.md` 第 5 节；BR-OPS-07；OP-20；AC-OPS-01～03；PIT-091；B:H-042（验收 T-081～T-084）。
- **证据**：旧ADR-0010、旧ADR-0027（“备份 / 恢复从未在生产演练”）；`docs/runbooks/production-deployment.md:55,160@main`；`docs/runbooks/infrastructure.md:17,105@main`。
- **分级 · 落点 · 核验**：`risk` · `L6`（备份与演练告警）+ `手工`（Owner 保管私钥、批准建桶；演练由运维泳道执行） · 本轮已读：`production-deployment.md:53-56,159-160@main`、`infrastructure.md:16-17,104-105@main`；未逐条复核：旧ADR-0010、旧ADR-0027 复盘

### 2.9 安全与认证

#### PIT-059 数据库与密钥文件的权限
- **现象**：worker、运维控制台、迁移与终结器曾共用数据库属主凭据，“只追加”的触发器对它们无效；数据库加固撤销默认连接权限后，新建的登录角色连不上，需要显式授权；Compose 文件式密钥的属主与权限设置被忽略，只能在宿主上预置 0400 文件。
- **根因**：权限设计是逐步补的，验证用的是切换角色而不是真实登录。
- **预防规则**：数据库登录按角色从第一天分开（公开只读、反馈写入、私有业务、认证、worker、迁移、备份七类；fetcher 没有数据库登录，`06-security-and-access.md` 第 1 节）；权限测试用真实登录执行；服务级密钥是 root 属主、0400 的普通文件、只读挂载，配置里只放文件路径，不放环境变量与命令行（06 §4.1）；各进程只挂自己需要的密钥；启动自检属主、模式、类型与大小，不符即拒绝启动。
- **自动检查**：L2 权限矩阵：每个角色尝试越权写入都得到权限错误；启动自检用例（属主或模式不符拒绝启动）。
- **关联**：INV-26；`04-architecture/06-security-and-access.md` 第 1、4 节；AC-SEC-06、AC-SEC-07；ADR-0019。
- **证据**：#134；旧ADR-0025、旧ADR-0028。
- **分级 · 落点 · 核验**：`incident` · `verify`（L2 权限矩阵 + 启动自检） · 未逐条复核：#134；旧ADR-0025、旧ADR-0028 复盘

#### PIT-060 后台身份设计过早过重
- **现象**：2026-08-26 一天合并 5 个身份相关 PR（加密存储的逐人动态口令、重放保护、会话、四角色与二次验证设计），10 天后 Owner 决定只用“账号 + 密码”，动态口令与多角色基本弃用；更早的回环运营台合并后并未接入生产。
- **根因**：在“谁用后台、用来做什么”确定之前先做了完整的安全方案。
- **预防规则**：身份与权限按当前真实用户（唯一负责人 + 具名管理员）实现最小可用集：**只用账号 + 密码**（Owner 2026-09-06 决定，旧ADR-0031），不排期动态码、不预留界面入口；observer 只作机器只读身份；新增安全机制必须对应已记录的威胁与用户场景；权限矩阵以规格表为准，规格外的角色与认证因素不实现。
- **自动检查**：L2 权限矩阵用例与规格表一一对应（`verify` 比对规格编号与用例名）。
- **关联**：BR-IAM-01、BR-IAM-02、BR-IAM-03；ENT-44；OP-01、OP-15；DEC-05、DEC-32。
- **证据**：#94；#96；#98；#101；#102；Issue#103；#136；旧ADR-0022、旧ADR-0026；#77。
- **分级 · 落点 · 核验**：`process` · `verify`（L2 权限矩阵用例与规格表一一对应，T-0011） · 对照已核：PR#94 / #96 / #98 / #101 / #102（2026-08-26）、PR#136（2026-09-05）；本轮已读：#103 是 Issue 而非 PR

#### PIT-061 公开入口的限流、可信代理与探针
- **现象**：伪造的预登录材料可以改动目标账号的限流桶；反向代理必须用直接 TCP 对端替换客户端提交的转发头，宿主回环上的“多客户端”冒烟其实都来自同一来源；令牌桶在第二个客户端启动时回补，探针不稳定；每进程突发额度 20，而刷新一次页面就要 18 个请求；公开 `/readyz` 被代理到未限流的数据库就绪检查。
- **根因**：限流键与可信代理链没有统一设计，页面请求数与限流参数互不知情。
- **预防规则**：限流键只来自反向代理写入的对端地址（哈希）或已验证身份，未认证请求不能影响他人的桶；只信任配置的代理跳数（`trustProxy` 设为 1 跳或具体地址，绝不设 `true`）；限流在应用层令牌桶，不在 Caddy；公开读的突发额度必须 ≥ 首屏 API 请求数的 2 倍，且首屏请求数有上限；`/healthz` 只在内部可达、`/readyz` 不对公网开放，公网只暴露一个经限流的公开新鲜度探针（06 §2.2）。
- **自动检查**：L2 伪造转发头、伪造预登录、并发客户端的限流用例；L4 统计首屏请求数；部署后冒烟检查公开域名访问私有路径返回 404（INV-25）；验收见 AC-SEC-09 与 T-097（限流键与可信代理）、T-098（首屏请求数预算）（`05-quality/06-acceptance-scenarios.md` 第 16 节）。
- **关联**：INV-25；`04-architecture/06-security-and-access.md` 2.2、AC-SEC-09；T-097（限流键与可信代理）、T-098（首屏请求数预算）。
- **证据**：#102；#116；#118；#45；#47；旧ADR-0018、旧ADR-0019。
- **分级 · 落点 · 核验**：`incident` · `verify`（L2 / L4）+ `release-check`（部署后冒烟） · 对照已核：旧ADR-0019:21（每进程突发 20、首屏 18 个请求是设计上限）；本轮已读：`docs/runbooks/production-deployment.md:130@main`（公网 `/readyz` 回归门禁）；未逐条复核：#102、#116、#118、#45、#47

#### PIT-062 日志与协作记录泄露敏感信息
- **现象**：即使关闭访问日志，反向代理的运行时错误日志仍会记录 OAuth 回调查询值；部署 Issue 的早期评论含身份类信息，需要 Owner 在网页上手工编辑删除；云接口错误信息要改成只输出白名单错误码。

- **分级 · 落点 · 核验**：`incident` · `verify` · 未逐条复核：#172、Issue#50、#52

#### PIT-063 读者可见功能反复加撤，入口长期占位

- **现象**：一个 PR +108,061 / −319 行、388 个文件；另有 +29,584、+23,065（整合另一工具的已提交与未提交修复）、+19,661、+18,032 行的 PR；法规升级草案 +64,921 行、195 个文件一直未合并。

#### PIT-081 法规长文被套上新闻线的容量上限，或被降成元数据与摘要
- **现象**：2024-04-18 联邦公报里的硅尘规则（文号 2024-06920）有 3,903 个节点、1,479,755 字节文本，超过旧新闻线共用的 1MB 正文上限；同一期 XML 共 8,211,943 字节，官方 PDF 268 页、12,093,983 字节，处理计划约 6.36MB 且还没有算上图件文字（旧分支实测）。若沿用新闻线“超限只留元数据与原文入口”（PIT-014），这类法规会被降成摘要或元数据而无人察觉。旧分支为此给法规材料单设上限：2,000,000 字节、8,192 个节点、2,000 字节处理分段，新闻上限不变；另用一份自编的约 1.49MB 单文书验证了完整保存与逐段重组——那是压力夹具，不是真实样本，也不证明成本。
- **根因**：把新闻线的容量与降级规则当成全系统常量；容量按“一篇短文”假设，没有用真实长文测量。
- **预防规则**：容量规则按业务线分开配置：资讯线保留 BR-ACQ-22、BR-MAT-13（超限保留元数据，不保存截断正文）；**法规线不适用**——超限记 `blocked_capacity`，先分段或延后处理，不截断、不降为元数据或摘要、不标“全文”（BR-POL-12；旧ADR-0037:54-56@policy“不把不合格法规降成摘要继续公开”）。法规线的上限与分段值由真实样本测定后写入配置，旧值（2,000,000 字节、8,192 节点、2,000 字节分段）只作起点，“2MB”是旧实现的法规上限而不是产品上限；单个材料或处理计划的数据库上限（旧值 8MiB）仍然有效，超出则拒绝而不截断。成本与容量按真实长文（百万字节级、含图件）测量，自编夹具只证明存取。

#### PIT-082 图件、公式与表格按位置绑定，“数量一致”不等于“配对正确”
- **现象**：同一份联邦公报规则：XML 里有 118 处图件引用，只有 117 个唯一标识（重复出现的位置不能去掉）；官方 PDF 含 118 个图像对象与 118 个可提取的图件标识，XML 与 PDF 的标识多重集合相同、提取顺序不同——这不能当作按序配对或语义一致的证据；PDF 第 5 页肉眼可见完整的统计表，本机 OCR（Tesseract）单表识别却丢失大量单元格，旧分支明确不把它接为合格附件。美国 eCFR Title 30 批量 XML 另有 75 个图件引用与 11 个公式未决，因此不晋升为完整材料（引 `10-policy-service.md` 附录 A.1）。
- **根因**：用“数量相等”或“出现顺序”推断对应关系；把 OCR 输出当作合格附件；转换后的 XML 对表格与图件的呈现本身有限制（GPO 格式指南）。
- **预防规则**：图件、公式、OCR 表格按“文书 + 页码或节点 + 引用身份”逐位置绑定，重复引用保留各自的位置；数量或标识集合相等不是配对证据；缺失的位置逐一登记为缺口，检查器对原件始终返回“不完整”（`complete_original=false`），无图件的 XML 也不因此自动合格；OCR 与视觉输出须核对结构、单元格、单位与脚注并经评测后才能采用；任一决定性缺项 → 不运行全文解读、不公开确定性解读，只公开基本事实并列出缺项与原文入口（BR-POL-12 第 3、4 条）。
- **自动检查**：L2 夹具：“118 处引用 / 117 个标识”型的重复引用、XML 与 PDF 顺序不同、OCR 缺格的表格；断言不按序配对、缺口逐位置记录、材料不晋升为完整（B:T-020、T-029、T-030）；评审：附件表格给出阈值时，附件取得前不宣称适用（POL-T02）；扫描不清的关键数值不过则暂缓该结论（POL-T28）；跨页表格恢复正确行列（POL-T44）。

#### PIT-084 历史沿革链接不进当前取得队列
- **现象**：目录的每个主条目都带历史沿革链接（606 个主记录对应 1,192 个沿革链接）。若把沿革链接当作当前正文目标，旧版回扫会覆盖新版；若首次发现时间取“整轮确认”的时刻，会冒充真实的发现时间。

#### PIT-085 文书、版本与语言要分开：一种语言失效、迟到或误配，不能牵连另一种
- **现象**：同一部加拿大法规的英法两个版本（`SOR/2002-222` 与 `DORS/2002-222`）是同一文书、两个不同版本，文号、正文、原文版本各自独立。若一份文书只有一个“当前版本”槽，最后完成处理的语言会覆盖另一种语言的可读版本；切换语言时，旧语言迟到的正文或 409 响应会混入新语言、甚至误撤销新语言；若按标题或数字相似来推测配对，会把不同文书误并。
- **根因**：把语言当成文书的一个属性，而不是独立的版本表达；配对没有显式依据，也没有可拆回的路径。
- **预防规则**：每份文书每种语言保存一个当前公开版本，各语言分别核对资格，旧公开头与不可变历史保留（BR-POL-23）；配对只凭目录显式且双向一致的官方标识（如 `olid`），不按标题、语言后缀或数字相似推测；目录更新改变官方 ID、配对、语言、文号或类型时，相关旧材料先退出当前视图，经原件核对形成新身份，历史与目录快照不删除，误配可追溯拆回；列表与国家数量按文书计，不按语言；默认语言取稳定排序的首个合格语言，只是展示默认值，不是法律效力排序；切换语言取消旧分页请求并重新挂载正文，旧语言迟到的响应不混入；一种语言失效，其他合格语言继续可读，旧链接给出版本变化提示，不静默回退为另一种语言；配对不证明两个版本同期、等义或现行有效，“历史法定版本”与“当前可读语言版本”是不同维度。

- **根因**：请求头与指纹都按新闻线（HTML、原始字节）设计。
- **预防规则**：运行时请求头按来源适配器声明的已接受格式设置，接收端仍独立拒绝不匹配的类型，不把 HTML 错误页当原件；处理版本改用包含注释与命名空间作用域的规范化 XML 指纹——属性值、正文、注释与命名空间绑定的变化仍会改变指纹；该指纹只判断 XML 表达是否一致，不表示两个不同地址已获得身份合并许可，也不推断法律修订；对外阅读页显示“源站 XML 快照”，不把内部哈希当作官方法定版本名称；XML 里的 current-date 与网页上的汇编截至、更新时间分别记录，不据此宣称法定现行性。使用条件仍逐用途核对：政府页面的复制条件不自动替代来源契约、第三方内容检查或完整中文质量验收（BR-POL-17）。
- **自动检查**：L2 录制样本：缺 Accept 得 406 的回归与“声明 XML 后得 200”；同内容、不同字节表达不重复建版本，属性值变化则改变指纹；返回 HTML 错误页时不当作原件（B:T-006、T-019；与 PIT-004 的 406 回归同源）。

#### PIT-087 法律日期与法律状态分维记录；“Final rule”不等于已生效
- **现象**：联邦公报的“Final rule”标签与日期不能推出当前的生效或适用状态（旧分支检查器明确“不从 Final rule 或日期推断当前生效 / 适用状态”）；官方目录里的 in force 标签不能机械变成“全法已施行”，汇编日期与目录标志只是发现线索，不是现行性证据；计划日期或附条件日期不是“已经发生的变化”；只有日期的证据不补造时分或时区。
- **根因**：一个“阶段 / 生效日”字段承载公布、登记、施行、适用、截止、废止等多种含义；用抓取、翻译完成或网页更新日期代替法律事实。
- **预防规则**：法律性质、制定阶段、公布状态、公布日期、分项施行、适用期、截止事项、废止分别记录（DEC-36，BR-POL-03）；日期的性质（原文公布、实质变化、注册登记、汇编、其他、未知）与“是否已经发生”分开核对，互不顶替；列表使用已确认发生的公布或实质变化日期，不用翻译完成、抓取或网页更新日期代替；不从 Final rule、in force 标签、汇编日期或目录标志推断全法已施行；条款可分项生效，实施条款另定的，依实施条款；只有日期的证据不补时分、不补时区（PIT-016、PIT-017）。
- **自动检查**：L1 / 评审夹具：Final rule 加登记日期、in force 但实施条款另定（POL-T05）、法律已公布而部分条款待另行公告（POL-T04）、已通过法案尚未正式公布（POL-T10）、计划生效日未到、追溯适用（POL-T18）（B:T-026、T-027、T-032）。
- **关联**：PIT-017；BR-POL-03、BR-POL-15；AI-18；INV-24；DEC-36；F-049；B:H-026（验收 T-026、T-027、T-032；T-119、T-124）。
- **证据**：`docs/policy-upgrade/federal-register-originals.md:3-6@policy`；`docs/policy-upgrade/interpretation-runtime.md:20-28,47-53@policy`；`docs/policy-upgrade/official-identities.md:14@policy`（仅目录撤下不推断法律废止）；`docs/policy-upgrade/xml-negotiation-audit.md:21@policy`（current-date 与网页汇编截至日分别记录，不据此宣称现行性）。
- **分级 · 落点 · 核验**：`defect` · `verify`（L1 夹具）+ `手工`（具名评判人评审，DEC-15） · 本轮已读：上列三处 @policy

#### PIT-088 解读必须覆盖全文，文末例外可以否决结论
- **现象**：只读前几段形成的结论，会漏掉原稿没有引用的文末例外、附件与定义。旧分支的处理链因此规定：从当前原文与完整中文候选重建全部部分与哈希，不信任外部传入的 complete 标记；分组核对原文、事实与译文；长文经最多六个子输入的有界归并逐层合成，输入覆盖必须完整；形成候选解读后，对每个候选结论、标题和相关性重新覆盖全部原文分组核对——原稿未引用的文末例外也能否决结论；证据摘录不被称为全文，不能截取第一段代替全篇。
- **根因**：长文用首段或摘录代替全篇；校验只检查被引用的部分。
- **预防规则**：解读用固定的分段核验链，生产主链路不用 Agent 循环（DEC-16）；任何缺失的分组、缺失的结论判断、不支持的引用或反证，都不能得到“完整核对记录”；“模型辅助核对通过”不等于独立法律权威——来源与当前版本、使用许可、建设期真实质量评估与原子公开条件仍是独立门槛（BR-POL-11）；重要附件缺失时只公开有依据的基本事实（PIT-082）；父任务只在全部依赖结果存在时可执行，来源、原文、内容或控制版本变化后，旧任务不能继续晋升结果。
- **自动检查**：L2 / L5：自编约 100 段长文的全分支归并与全原文复核（旧分支已有）、“末条排除特定矿种 → 保留排除条件”（POL-T01）、只有首段结果无法组装完整上下文；原文失效、暂停与全篇反证的回归（B:T-029、T-030、T-032）；真实语义质量要由评判人抽检（DEC-15），程序门禁不能证明法律语义正确。
- **关联**：PIT-014、PIT-081、PIT-082；INV-36；BR-POL-11、BR-POL-13；AI-17、AI-19、AI-20、AI-21（取代已废弃的 AI-11）；DEC-15、DEC-16；F-048；B:H-027（验收 T-029、T-030、T-032）。
- **证据**：`docs/policy-upgrade/interpretation-runtime.md:1-45@policy`。
- **分级 · 落点 · 核验**：`defect` · `verify`（L2）+ `手工`（评判人抽检） · 本轮已读：`interpretation-runtime.md:1-66@policy`；旧分支的测试数据均为自编，真实语义质量记录为空

#### PIT-089 没有旧法原文，不写“由 X 改为 Y”；勘误的范围要精确
- **现象**：没有另行取得并关联旧规范原文时，新旧条款比较保持不可用，不凭模型记忆填旧法；修订、废止、勘误、实施与普通引用关系，都需要原文明示文号、适用事项、条件和引用证据；程序不会因为数据库里暂时只有一个同号候选就认定法律身份；自动链接还要求引文里出现目标官方地址，且目标是单文书地址、有唯一的合格公开版本；文本差异不被自动称为法律修订；汇编目录元数据不能独立晋升为法规解读；某条款被更正时，只改变相应分段的缓存键，未变化部分可复用，但依赖全文的经营影响分析随之失效。B 另列“勘误被当成全新法规、语言限定的更正被扩成所有语言”，只有聊天来源，按 `risk` 处理。
- **根因**：用“看起来像修订”的文本差异或模型记忆生成变化声明；没有把勘误绑定到具体版本、语言与条款。
- **预防规则**：变化声明绑定“双版本 + 官方关系”；证据不足时写“无法完成对比”，不写“由 X 改为 Y”“修订了什么”（BR-POL-14 第 4 条、DR-52）；关系只由原文明示建立，同号歧义不猜（BR-POL-04）；勘误与更正的影响范围精确传播——条款、语言、版本各自限定，不向外扩大。
- **自动检查**：L2 / 评审夹具：无旧法原文时新旧比较不可用；同号候选唯一、多个、集合地址、已撤回目标分别是否生成链接；同一 URL 的正文被勘误后保存新版本并使解读重新核验（POL-T09）；旧法修订仅改两条时只重算相关条款（POL-T20）（B:T-027、T-028、T-032）。
- **关联**：PIT-021、PIT-087；INV-36；BR-POL-04、BR-POL-14、DR-52；AI-18、AI-21；ENT-79；F-049、F-050；B:H-028（验收 T-027、T-028、T-032）。
- **证据**：`docs/policy-upgrade/interpretation-runtime.md:27,57-63@policy`；`docs/policy-upgrade/historical-reading.md:29-31@policy`；`docs/policy-upgrade/material-processing.md:29-31@policy`。
- **分级 · 落点 · 核验**：`defect` · `verify`（L2 夹具）+ `手工`（评审） · 本轮已读：上列三处 @policy

#### PIT-090 退出运营台：撤页面不等于撤能力，不得连带删除反馈收件、服务身份、账本与法律证据
- **现象**：旧分支的退出依赖清单显示，十个运营页（信源、模型配置、内容、审稿、异常、反馈、用量预算、账号、网站资料、我的账号）各自依赖共享的数据表与路由。公共反馈与站点设置在管理认证之前独立处理，直接删掉整个 OperationsAPI 会让前台反馈回归；全局 `processing_paused` 被 worker 多处共用，做不到“暂停新闻、法规继续”；退出清单明确“不得为了退出运营台删除共享数据库、凭据或已有法律证据”。该清单是静态依赖核验，旧分支尚未执行配置迁移，也没有关闭任何生产入口。
- **根因**：把“页面”与“能力”混为一谈，退出时按页面删代码。
- **预防规则**：取消页面不取消能力。旧分支的退出顺序（只作经验参考：新站没有旧运营台可退出，也不导入旧站配置，DEC-20）：先取得有效的非秘密配置快照与秘密引用；工程导入走现有校验、比较并交换与审计，先干运行并比较配置等价；在隔离候选环境验证“无登录状态重启、来源任务、用量与熔断、只读 MCP、公共反馈、下架一致性”；再关闭运营页面与不必要的公网写入口，保留工程恢复路径；最后只撤销退役控制面的会话与权限。必须保留：公共反馈收件与隐私保护（截图与联系方式保持私有）、服务身份、费用回执与用量账本、审计、持久下架、真实的人工修订与冲突记录、未知付费调用的核对；退出前先把暂停拆到业务线（ADR-0016）。回退到经验证的上一软件与配置版本，保留新旧审计、付费回执、游标与下架事实。新项目从第一天起不建日常运营台（ADR-0018、BR-OPS-08），本条是旧分支退出运营台时的教训（“撤页面不撤能力”），用来约束“最小私有页面”的边界。取消运营台后，Owner 的日常接触面只剩公开站、告警与说明书，所以“Owner 系统说明与应急手册”（小白版 + 专业版 + 凭据清单 + Owner 操作清单）是 M1 上线交付物与验收项（`01-product/04-private-operations.md` 8.1；`04-architecture/07-deployment-and-ops.md` 9 上线检查表第 10 项）。
- **自动检查**：L4 / L2：隔离候选环境里无会话重启后，定时任务、配置、预算与诊断照常（POL-T40）；关闭运营页面后公共反馈仍可提交且收件私有；新闻暂停时法规继续运行（POL-T47；B:T-077）；退出过程不删除共享账本与审计（B:T-062～T-066、T-080）。
- **关联**：ADR-0016、ADR-0018；BR-OPS-08、BR-OPS-09；DEC-04；PIT-052、PIT-060；B:H-039（验收 T-062～T-066、T-077、T-080；T-127、T-135）。
- **证据**：`docs/policy-upgrade/operations-exit.md:3-45@policy`；`docs/architecture/decisions/0037-policy-intelligence-all-jurisdictions.md:21-22,37-39@policy`。
- **分级 · 落点 · 核验**：`defect` · `L4` + `verify`（隔离候选环境验证）+ `手工`（Owner 演练手册） · 本轮已读：上列两处 @policy

### 2.14 产品层、交付与通用补充（PIT-091～PIT-107）

> 本节收三类条目：旧仓库有记录、但两份交接包都没写成坑点的事故（回滚验收、价格表到期、质量与成本泄漏点）；B 包独有的产品层与通用教训（多数只有聊天来源，按 `risk` 或 `process` 处理）；以及 Owner 验收方式带来的操作经验。条目格式与 2.1～2.13 相同。

#### PIT-091 回滚本身也要验收；进程被杀后没有自动回滚
- **现象**：旧仓库在首次部署之前，由独立核验员发现部署脚本在“回滚到上一版本后、上一版本的冒烟检查失败”时仍然打印成功（Issue#46 / PR#47，2026-08-15）；修复前的失败测试输出是 `FAIL: 0 == 0`，修复后，回滚冒烟失败必须非零退出、关闭公开入口、不打印成功。同一轮发现的另一条高危是公网 `/readyz` 绕过限流、直达数据库就绪检查（见 PIT-061）。旧运行手册还写明：可捕获的错误会进入回滚，但 SIGKILL、断电或主机故障**不会自动回滚**；只有留下“数据库激活已提交、主机交接未完成”一致证据的候选，才有显式的恢复入口；回滚目标不存在或恢复失败时保持公网关闭并返回非零；停止或读回失败要输出“公网监听关闭未验证”并要求立即人工处置，不能把入口配置当作端口已关闭的证据。
- **根因**：只设计了“失败就回滚”，没有给回滚结果本身设成功判定；发布状态没有持久化阶段，硬崩溃后没有对账入口，只能靠人工登录主机。
- **预防规则**：回滚后必须对上一版本重跑同一套成功判定（健康检查 + 公开读取冒烟 + worker 完成一轮，PIT-054），任一步失败则：非零退出、进入维护态（公开入口改为只读静态页或关闭）、告警、不登记产品更新、不打印成功；发布状态机持久化每个阶段，进程被杀或断电后，下次启动（或定时对账）检查未完成的激活或回滚并给出恢复命令；入口是否已关闭要由独立读回确认，读回失败如实写“未验证”；回滚应用版本不等于回滚数据（PIT-046）。回滚期间的暂停处理见 PIT-052。
- **自动检查**：`release-check`：部署状态机测试在“上一版本冒烟失败”“数据库已激活但主机切换未完成”两点注入故障，断言非零退出、入口关闭或只读、不打印成功；硬崩溃后再次启动能对账并给出恢复命令（AC-OPS-06）；验收：T-149（发布失败自动回滚与三类回退分开演练）。
- **关联**：INV-29；ADR-0012 第 3 点、ADR-0017 第 8 条；BR-OPS-07；`04-architecture/07-deployment-and-ops.md` 3.2、6.4；AC-OPS-06；T-149；PIT-046、PIT-054、PIT-058；B:H-042（验收 T-081～T-084）。
- **证据**：Issue#46；PR#47（2026-08-15 合并，+122 / −21 行、6 个文件）；`docs/runbooks/production-deployment.md:127-130,304-317,383-394@main`。
- **分级 · 落点 · 核验**：`defect` · `release-check`（部署状态机注入测试） · 本轮已读：Issue#46、PR#47 描述与上列手册行；定级说明：首次部署前由独立核验发现并修复，没有线上事故记录

#### PIT-092 范围由职责矩阵决定，不由例子决定
- **现象**：Owner 用阿根廷举例，说明联邦与地方的发布职责不同，被一版方案写成“以阿根廷 24 个地区为交付本体”（B:H-002，来自讨论记录，**只有聊天来源**）。旧仓库 ADR 的原则是：示例不产生优先国家或假政策；33 国是已授权的研究底表，不是数量上限；地方与部门是否必需，以“有权发布”与覆盖缺口判断，不按行政区数量验收。
- **根因**：把举例当规格，把数量当目标。
- **预防规则**：覆盖分母来自固定的目标表（`data/jurisdictions-36.json`：36 个对象，每个带 `news_scope` / `policy_scope`）与发布职责矩阵（法域 × 发布机关职责 × 七个经营主题）；示例不得增删分母，也不生成该国的行政区清单或优先级；范围变化必须由 Owner 决定（PIT-078）；受阻的对象仍留在分母里（BR-SRC-03、BR-POL-25）。
- **自动检查**：`verify`：分母等于法域字典；规格或任务卡里出现“按某国示例”的清单而没有目标表依据时，评审标出（B:T-009、T-089；POL-T50）。
- **关联**：PIT-078；BR-SRC-03、BR-POL-25；DEC-03；F-045、F-046；B:H-002（验收 T-009、T-089）。
- **证据**：`docs/architecture/decisions/0037-policy-intelligence-all-jurisdictions.md:14,17-19,30@policy`；B:discussion-distillation（D02，仅聊天）。
- **分级 · 落点 · 核验**：`risk` · `verify` + `手工`（规格评审） · 本轮已读：`0037:9-35@policy`；聊天来源未补到仓库锚点

#### PIT-093 降优先级不等于删除一条业务线
- **现象**：“新闻优先级降低”曾被误读成永久删除新闻产品；法规的进展又与原新闻规则混用（B:H-003，**只有聊天来源**）。旧仓库 ADR 的原话是“新闻不适合法规不等于新闻垃圾”，并要求“法规业务独立准入与资源调度”。
- **根因**：把“排队先后”与“产品存废”混为一谈。
- **预防规则**：新闻线与法规线是两个业务域，共享可靠的底层能力，独立准入、暂停与优先级（ADR-0016，BR-OPS-09、BR-POL-21）；积压时翻译与加工的先后只改变排队次序（法规 > 官方一手 > 其他），不降级、不停线；不设预算保底额与调剂额（DEC-08、DEC-09，BR-COST-12；BR-COST-11 已废弃）；合格的新闻不因“没有影响分析”被阻塞（INV-13、BR-ENR-06）。
- **自动检查**：L2：暂停资讯线时法规照常运行；法规积压时资讯实时流不受阻（B:T-031、T-077）。
- **关联**：PIT-038、PIT-090；ADR-0016；DEC-01；B:H-003（验收 T-031、T-077；T-137）。
- **证据**：`docs/architecture/decisions/0037-policy-intelligence-all-jurisdictions.md:23,39@policy`；B:discussion-distillation（D01 / D02，仅聊天）。
- **分级 · 落点 · 核验**：`risk` · `verify`（L2） · 本轮已读：`0037:21-24,39@policy`

#### PIT-094 生产运行不依赖开发会话
- **现象**：维护 Agent 在会话里逐站读正文，工程时间替代了服务器上的自动生产——B 记为 Owner 2026-09-27 的直接纠正（B:H-006，聊天来源）。旧分支文档的口径是“目标仍是服务器持续运行，而不是 Codex 在会话中逐站读正文”，ADR 明确“Codex 不进入生产调度依赖”。

#### PIT-105 解读把示例、措施或他方义务写成“一切矿企都受影响”
- **现象**：B:H-029（聊天来源）：跨境供应链的示例被写成“一切矿企都受影响”；限制性指令（如暂扣令）被写成“具体货物已被没收”。旧分支有仓库依据的相邻规则：涉及银行的义务不能直接改写为矿企义务，不使用模板内部项目或“我公司”的口吻；每项经营影响保留地区、法定主体、受影响主体、活动、条件、直接 / 间接作用、期限和例外。条约有参与方与保留，也不能写成所有国家的企业都受约束（POL-T26）。
- **根因**：把“示例”“措施”和“执行结果”混写成适用范围；影响条目没有逐条绑定证据。
- **预防规则**：影响条目逐条带证据：法域连接、法定主体、受影响主体、产品或活动、条件、例外与不确定性（BR-POL-13）；“措施”与“执行结果”分开（限制令不等于具体货物被没收）；不写“我公司”，不使用内部项目或谈判事实（BR-POL-06、DR-51）；示例只作说明，不成为适用范围；没有依据的量化或确定性结论删除或暂缓（POL-T23）。

## 4. 测试体系教训

### 4.1 有效的

| 做法 | 为什么有效 | 证据 |
|---|---|---|
| 真实 PostgreSQL 的并发与锁序回归 | 能复现只有生产才会出现的竞态与 ABA | #146（8 个用例覆盖两种锁序与“暂停→恢复”）；#152 |
| 假模型故障注入（超时、崩溃、结果未知；旧站的“预算耗尽”注入随月度上限取消，新项目改为“熔断触发”） | 费用与幂等规则在多次重构中没被打破 | #142；#144；#177 |
| 录制真实响应回放，与有界的真实试抓取证分开 | PR 不联网也能覆盖真实页面结构；真实取证只作证据，不冒充“已接入” | #143；#148；#149 |
| 桌面 / 手机 / 深浅色的浏览器 E2E + 无障碍扫描 | 布局与可访问性回归由机器发现 | #141（56 次页面检查无违规、无横向溢出） |
| 确定性线程回归与实测容量基准 | 先测量再调参，数字可复现 | #174；#175；旧ADR0035 |
| 读取实际发布文件的校验回归 | 直接防住“部署成功但更新日志未登记” | #175 |

### 4.2 形式主义的

1. **测试数量成了汇报指标**：Python 测试约 10.2 万行，比服务代码还多；999 项流水线测试与 66 项 E2E 全绿时，生产已停更 5 天——缺的是生产新鲜度监控，不是测试数量（#173、审计F01）。
2. **断言文档措辞与哈希**（PIT-069）。
3. **覆盖率门槛守护了很快被弃用的代码**：管理员认证的 95% 覆盖率门（#136）守护的动态口令与多角色实现，10 天后基本弃用（PIT-060）。
4. **合成回放与合成数据 E2E 被当作质量与上线证据**；“黄金集作为实施前置条件”导致黄金集从未开始（PIT-073、旧ADR0009）。
5. **观察器本身成了需要反复修的系统**：24 小时观察器三次修改，一次也没有完整通过（PIT-079）。
6. **“RED→GREEN 证据登记”变成文书工作**：PR 描述逐条记录失败数与通过数，却没有让质量信号更早出现（#20、#32、#43 等）。

### 4.3 新项目的落地要求

- 每条 INV、BR 与可自动化的 PIT 都有同名用例，验证回执按编号列出通过情况（`03-testing-standards.md` 第 2 节）。
- 汇报不写测试数量，写 INV / PIT 用例状态与 L6 指标。
- L6 至少监控四类（阈值以 `04-architecture/07-deployment-and-ops.md` 6.4 为准）：①**新鲜度分三层**——硬告警（各业务线调度器最近一次成功周期、各阶段最久未推进任务的年龄、暂停超时、worker 进程在但没有任务完成，与有没有新稿无关）、供给报告（“检查成功但无新稿”不得报为供给通过，不设新闻到达期限）、资讯线软告警（最近一次公开距今过久；法规线改用“计划检查成功 + 真实无更新”，不因没有新法规判宕机）；②用量与未知占用的账龄、异常熔断的预警与触发；③备份与恢复演练；④系统盘与内存（内存以 MemAvailable 与容器工作集为口径）。外部拨测独立于应用（PIT-052）。
- 每个真实误判（识别、准入、聚簇、翻译）先进夹具或评测集，再改规则（PIT-022、PIT-034）。
- 黄金集从第一批真实数据开始积累、随产品增长，不作为开工前置条件。
