## 什么时候必须当场记（第 1 层）

- Owner 纠正了我们；
- Codex 或其他 agent 因为交接写错被卡住；
- 自己的 PR 让 CI 失败（查明是本 PR 的原因后）；
- 审查意见经核实属实；
- 交接或汇报里出现事实错误（表名、时间、数字、结论）。

每条五行：

```markdown

- 根因：
- 怎么核实的：（对照了哪份原始记录）
- 以后怎么防：（能写成检查的写检查）
- 证据：PR / 看板评论 / CI run 链接
```

## 定期整理（“做梦”）

- **频率**：每合并 5 个 PR 或每周日，先到为准；开一张整理卡，只改本目录、`02-pitfalls.md` 与必要的规则文字。
- **步骤**：
  1. 读各 `inbox/*.md`，以及上次整理以来的看板与 PR；
  2. 逐条对照原始记录核实，记错的改正；
  3. 和已有 PIT 重复的合并进原条目（补现象与证据），新的编下一个 PIT 号；
  4. 过时的条目标“已被取代 → PIT-nnn”或“已废弃”，写原因，不删除；
  5. 更新 `INDEX.md`（只留当前最常犯的十几条），清空已收入的 inbox 条目；
  6. 同一条坑第二次出现的，按并行开发规则第 13 条补自动检查。
- **整理报告**（写在整理卡与看板）：新增几条、合并几条、**复发几次（同一 PIT 再次出现）**、INDEX 行数。复发次数是这套记忆是否起作用的主要指标。
- Codex 只读复核整理里引用它报告的事实。

## 冲突怎么判

1. **和 Owner 的决定有冲突**（事实、经验或新情况与 Owner 某个决定对不上）：不默默照办任何一边，拿给 Owner 决定，附冲突内容、证据和建议；Owner 决定后记进台账，注明取代了哪一条。决定之前维持现状；继续下去会花钱、出安全问题或违规的，先停下那一步再问。
2. **技术与经验之间的冲突**（PIT 之间、旧做法与新优化之间）：按证据裁决，不打扰 Owner。新的、核实过的经验取代旧的，旧条目标“已被取代”并链接；分不出时以代码、CI、数据库的实际情况为准；仍定不了的，按第 1 条升级。
3. 整理时发现 Owner 早先的某个决定已被后来的经验证明不合适：列在整理报告里请 Owner 确认，不自行改动。

## 不记什么

代码里一看就知道的状态、一次性的进度、聊天里的情绪。只记从代码和环境里查不到的东西：为什么、怎么验证过、下次怎么防。
