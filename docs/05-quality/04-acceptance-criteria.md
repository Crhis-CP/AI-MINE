### 0.3 每条验收必须包含什么

①**对象与数据量**（验什么、多少个）；②**判定方法**（自动化、人工清单或评测）；③**通过阈值**（数值或清单；取值依据不存在时写 `not_evaluated`，不写“达到认可的水平”）；④**证据形式**（回执、报告、截图、读回记录）；⑤**层**（自动化、环境、业务、评测）。其中“层”沿用 A：自动化 = CI 可重复执行；环境 = 真实部署后的自动检查与观察；业务 = Owner 或质量 Agent 在真实浏览器与真实数据上确认；评测 = 黄金集或留出集。三层分开记录，互不替代。

### 1.2 两条状态轴（互相独立）

| 轴 | 取值 | 用在哪里 |
|---|---|---|
| **功能交付状态**（时间线） | `specified → implemented → locally_verified → integrated → live_verified → quality_accepted` | 追踪表 `implementation_state`；交接时全部为 `specified` |
| **单条验收结果** | `not_implemented / ready_to_test / passed / failed / blocked_external / not_applicable_with_reason`，另有 **`conditional`（有条件通过，必须列出条件与期限，到期未满足转 failed）** | 追踪表 `last_result`；场景与验收条目的结果 |

- 与 A 旧称的对应：规划中 = `specified`，开发中 = `implemented`，已合并 = `integrated`，已上线 = `live_verified`，已验收 = `quality_accepted`；`locally_verified`（源码与离线测试有证据）是新增的中间态。
- 各状态需要的证据（对应八列）：`locally_verified` 需要“源码 + 离线测试”两列；`integrated` 需要合并记录与合并后复验；`live_verified` 需要“部署”列（外部读回发布标识头与实际版本），来源相关功能再加“研究、接入”列，不得用一次预览或本地抓取宣称持续供稿；`quality_accepted` 需要“内容”列（留出集或 Owner 本人抽检，未评测写 `not_evaluated`，不得宣称“质量已验证”）、业务验收（Owner 用手机与桌面在真实环境确认）和里程碑要求的 24 小时、7 天观察。`live_verified` 与 `quality_accepted` 必须链接证据，由机器状态给出，文档与汇报不得自行宣称。
- B 的“完成口径六行”合并进八列：文档完成 → “源码”列的规格与契约版本；工程完成 → “源码 + 离线测试”；数据完成 → “研究 + 接入”；部署完成 → “部署”；持续服务 → “24 小时 + 7 天”；内容质量 → “内容”。B 的“测试结果六态”即上表第二条轴（本文补 `conditional`）。

旧仓库的观察器口径（`docs/runbooks/automatic-live-intelligence.md:433-477@main`）把“运行稳定”与“内容供给”分开评级，供给证据必须覆盖全部样本、绑定一个启动版本、晚到的有效样本不能补缺；`docs/runbooks/production-deployment.md:635-639@main` 给出资源判据。两包原先都没有把“近期”“批”“新稿”写成可机械判定的规则，开发者手动导入、回填的老文、起始库存、人工发布都可能被当作“近期新稿”。固定如下：

| 项 | 判定 |
|---|---|
| 新稿 | 在观察窗口内**首次发现**（按最早不可变修订时间，排除起始库存）、**首次公开时间在窗口内**、当前公开修订**已有可读中文**。人工发布、公开时已超过 72 小时的、回填的，单列，不计入 |
| 一批 | 一个自动任务周期产生的新稿集合；“两批”= 两个不同周期，其间**无重新部署、无开发会话介入**（以部署记录与会话审计佐证） |
| 24 小时 | **同一提交与制品**，固定间隔采样（旧口径：24 小时内 289 个样本，约每 5 分钟一个，间隔为推算；新环境可重设但须写明），样本覆盖全窗口，晚到样本不补缺；窗口内换版本则重新计时；“observing”不等于已满 24 小时；混合版本样本不能证明稳定 |
| 指标清单（固定） | 采集尝试、成功、新发现；队列与中文积压；实际公开数；模型费用（已确认、预留、未知）；错误；重启与 OOM；磁盘余量。A 的四项监控并入此清单 |
| 资源判据 | OOM = 0；非预期重启 = 0；磁盘余量 ≥30%（旧值，新环境可按基线调整但须写明）；内存以 MemAvailable 与容器工作集为口径（AC-OPS-04，`07-deployment-and-ops.md` §7.2） |
| 评级 | 分两项：**运行稳定**（通过 / 不通过）与**内容供给**（有新稿 / 无新稿 / 待定）。“稳定但无新稿”不得报为供给通过；**不设新闻到达期限**，低频官方源以检查证据评价 |
| 10 条 / 3 发布方 | 发布日期在 72 小时内、来自不同发布方、每条在公开修订里有中文标题与导读；人工发布与回填不计 |
| 观察器 | 只做只读查询与报告；判定规则写在本文，不写进长期守护进程 |

## 7. 汇报口径（ACC-15）

Owner 要求每次更新都告诉他“目前距离……还有多久”，**以百分比计**（2026-08-31）。旧项目因用配置数、候选网址、测试数量或“进程在跑”代替产品完成而进度虚高。规定如下：

- **完成度 = 有验收记录的条目数 ÷ 全部约定条目数**。分母**包含受阻项**（`blocked_external`、`not_evaluated` 一并计入分母）；分子**只计有验收记录且结论为“通过”的条目**，“有条件通过”不计入分子、单列报告；不得以配置数、候选数、测试数量、心跳正常作分子。
- 条目取本文的验收条目（及其依赖的专项验收）；**资讯线与法规线分别计算**，再给总数；每次汇报写明分子与分母，不只报百分比。
- 汇报格式（周五，`06-agents/02-roadmap-and-wbs.md` §12）：产品阶段（当前关）+ 完成程度（%，含分子分母）+ 已经能自动做什么 + 没做什么 + 风险 + 下一步；功能按 F 编号分维度给证据，环境验收与业务验收分行。
- “还有多久”不以日期承诺：以**尚未通过的条目及其依赖的外部输入**（Owner 输入、授权、采购）与**观察窗口的时间下限**（24 小时、7 天）分别报告。

## 9. 功能级验收（写在任务卡里）

每个功能（F-*）的验收条目写在任务卡的“验收要点”中，引用功能规格卡号（`02b-functional-specification.md` 的“验收 A-F0nn”语句）与本包的 T 场景号，格式：

- **前置条件**：数据与环境状态；
- **操作**：读者或私有操作者做了什么；
- **预期**：可观察的结果（页面显示、接口返回、计数变化、审计记录）；
- **反例**：不应该发生什么（例如“不应调用模型”“不应出现在 RSS”）；
- **证据**：截图、接口响应、计数、日志片段（脱敏）。

功能规格卡的验收语句若在 `06-acceptance-scenarios.md` 里找不到对应场景，在 `07-traceability.json` 标 `pending_case`，不得空着宣称“有测试入口”。
